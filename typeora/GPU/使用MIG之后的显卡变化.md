### 问：MIG是不是需要root权限

**结论先行：是的，MIG（Multi-Instance GPU）的创建、删除和配置需要 root 权限（或等价的管理员权限）。**

下面分层说明，避免混淆“使用 MIG”与“管理 MIG”这两件事。

------

## 一、哪些操作**必须**要 root 权限

以下 **MIG 管理类操作**，本质上是**对 GPU 设备本身进行重配置**，只能由 root 或具备等价能力的主体执行：

1. **开启 / 关闭 MIG 模式**

```bash
nvidia-smi -i 0 -mig 1   # 开启
nvidia-smi -i 0 -mig 0   # 关闭
```

1. **创建 / 删除 GPU Instance / Compute Instance**

```bash
nvidia-smi mig -cgi 19 -C
nvidia-smi mig -dci
```

1. **查看 / 修改 MIG 拓扑与实例配置**

```bash
nvidia-smi mig -lgi
nvidia-smi mig -lci
```

1. **重置 GPU（reset）**

```bash
nvidia-smi --gpu-reset
```

> 原因很简单：
> MIG 会改变 **显存切片、SM 数量、L2 Cache、NVLink 拓扑**，属于硬件级资源划分。

------

## 二、哪些操作**不需要** root 权限

一旦 MIG 实例已经被 root **提前划分好**，**普通用户就可以直接使用**：

### 1. 使用 MIG 设备跑程序（不需要 root）

例如：

```bash
CUDA_VISIBLE_DEVICES=MIG-GPU-xxx/gi/ci python train.py
```

或者在 Docker / K8s 中：

```bash
--gpus device=MIG-GPU-xxx
```

此时用户：

- 看不到完整 GPU
- 只能看到被分配给他的 MIG 设备
- 无法越界访问其他 MIG 实例

### 2. 查看自己可见的 MIG 设备

```bash
nvidia-smi
```

只要驱动允许，普通用户是可以看到**被授权的 MIG 设备**的。

------

## 三、为什么 MIG 设计成“必须 root 管理”

这点和你前面问的 **K8s / Docker GPU 隔离问题**是强相关的：

| 层级                 | 作用                    | 是否需要 root |
| -------------------- | ----------------------- | ------------- |
| MIG                  | 硬件级切片（显存 + SM） | **是**        |
| Docker               | 进程级隔离              | 否            |
| K8s                  | 调度已存在的资源        | 否            |
| CUDA_VISIBLE_DEVICES | 可见性控制              | 否            |

**关键结论：**

> MIG 不是调度器
> MIG 是 **“硬件资源形态的定义者”**

所以：

- **不能**让普通用户随意切 MIG
- 否则相当于让用户重配 PCIe 设备

在真实环境中，一般是 **“root 预切 + 普通用户使用”**：

### 标准流程

1. **管理员（root）**
   - 开机后配置好 MIG 切片
   - 固定切成如：`1g.10gb × 7`
2. **平台层（K8s / 实训平台 / 调度系统）**
   - 把 MIG 实例当成“独立 GPU”
   - 只做调度，不做切片
3. **普通用户**
   - 无 root 权限
   - 只能使用分配到的 MIG

这正是 **NVIDIA 官方 + 云厂商的推荐模式**。

## 一、结论（必须牢记）

**不可以。**

> **一旦某张物理 GPU 处于 MIG 模式：

  - ✅ 只会暴露 **MIG Device（MIG-GPU-xxx/gi/ci）**

## 二、为什么不能“二选一”（这是硬件级限制）

### 1. MIG 不是“软件限制”，而是**硬件重构**

开启 MIG 后，GPU 在硬件层面发生了变化：

- SM 被物理划分
- 显存地址空间被硬切
- L2 Cache 被分片
- Copy Engine / GPC 被绑定

此时：

> **已经不存在“完整 GPU”这个逻辑实体**

所以：

- 驱动层 **无法** 再给你一个“整卡设备节点”
- CUDA 也无法感知“整卡”

------

### 2. NVIDIA 驱动的设备暴露规则（非常关键）

| GPU 状态 | 用户看到的设备                   |
| -------- | -------------------------------- |
| MIG 关闭 | `/dev/nvidia0`（整卡）           |
| MIG 开启 | `/dev/nvidia-caps/*`（MIG 实例） |

驱动层面是 **互斥的**，不是并存的。

### 问：那按照你这个说法，用了MIG之后会影响到原来的多卡A800互联性能吗？

这是一个**非常专业、而且问到点子上的问题**。结论并不是简单的“会 / 不会”，而是**在什么层面、影响到什么程度**。我按“物理互联 → MIG 机制 → 实际使用场景”三层给你讲清楚。

------

## 一、先给出结论（可以直接作为设计结论）

> **会影响，而且是“结构性影响”，不是简单的性能下降。**

更准确地说：

1. **开启 MIG 的 GPU，不能再参与 NVLink / NVSwitch 的跨卡聚合通信**
2. **跨 MIG 实例之间没有 NVLink 可用**
3. **多卡大模型训练（DDP / Tensor Parallel）几乎等同于“被禁用”**

所以：

- **MIG ≠ 多卡互联加速**
- **MIG 与“高性能多卡训练”在设计目标上是冲突的**

------

## 二、为什么 MIG 会影响 A800 / A100 的互联（底层原因）

### 1. NVLink / NVSwitch 的前提条件

NVLink 不是“进程级”的，而是：

> **以“完整 GPU 设备”为最小互联单元**

互联依赖：

- 完整 GPC / SM 拓扑
- 统一显存地址空间
- GPU 级别的 BAR / DMA

------

### 2. MIG 打破了这些前提

开启 MIG 后：

- GPU 被拆成多个 **独立的逻辑 GPU**
- 每个 MIG 实例：
  - 有独立显存
  - 有独立 SM
  - 有独立地址空间
- **NVLink 端口不再映射到 MIG 实例**

结果是：

> **驱动层直接关闭了 MIG GPU 的 NVLink 能力**

不是“慢”，而是**不可用**。
