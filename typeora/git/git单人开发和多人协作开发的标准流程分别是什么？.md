### 问：git单人开发和多人协作开发的标准流程分别是什么？

Git 的使用流程在「单人开发」和「多人协作」时有本质的区别。单人开发追求的是**效率与备份**，而多人协作追求的是**代码质量、减少冲突与可追溯性**。

以下是这两种场景的标准流程：

------

### 一、 单人开发流程 (Solo Workflow)

单人开发时，你是仓库的唯一主宰。流程的核心在于：**频繁提交以保存进度，定期推送以防止本地丢失。** 通常只需要维护一个主分支（`main` 或 `master`），偶尔为大型实验性功能创建分支。

#### 核心流程步骤：

1. **拉取/同步 (Pull/Clone)：**
   - 如果是新的一天或换了电脑，先确保本地代码是最新的。
   - `git pull origin main`
2. **开发与修改 (Coding)：**
   - 直接在本地进行代码编写、修改 bug。
3. **暂存更改 (Add)：**
   - 将修改的文件放入暂存区。
   - `git add .` (或者指定文件名)
4. **提交版本 (Commit)：**
   - **这是最重要的一步。** 即使是单人开发，也建议写清楚 commit message，方便未来回溯。
   - `git commit -m "完成登录页面的UI布局"`
   - *技巧：单人开发可以提交得非常频繁，哪怕功能没写完也可以提交，只要不推送到远程影响部署即可。*
5. **推送到远程 (Push)：**
   - 当你完成了一个阶段的工作，或者准备下班时，推送到远程仓库（GitHub/GitLab/Gitee）作为备份。
   - `git push origin main`

#### 单人开发最佳实践：

- **不要怕犯错：** 如果代码写乱了，可以直接用 `git reset` 或 `git checkout` 回退，反正没有队友会受到影响。
- **实验性分支：** 如果要做一个可能会破坏现有代码的大功能，建议 `git checkout -b feature-xxx` 开个分支，测试通过后再合并回主分支。

------

### 二、 多人协作开发流程 (Team Collaboration Workflow)

多人协作的核心在于**分支管理 (Branching Model)** 和 **代码审查 (Code Review)**。目前最主流的协作模式是 **Feature Branch Workflow** (功能分支工作流)。

> **原则：** 永远不要直接在 `main` (或 `master`) 分支上直接 Commit 代码。

#### 核心流程步骤：

1. **同步主分支 (Sync)：**
   - 在开始任何工作前，先切回主分支并拉取最新代码，防止基于过时的代码开发。
   - `git checkout main`
   - `git pull origin main`
2. **创建功能分支 (New Branch)：**
   - 基于最新的主分支创建一个新分支。命名要有意义（如 `feat/user-login`, `fix/bug-102`）。
   - `git checkout -b feat/new-function`
3. **开发与提交 (Dev & Commit)：**
   - 在你的分支上进行开发。
   - `git add .`
   - `git commit -m "实现主要逻辑"`
4. **推送到远程 (Push Branch)：**
   - 将你的**分支**推送到远程仓库（而不是推送到 main）。
   - `git push origin feat/new-function`
5. **发起合并请求 (Pull Request / Merge Request)：**
   - **协作的关键点：** 在 GitHub/GitLab 页面上，发起一个 PR (Pull Request) 或 MR，请求将你的 `feat/new-function` 合并进 `main`。
   - 在描述中写清楚你改了什么、怎么测试。
6. **代码审查 (Code Review)：**
   - 队友查看你的代码，提出修改意见。
   - 你根据意见在本地修改 -> 再次 Commit -> 再次 Push（PR 会自动更新）。

   - 如果此时有队友先合并了代码，导致你的分支和主分支冲突，你需要：
     - 拉取最新的主分支到本地。
     - 将主分支合并进你的功能分支 (`git merge main`)。

2. **合并与部署 (Merge & Deploy)：**
   - Review 通过且无冲突后，由管理员或负责人点击 "Merge"。
   - 你的代码正式进入主分支。
3. **清理 (Cleanup)：**
   - 删除远程和本地的旧分支。
   - `git branch -d feat/new-function`

### 三、 两种模式的对比总结

| **特性**     | **单人开发**                                      | **多人协作**                                      |
| ------------ | ------------------------------------------------- | ------------------------------------------------- |
| **分支策略** | 通常单分支 (`main`) 到底                          | 严格的分支管理 (Feature/Fix/Hotfix)               |
| **提交频率** | 随意，甚至可以为了备份写 "wip" (work in progress) | 严谨，每个 Commit 最好是原子性的、可运行的        |
| **代码合并** | 几乎不需要，或者直接 Merge                        | 必须通过 Pull Request (PR/MR) 进行                |
| **冲突处理** | 极少遇到                                          | 家常便饭，需要沟通解决                            |
| **安全性**   | 依赖自觉，容易误操作覆盖                          | 依赖权限控制 (Protected Branch)，主分支通常被保护 |

### 问：给我团队协作中常见的 Git 冲突解决指南

在团队协作中，Git 冲突（Conflict）是**无法完全避免的正常现象**。它并不代表你做错了什么，只说明**你和队友同时修改了同一个文件的同一行代码**，Git 无法自动判断该保留哪一个，所以把决定权交给了你。

以下是标准的 **Git 冲突解决指南**，分为「发生时怎么办」、「如何动手修」和「遇到紧急情况如何撤退」三个部分。

------

### 一、 什么时候会发生冲突？

通常发生在以下两个动作中：

1. `git pull`：当你拉取远程代码时，发现远程的修改和你本地未提交（或已提交但未推送）的修改撞车了。
2. `git merge`：当你试图把主分支 (`main`) 合并回你的功能分支，或者把功能分支合并进主分支时。

Git 会提示你：

> ```
> CONFLICT (content): Merge conflict in [文件名]. Automatic merge failed; fix conflicts and then commit the result.
> ```

------

### 二、 手把手解决流程 (Standard Resolution)

#### 第一步：定位冲突文件

在终端输入：

Bash

```
git status
```

输出中显示 `both modified:` 的红色文件，就是你需要处理的冲突文件。

#### 第二步：读懂“冲突标记”

打开冲突的文件。Git 并不是把文件搞乱了，而是插入了特殊的标记来区分代码。你会看到类似这样的结构：

Plaintext

```
<<<<<<< HEAD
console.log("这是我本地修改的代码");
=======
console.log("这是队友提交的代码，或者远程最新的代码");
>>>>>>> origin/main
```

**标记说明表：**

| **标记符号**          | **含义**                                                     |
| --------------------- | ------------------------------------------------------------ |
| `<<<<<<< HEAD`        | **冲突开始**。下面的内容是你当前所在分支（本地）的修改。     |
| `=======`             | **分隔线**。上半部分是你的，下半部分是传入进来的（别人的）。 |
| `>>>>>>> branch_name` | **冲突结束**。同时也指明了下半部分代码来自哪个分支。         |

#### 第三步：编辑与保留

你需要人工介入，做以下三件事之一：

1. **保留你的**：删除 `=======` 下面的代码。
2. **保留队友的**：删除 `=======` 上面的代码。
3. **都要（合并逻辑）**：将两段代码融合，或者按逻辑顺序重写。

**最后，务必删除 `<<<<<<<`、`=======`、`>>>>>>>` 这三行标记符号。**

#### 第四步：标记为“已解决”

文件修改保存后，告诉 Git 冲突已搞定：

Bash

```
git add [文件名]
# 或者一次性添加所有解决好的文件
git add .
```

#### 第五步：完成合并

提交这次合并：

Bash

```
git commit -m "fix: resolve conflict in login.js"
# 如果是在 git pull 或 git merge 过程中，直接 git commit 即可，Git 会自动生成合并信息。
```

### 三、 现代化工具辅助 (推荐)

虽然手动改文件是基本功，但在实际工作中，我们通常使用 IDE 的图形化工具，效率更高且不易出错。

- VS Code (最常用):

  当打开冲突文件时，VS Code 会自动高亮冲突区域，并在上方提供四个按钮：

  - `Accept Current Change` (保留我的)
  - `Accept Incoming Change` (保留传入的)
  - `Accept Both Changes` (保留两者)
  - `Compare Changes` (对比差异)
  - **操作：** 点击其中一个按钮，VS Code 会自动帮你删除多余代码和标记符号。

- IntelliJ IDEA / WebStorm:

  在冲突文件上右键 -> Git -> Resolve Conflicts。它会弹出一个三栏窗口（左边是你，右边是由于，中间是结果），非常直观。

### 四、 紧急救险：如果修坏了怎么办？

如果你在解决冲突的过程中把代码改乱了，或者不知道自己在操作什么，**千万不要提交**。你可以使用“后悔药”命令，让一切回到冲突发生之前的状态。

**如果是 `git merge` 导致的冲突：**

Bash

```
git merge --abort
```

**如果是 `git rebase` 导致的冲突：**

Bash

```
git rebase --abort
```

执行后，你的工作区会恢复到合并动作开始前的样子，你可以深呼吸，重新开始。

------

### 五、 最佳实践：如何减少冲突？

解决冲突很累，最好的办法是减少它发生的概率：

1. **勤拉代码 (Pull Often)：** 每天早上开工前、或者准备提交代码前，先 `git pull origin main`。越早发现冲突，解决成本越低。
2. **分支粒度要小：** 一个功能分支不要做太久（比如超过一周）。长期不合并的分支是“冲突制造机”。
3. **不要随意格式化：** 不要使用全局的代码格式化工具去重新排列你不负责的文件。这会导致由于空格或换行产生的“假冲突”，非常扰人。
4. **先沟通：** 如果你发现冲突的代码逻辑非常复杂，不要盲目删除队友的代码。**使用 `git blame [文件名]` 查看那行代码是谁写的，直接去找他沟通。**
