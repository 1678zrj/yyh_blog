# Git 能高效管理和区分不同快照（提交）的核心机制

Git 能高效管理和区分不同快照（提交）的核心机制是基于 **哈希值（SHA-1）** 和 **增量存储**。下面我会详细解释 Git 是如何做到的：

------

## **1. 每个快照的唯一标识：哈希值**

- Git 中的每次提交（commit）会生成一个 **SHA-1 哈希值**，用来唯一标识这个提交。
- 这个哈希值是基于以下内容计算的：
  - 提交的作者信息（名字、邮箱、时间戳）。
  - 提交信息（commit message）。
  - 暂存区中记录的所有文件的状态。
  - **上一个提交的哈希值（父提交）**。

### **结果：**

- 只要提交中的任何内容发生变化（文件内容、提交信息、时间等），生成的哈希值就会完全不同，这确保了快照的唯一性。
- 因此，Git 可以轻松区分不同的快照。

------

## **2. 快照的存储方式：增量存储**

Git 并不是将每个快照保存为整个项目文件的完整副本，而是使用以下机制来优化存储和速度：

### **2.1 Blob（文件对象）**

- 每个文件的内容以一个 **Blob 对象** 存储，Blob 是文件内容的压缩版本。
- 每个 Blob 用 SHA-1 哈希值标识，因此相同的文件内容会有相同的哈希值。
- **结果：文件未修改时，不会重新存储，只会复用已有的 Blob。**

### **2.2 Tree（目录对象）**

- Tree 用来表示目录结构。
- 它包含了指向文件 Blob 的引用，以及文件的权限和名称。
- 如果一个目录或文件发生变化，Git 只会更新这个目录相关的 Tree，而不影响其他目录。

### **2.3 Commit（提交对象）**

- Commit 是一个引用，它指向顶层 Tree 和父提交（上一次提交）。
- Commit 记录了项目的快照信息，包括：
  - 顶层目录（Tree）。
  - 提交信息。
  - 父提交的哈希值。

------

## **3. 具体例子：文件变化时 Git 如何存储**

假设有一个项目，初始提交包含两个文件 `file1.txt` 和 `file2.txt`：

### **第一步：初始提交**

```bash
echo "Hello" > file1.txt
echo "World" > file2.txt
git add .
git commit -m "Initial commit"
```

- Git 创建了两个 Blob 对象：
  - Blob1：存储 `Hello`（file1.txt 内容）。
  - Blob2：存储 `World`（file2.txt 内容）。
- Tree1：目录结构，指向 Blob1 和 Blob2。
- Commit1：指向 Tree1。

```
Commit1 -> Tree1 -> Blob1 (Hello)
                  -> Blob2 (World)
```

### **第二步：修改 `file1.txt`**

```bash
echo "Hello Git" > file1.txt
git add .
git commit -m "Update file1.txt"
```

- Git 创建了新的 Blob3：
  - Blob3：存储 `Hello Git`（file1.txt 新内容）。
- Tree2：指向新的 Blob3，同时仍然指向未修改的 Blob2。
- Commit2：指向 Tree2，并记录父提交 Commit1。

```
Commit2 -> Tree2 -> Blob3 (Hello Git)  # 新文件内容
                  -> Blob2 (World)     # 未修改
Commit1 -> Tree1 -> Blob1 (Hello)
                  -> Blob2 (World)
```

**结果：**

- 只有 `file1.txt` 的新内容被存储，Git 复用了未修改的 `file2.txt` 的 Blob。

------

## **4. 快照之间的比较：文件级别差异**

Git 使用以下机制来区分和比较快照：

1. **通过 Commit 对象找到对应的 Tree。**
2. **通过 Tree 对象找到具体文件的 Blob。**
3. **比较不同 Blob 的内容，识别哪些文件发生了变化。**

例如：

```bash
git diff HEAD~1 HEAD
```

- 这条命令会比较当前提交（HEAD）和上一提交（HEAD~1）之间的差异。
- Git 根据 Tree 找到不同的 Blob，并计算文件内容的差异。

------

## **5. 为什么 Git 的存储方式高效？**

1. **内容唯一性（基于哈希）**
   - 相同内容的文件只存储一次（Blob 复用），即使文件在不同提交或分支中重复存在。
2. **增量存储**
   - Git 只记录变化的部分，未修改的文件直接复用之前的 Blob 和 Tree。
3. **高效的差异比较**
   - 通过 Blob 和 Tree 的指针关系，Git 可以快速定位哪些文件发生了变化，避免逐个文件比较。
4. **压缩存储**
   - 在底层，Git 使用 `packfile`（压缩存储格式）进一步优化空间。

------

## **总结**

- Git 区分快照的核心机制是 **SHA-1 哈希值**，确保每次提交都有唯一标识。
- 文件存储是基于增量和对象模型（Blob、Tree、Commit），只记录变化，未修改的部分直接复用。
- 这种机制使 Git 高效地管理大量版本，同时提供快速的差异比较和历史回溯功能。



# 注：

修改后的 **`file1.txt` 的所有内容** 都会被 `Blob3` 存储，而不是仅存储新修改的部分。

------

### **原因：Blob 是文件的完整内容存储**

1. Blob（Binary Large Object）

    是 Git 用于存储文件内容的核心对象。

   - 每个 Blob 存储的是文件的 **完整内容**，而不是增量变化。
   - Blob 的内容是基于文件的内容计算的 **SHA-1 哈希值**。
   - 如果文件发生了任何变化，即使只是修改了一个字符，Git 都会创建一个新的 Blob 对象来存储修改后的完整内容。

------

### **例子说明**

假设 `file1.txt` 原内容为：

```
Hello
```

修改后内容为：

```
Hello Git
```

#### **提交前的状态：**

- 初始提交创建的 Blob1：
  - Blob1 内容为：`Hello`
  - 哈希值计算基于完整的 `Hello`。

#### **提交后的状态：**

- 修改后的 

  ```
  file1.txt
  ```

   会创建一个新的 Blob3：

  - Blob3 内容为：`Hello Git`（整个文件的完整内容）。
  - 哈希值重新计算，基于完整的 `Hello Git`。

即使只新增了 `" Git"`，Blob3 仍会存储完整的修改后的文件内容。

------

### **为什么不是增量存储？**

虽然 Git 的存储机制在逻辑上是基于 **快照（Snapshot）**，但 Git 实际上通过以下方式实现高效性：

1. **Blob 是文件的完整内容**
   - Blob 保持文件内容的完整性，任何修改都会生成一个新的 Blob。
   - 这样可以确保每个 Blob 独立于其他 Blob，便于追踪文件历史和恢复。
2. **增量存储由 `packfile` 实现**
   - Git 在底层会通过压缩和 `packfile`（打包文件）实现增量存储优化。
   - 当多个 Blob 被存储到磁盘时，Git 会将相似的 Blob 通过压缩算法合并，从而实现类似增量存储的效果。
   - 这使得即使文件很大，只修改了部分内容，也不会导致大量存储空间浪费。

------

### **总结**

- **Blob 对象总是存储文件的完整内容**，而不是修改的部分。
- 修改后的文件内容会生成新的 Blob，即使改动很小，Git 也会重新保存完整的文件内容。
- 底层的增量存储优化（如 `packfile`）是 Git 在磁盘级别实现的，与 Blob 的逻辑存储无关。

因此，`Blob3` 存储的是 `file1.txt` 修改后的完整内容，而不是仅仅存储新增的 `" Git"`。
