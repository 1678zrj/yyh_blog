### 问：数据库和状态机在分布式系统只能够约束系统自身，而无法约束第三方服务，因此需要分布式锁。这个应该怎么理解呢，我没有接触过实际业务，因此很难理解

数据库事务和状态机只能控制**你自己系统内部的数据一致性**，但无法撤销或阻止**外部物理世界/第三方系统已经产生的副作用（Side Effects）**。



调用外部接口（如微信支付扣款、银行转账、物流发货、短信发送）是跨越网络边界的，**你的数据库 `ROLLBACK` 无法让微信把扣掉的钱退回来，也无法让已经发出的短信撤回。**



### 典型反例：为什么仅靠状态机和数据库会出事故？

假设用户发起了一笔 **100 元的退款**，由于网络抖动或前端重复点击，系统同时收到了两条相同的退款请求，分别由 **节点 A** 和 **节点 B** 处理。



1. **节点 A** 查询数据库：订单状态为 `PAID`，符合退款条件。
2. **节点 B** 并发查询数据库：订单状态依然是 `PAID`。
3. **节点 A** 调用微信支付退款 API：成功退款 100 元。
4. **节点 B** 也调用微信支付退款 API：成功退款 100 元（**灾难发生：外部第三方多退了 100 元**）。
5. **节点 A** 更新数据库状态：`UPDATE order SET status='REFUNDED' WHERE status='PAID'`（更新成功）。
6. **节点 B** 更新数据库状态：因状态已被 A 改为 `REFUNDED`，更新受阻或回滚。

> **问题核心：** 数据库的状态机确实保证了系统自身的数据最终是一致的（数据库里只有一条退款成功的记录），但**第三方微信支付已经实打实扣了两次款**。数据库的锁和事务只管得住自己的表，管不住发向外网的 HTTP 请求。

### 分布式锁是如何解决这个问题的？

分布式锁的作用是将**并发的“外部调用 + 内部状态变更”整体串行化**，把防御关口前移到调用第三方之前：



Plaintext

```
[进入处理]
   ↓
[获取分布式锁 (Key: lock:refund:order_123)]
   ↓ (只有获得锁的节点能继续，未获得者排队或直接丢弃)
[查数据库状态是否允许操作] ──(已完成/不符合)──> [释放锁并返回]
   ↓ (符合)
[调用第三方外部 API] (确保此时全集群只有一个线程在调用)
   ↓
[更新本地数据库状态]
   ↓
[释放分布式锁]
```

### 生产环境中的双重防线

在实际工业级业务中，解决第三方交互问题通常需要两层防护配合使用：



- **分布式锁（自身防线）：** 在发起外部调用前阻断本系统内的并发重复请求，避免多节点同时触发昂贵的网络调用。
- **业务幂等号 / Idempotency Key（外部防线）：** 每次请求外部时携带全局唯一流水号（如 `out_request_no = order_123_refund_1`）。即便分布式锁因超时意外失效导致多次调用，第三方服务也会根据该流水号识别为同一笔请求并直接拦截，避免重复扣款。

### 问：数据库不也可以通过乐观锁或唯一索引在并发请求时进行竞争吗

你的直觉非常敏锐，在技术实现上**完全可以用数据库来做并发竞争**。



如果通过唯一索引或乐观锁在**调用第三方之前**先完成一次数据库的状态抢占，确实可以防止多节点重复调用外部服务：



Plaintext

```
[并发请求 A, B]
   ↓
[抢先执行 DB 乐观锁 / 插入防重表] 
   ├─ 节点 A 抢占成功 (status -> 'REFUNDING') ──> [调用第三方 API] ──> [DB 改为 'REFUNDED']
   └─ 节点 B 抢占失败 (影响行数 0 / 唯一键冲突) ──> [直接报错返回，不发起调用]
```

既然数据库能做到，为什么业界还要广泛引入 **Redis 等分布式锁**？主要原因在于以下几点工程痛点：



### 1. 节点宕机后的“死锁”与悬挂状态处理

- **数据库方案：** 如果节点 A 成功将状态改为 `REFUNDING`，但在发起 HTTP 请求的一瞬间机器宕机或断电，该记录将永久停留在 `REFUNDING`。要解决这个问题，必须额外编写定时任务扫描“长时间处于中间状态”的订单并进行补偿重试或回滚。
- **分布式锁方案：** 分布式锁原生支持 **TTL（Lease / 租约过期机制）**。如果业务节点崩溃，锁在超时后会自动释放，天然具备容灾恢复能力。

### 2. 避免数据库连接池耗尽（长事务陷阱）

外部第三方 API 的响应时间是不可控的（网络抖动时可能耗时 3~10 秒甚至超时）。



- **悲观锁（`SELECT ... FOR UPDATE`）：** 在整个调用第三方期间必须保持数据库事务开启。如果有大量并发请求排队，数据库连接池会在几秒内被占满，导致整个系统的所有业务瘫痪。
- **分布式锁：** 加锁和释放锁都在内存缓存（如 Redis）中完成，完全不占用宝贵的数据库连接。

### 3. 性能与数据库负载隔离

- 数据库是分布式系统中最昂贵、最难水平扩展的资源。频繁利用数据库做高频、瞬时的锁竞争（如秒杀、高并发重试）会消耗大量磁盘 IOPS 和 CPU。
- Redis 等内存组件单机即可轻松支撑数万至十万 QPS 的锁操作，能将并发压力拦截在最外层，保护核心数据库。

### 方案对比与选型

| **维度**         | **数据库方案（唯一索引 / 乐观锁）**  | **分布式锁（Redis / Redisson 等）**    |
| ---------------- | ------------------------------------ | -------------------------------------- |
| **外部调用保护** | 先改状态为中间态（如 `DOING`）再调用 | 调用前直接加锁，调用后释放             |
| **宕机恢复**     | 需依赖额外定时任务清理超时的中间状态 | 依赖锁 TTL 自动释放，轻量自然          |
| **性能与吞吐**   | 受限于 DB 磁盘 IO 与连接池，吞吐较低 | 纯内存操作，支持极高并发               |
| **系统复杂度**   | 无需额外中间件，架构简单             | 需要维护 Redis 高可用集群              |
| **适用场景**     | 中低并发、操作频率低的管理后台业务   | 高并发、高频交互、对延迟敏感的核心业务 |

在实际业务中，**小体量系统直接用数据库乐观锁 + 状态机**足够应付；当业务并发量上升、依赖复杂的外部调用链条时，引入**分布式锁**做前置流量削峰与串行化则是标准解法。

### 问：或者说DB 乐观锁 / 插入防重表也属于分布式锁的一种

你的理解完全正确。从广义的**分布式并发控制**角度来看：



- **基于唯一索引的防重表：** 本质上就是一种**基于数据库实现的分布式互斥锁**。
- **数据库乐观锁（CAS 版本号/状态机）：** 属于**无锁并发控制协议（Lock-Free Concurrency Control）**，虽然没有显式的“锁对象”，但它达成了与分布式锁相同的排他控制目标。

### 两种 DB 方案与分布式锁的对应关系

**1. 插入防重表（唯一索引）= 显式互斥锁**



- **加锁：** `INSERT INTO lock_table (resource_key) VALUES ('refund_order_123');` 成功即获取锁。
- **互斥：** 利用数据库的唯一索引约束（Unique Key），任何其他节点同时 `INSERT` 都会因主键/唯一键冲突而报错，从而阻断并发。
- **释放锁：** 业务处理完毕后 `DELETE FROM lock_table WHERE resource_key = '...';`。

**2. 乐观锁（版本号 / 状态条件更新）= 隐式 CAS 锁**



- **原理：** `UPDATE orders SET status = 'PROCESSING', version = version + 1 WHERE id = 123 AND version = 1;`
- **互斥：** 利用单行记录的行锁与原子性判断（Compare-And-Swap）。并发时只有一个节点会返回 `affected_rows = 1`，其他节点均为 `0`，从而实现竞争排他。

### 为什么技术选型时通常将“DB 方案”与“分布式锁”分开讨论？

在实际工程术语中，大家常说的“分布式锁”通常狭义地指代 **Redis 或 ZooKeeper/Etcd 等专用协调组件**，主要区别在于设计定位：



| **维度**            | **DB 方案（防重表 / 乐观锁）**            | **专用分布式锁（Redis / Redisson / ZK）** |
| ------------------- | ----------------------------------------- | ----------------------------------------- |
| **本质定位**        | 借用业务数据存储做并发防御                | 专用的分布式协调与同步原语                |
| **加锁粒度**        | 绑定在具体的数据行或防重记录上            | 任意字符串 Key 均可作为临界区锁           |
| **租约机制（TTL）** | 较弱，宕机后易残留死锁，需写定时器清理    | 原生支持 TTL 过期与 Watchdog 自动续期     |
| **阻塞与排队**      | 很难实现阻塞等待（只能轮询查表，耗费 IO） | 支持 Pub/Sub 或监听机制实现优雅排队唤醒   |

**防重表和乐观锁就是数据库维度的分布式锁实现方案**。在并发不高、没有引入额外中间件诉求时，使用它们完全能满足业务需求。

### 问：是不是因为Redis方案比较快，在可靠性要求不高的场景就用Redis，在可靠性要求高的场景就用ZK，基本不用数据库方案？

这个说法**不完全准确**。实际工业界的真实情况是：



1. **Redis 分布式锁是绝大多数业务系统的默认选择（覆盖 90% 以上场景）**，并不是因为“可靠性不高凑合用”，而是它在性能、可用性和开发运维成本之间取得了极佳的平衡。
2. **ZooKeeper / Etcd 确实更可靠（CP 模型）**，但通常用于**基础架构级协调**（如 Leader 选举、注册中心、配置同步），很少纯粹为了普通业务去引入。
3. **数据库方案不仅没有被淘汰，反而是核心业务（如电商、金融、支付）的“最后一道防线”**。

### 三种方案的真实工业定位与取舍

**1. Redis：高并发业务的主流首选**



- **优势：** 纯内存读写，单机轻松支撑数万至十万 QPS，延迟在毫秒级以内；生态完善（如 Redisson 封装了看门狗自动续期、可重入锁等）。
- **可靠性隐患：** 主从异步复制可能导致锁丢失。当 Master 加锁成功后尚未同步给 Slave 就发生宕机，Slave 升为 Master 时，其他节点可能会重复获取同一把锁（出现短暂的双主加锁）。
- **适用场景：** 防重复点击、秒杀防超卖、缓存击穿防御、异步任务去重等绝大多数互联网业务。

**2. ZooKeeper / Etcd：强一致性与基础设施组件**



- **优势：** 基于 Zab / Raft 共识协议（严格的 CP 模型）。通过临时节点 + 心跳会话（Session）实现，无需担心主从切换丢锁，节点宕机后心跳断开锁立即释放。
- **劣势：** 每次加锁/释放锁都要写入磁盘日志并通过半数节点确认（Quorum），吞吐量远低于 Redis；如果系统本身没有 ZK/Etcd 依赖，额外引入的运维复杂度极高。
- **适用场景：** 分布式调度系统（如 XXL-Job / ElasticJob 抢主节点）、Hadoop/HBase 高可用切换、分布式中间件底层元数据锁。

**3. 数据库方案：并非“不用”，而是“用法变了”**



- **不推荐的做法（单纯的 DB 锁表）：** 专门建一张 `t_lock` 表用 `SELECT ... FOR UPDATE` 或频繁 `INSERT/DELETE` 做通用锁。这会迅速耗尽数据库连接池，造成性能断崖。
- **极力推荐并广泛使用的做法（业务防重与状态机 CAS）：** 在金融、支付、结算等绝对不能出错的核心链路中，**业务表上的唯一索引（幂等流水号）和乐观锁（状态机条件更新）是必不可少的最终兜底机制**。

### 方案多维对比

| **维度**           | **Redis 分布式锁**             | **ZooKeeper / Etcd**       | **数据库（乐观锁 / 唯一索引）** |
| ------------------ | ------------------------------ | -------------------------- | ------------------------------- |
| **一致性模型**     | AP（主从切换可能丢锁）         | CP（强一致，保证绝对互斥） | 强事务一致性（单库 ACID）       |
| **吞吐能力 (QPS)** | 极高（10万+）                  | 中等（数千至上万）         | 较低（受限于磁盘 IO 与连接池）  |
| **锁释放机制**     | TTL 超时 / 看门狗续期          | 心跳断开，临时节点自动删除 | 事务提交 / 状态变更完成         |
| **运维与依赖成本** | 极低（现代系统基本标配 Redis） | 较高（需维护独立的集群）   | 零（复用已有业务数据库）        |
| **典型定位**       | 业务高并发前置防线             | 基础架构选举与元数据协调   | 核心数据最终一致性底座          |

### 业界的标准落地架构：组合防御

在实际中大型系统中，最常见的架构不是“三选一”，而是 **“Redis + 数据库” 组合拳**：



Plaintext

```
[用户并发请求]
      ↓
[第一道防线: Redis 分布式锁] ──(未抢到)──> 拦截 99% 重复流量，降低后端压力
      ↓ (抢到锁)
[调用第三方外部 API (携带业务幂等号)]
      ↓
[第二道防线: DB 唯一索引 / 乐观锁] ──(极端情况下 Redis 丢锁时兜底)──> 保证数据绝对正确
```

- **Redis** 负责在最外层扛住高并发、阻断大部分并发请求，避免大量重复请求打到数据库和第三方服务。
- **数据库唯一索引 / 乐观锁** 驻守在数据落地端，作为最后兜底，防止极端情况下因 Redis 节点故障而破坏数据一致性。

### 问：是不是幂等也像异步一样具有传播效应，要保证幂等的话，即使是第三方接口也得保证幂等

分布式系统中 ID 生成之所以让人头疼，是因为它在不同场景下的诉求是**互相冲突**的：既要全局唯一、高性能、不依赖单点，又要兼顾数据库 B+ 树索引性能（有序性）、对外防猜测（安全性）、前端兼容性（JS 精度）以及可读性。



破除这种烦躁的关键，是**不要试图用一种 ID 解决所有问题**，而是将业务中的 ID 分类治理。



### 分布式系统中的 4 类核心 ID

| **ID 类别**             | **典型例子**                               | **核心诉求**                                                 | **推荐生成方案**                                            | **避坑要点**                                                 |
| ----------------------- | ------------------------------------------ | ------------------------------------------------------------ | ----------------------------------------------------------- | ------------------------------------------------------------ |
| **1. 链路与临时标识**   | `TraceID`, `SpanID`, 分布式锁 `LockToken`  | 全局唯一、生成速度极快、无状态、无序也无妨                   | **UUID v4 / NanoID**                                        | 随用随抛，不作为数据库聚簇索引主键。                         |
| **2. 数据库内部主键**   | 用户表 `id`, 商品表 `id`                   | 单调递增（保护 B+ 树不频繁页分裂）、高效索引、存储紧凑（64-bit bigint） | **雪花算法 (Snowflake)** / **TSID** / **号段模式 (Leaf)**   | 必须注意时钟回拨；传给前端时必须转为 **String**（防止 JS 精度丢失）。 |
| **3. 业务与展示流水号** | 订单号 `order_no`, 支付单号 `out_trade_no` | 具备业务语义、防枚举（不可递增爬取）、按天归档、支持分库分表路由 | **业务前缀 + 日期 + 机器/分片位 + 随机/递增序列**           | 不能直接用数据库自增 ID 对外展示，否则竞品能直接推算每日订单量。 |
| **4. 客户端幂等 Key**   | `Idempotency-Key` (请求头)                 | 一次用户意图的唯一代号，服务端防重复提交                     | **前端页面加载时生成的 UUID**，或 **用户ID + 业务参数哈希** | 需设定合理的生存时间（TTL），配合 Redis 做前置拦截。         |

### ID 设计中最常踩的 3 个“工程大坑”

**1. 用原生 UUID 做 MySQL 主键导致性能崩塌**



- **原因：** UUID v4 是完全随机的无序字符串。InnoDB 的数据是按主键顺序存放在 B+ 树叶子节点的。每次插入完全随机的 UUID，会导致数据频繁在中间节点插入，引发大量的 **B+ 树页分裂（Page Split）** 和严重的磁盘随机 IO。
- **解法：** 如果非要使用类似 UUID 的方案，请选择时间有序的变种（如 **ULID**、**TSID** 或 **UUID v7**）。

**2. 前端 JavaScript 的“大数吃小数”精度丢失**



- **原因：** 64 位雪花算法（Snowflake）生成的 ID 最大可达 $2^{63}-1$，而前端 JavaScript 的 `Number` 遵循 IEEE 754 标准，最大安全整数仅为 $2^{53}-1$（9007199254740991）。
- **现象：** 后端返回 `1789234872349823488`，前端解析后变成 `1789234872349823500`，导致修改/查询永远找不到记录。
- **解法：** 序列化层统一将 Long 类型的 ID 转为 **String** 输出给前端。

**3. 雪花算法的“时钟回拨”与 Worker ID 分配**



- **原因：** 雪花算法高度依赖本地机器时间戳。如果服务器发生 NTP 时间校准向后倒退，或者在容器化（Docker/K8s）动态漂移部署时多个实例分配了相同的 `worker_id`，就会生成完全相同的重复 ID。
- **解法：** 容器环境下推荐使用**美团 Leaf**、**百度 UidGenerator** 或借助 Redis / ZK 自动注册分配与回收 `worker_id`。

### 实用减负法则

- **临时追踪/防重：** 无脑用 `UUID.randomUUID()`，不要做多余的复杂度。
- **底层数据库主键：** 优先采用现成的库（如 `Snowflake` / `TSID`），不用自己造轮子。
- **对外展示业务单号：** 统一采用固定模板拼接（例：`PO` + `20260901` + `分片区号(2位)` + `Redis自增补齐(6位)`）。
