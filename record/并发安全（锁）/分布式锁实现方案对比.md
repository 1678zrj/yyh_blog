### 问：两个分布式锁实现，你更推荐哪个？

**强烈推荐第二个实现（基于 `redis.lock` 封装的 `AsyncDistributedLock`）。**



第一个实现属于“简易自研玩具”，而第二个实现借助了 `redis-py` 官方维护的成熟组件，在生产可用性、并发等待支持、异常边界处理上均完胜。



### 核心维度对比

| **评估维度**       | **第一个实现（自研简版）**                                   | **第二个实现（官方组件封装）**                               |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **并发等待能力**   | ❌ **单次尝试（Fail-Fast）**：抢不到立即报错，无法应对短时排队场景 | **支持 `blocking_timeout`**：支持指定时间内的重试与轮询排队  |
| **底层稳健性**     | ⚠️ **基础实现**：每次调用 `eval` 执行完整脚本，无 `EVALSHA` 缓存优化 | **工业级保障**：官方库内置 `EVALSHA` 缓存、自旋回退与高精度时间控制 |
| **异常控制**       | ❌ 抛出宽泛的 `Exception`，容易在调用链路中掩盖其他系统级错误 | **自定义语义化异常**，并保留原始异常上下文（`from e`）       |
| **锁超时释放安全** | 使用 Lua 校验 UUID，能防止误删他人锁                         | 同样具备 Lua 校验，且安全捕获 `LockError`，防止掩盖业务本身的真实报错 |

### 为什么第一个实现在生产中容易踩坑

1. **缺乏排队重试机制**
   - 第一个实现仅执行了一次 `SET NX EX`。在微服务或高并发场景下，多个请求同时竞争同一个资源时，除了 1 个请求能成功外，其他请求会全部直接报错。
   - 第二个实现通过 `blocking_timeout` 提供了排队等待窗口，大幅降低了接口的瞬时报错率。
2. **异常穿透与掩盖风险**
   - 如果持有锁执行的业务代码耗时超过了 `expire_time`（锁已自动过期并被其他请求获取），第一个实现在退出 `__aexit__` 时虽然不会误删他人的锁，但无法平滑处理上下文切换。
   - 第二个实现通过 `try...except LockError: pass` 吞掉了由于锁超时释放导致的次生异常，确保代码块内部真实的业务异常（`exc_type`）能够正常向外抛出。

### 第二个实现的微调优化

第二个实现整体设计优良，仅在 `__aexit__` 处有一处细微冗余：



Python

```
async def __aexit__(self, exc_type, exc_val, exc_tb):
    try:
        # redis-py 的 release() 内部已通过 Lua 脚本原子性校验持有者 token
        # 此处提前调用 locked() 会额外增加一次无意义的 Redis 网络 I/O
        await self._lock.release()
    except LockError:
        # 锁已过期或被抢占时安全忽略，优先保留业务异常堆栈
        pass
```

**是的，完全正确。**



第二个实现本质上是对 `redis-py` 官方自带的 `redis.lock()` 进行了一层**面向业务场景的二次封装**。



### 官方自带的 `redis.lock()` 已经做了什么？

在 `redis-py` 库中，调用 `self.redis.lock(...)` 返回的是一个成熟的 `Lock` 实例。它在底层已经完整实现了：



- **唯一 Token 标识**（类似第一个实现中的 UUID，防止误释放他人锁）。
- **原子获取与排队轮询**（结合 `blocking_timeout` 和 `sleep` 进行自旋重试）。
- **Lua 脚本释放与 SHA 缓存**（通过 `EVALSHA` 优化网络传输与原子比对）。

### 这个二次封装额外带来了什么价值？

既然官方已经有锁，代码作者还要写 `AsyncDistributedLock` 这个包装类，主要是为了解决以下 3 个工程化问题：



1. **统一异常契约（Semantic Exception）**
   - 官方的 `lock.acquire()` 超时失败时只返回 `False`，或者直接抛出底层的 `LockError`。
   - 封装后将其统一转译为具有业务语义的 `DistributedLockTimeoutError`，方便上层业务代码精准捕获、告警或熔断。
2. **防止掩盖核心业务异常（Exception Masking）**
   - 如果 `async with` 内部的业务逻辑耗时过长导致锁已过期，退出时调用 `release()` 会触发底层的 `LockError`。
   - 封装类在 `__aexit__` 中通过 `try...except LockError: pass` 吞掉了锁释放失败的次生异常，**确保业务本身的真实报错能优先完整抛出**。
3. **收敛与统一全局默认参数**
   - 将业务常用的锁有效期（`timeout`）与最大等待排队时间（`blocking_timeout`）固化为统一的默认值，减少各处业务调用的配置心智负担。

### 问；帮我抽丝剥茧，看下第二个方案实际上是第一个方案的怎样的一个实现？

如果把 `redis-py` 官方锁（方案二的内核）的源码剥开，你会发现**它在底层逻辑上与方案一的骨架完全一致，但在每一个具体实现细节上，都做了工业级的工程补完**。



我们可以从四个核心维度逐层拆解方案二是怎样把方案一的“毛坯房”重构为“精装房”的：



### 1. 身份凭证（Token / Identifier）：从“静态绑定”到“生命周期隔离”

- **方案一的做法**：
  - 在 `__init__` 时生成 `self.identifier = str(uuid4())`。
  - **隐患**：如果同一个锁对象实例被复用多次调用 `acquire()`，它的标识永远不变。一旦出现并发复用，可能导致不同调用者之间的凭证混淆。
- **方案二的内部实现**：
  - `redis.lock` 在每次执行 `acquire()` 时动态生成/校验 Token（默认使用 `uuid4().hex` 或 `os.urandom(16)`）。
  - 锁在未持有状态时 Token 为空，只有成功获取锁后才将 Token 绑定到当前上下文，彻底隔离了对象生命周期与锁持有时效。

### 2. 加锁逻辑（Acquire）：从“单次硬碰硬”到“高精度自旋排队”

方案一只有**1 次尝试**，方案二内置了**带时间衰减的轮询机制**：



- **方案一**：

  Python

  ```
  # 仅执行一次 SET NX，失败直接返回 False / 抛出异常
  await self.redis.set(self.lock_key, self.identifier, nx=True, ex=self.expire_time)
  ```

- **方案二在底层的实现逻辑（伪代码等价）**：

  Python

  ```
  stop_time = time.monotonic() + blocking_timeout
  while True:
      # 1. 同样尝试 SET NX EX / PX
      if await self.redis.set(name, token, nx=True, px=timeout_ms):
          return True
      # 2. 如果不阻塞，直接退出
      if not blocking:
          return False
      # 3. 检查高精度单调时钟是否超时
      if time.monotonic() >= stop_time:
          return False
      # 4. 睡眠一小段自旋间隔（默认 0.1s），交出 CPU 控制权后再重试
      await asyncio.sleep(sleep_interval)
  ```

  > **核心提升**：方案二通过 `time.monotonic()`（单调时钟，不受系统修改时间影响）+ `asyncio.sleep`，在底层自动实现了非阻塞式的并发排队缓冲。

### 3. 解锁逻辑（Release）：从“传输整段脚本”到“EVALSHA 字节码缓存”

二者在**逻辑算法**上完全一致（都是“先比对 Token，相等才 DEL”），但**网络与执行效率**有质的差距：



- **方案一**：
  - 每次 `release()` 都将完整的 Lua 脚本字符串通过网络发送给 Redis。
  - Redis 每次收到后都需要进行语法解析和编译，浪费带宽与 Redis 单线程 CPU。
- **方案二在底层的实现逻辑**：
  - 内部使用 `redis.client.Script` 对象管理 Lua 脚本。
  - 首次执行时调用 `SCRIPT LOAD` 将脚本加载到 Redis 内存中并计算 SHA1 校验和。
  - 之后每次解锁，**只发送 40 位的 SHA1 摘要（`EVALSHA` 命令）**。只有在 Redis 重启导致缓存丢失时，才会透明降级重新加载。

### 4. 异常与边界：从“粗暴穿透”到“防异常吞噬”

在上下文管理器（`__aenter__` / `__aexit__`）的退出处理上：



- **方案一的缺陷**：
  - 如果代码块内执行了 15 秒（锁在 10 秒时已过期），Lua 脚本执行后返回 `0`，但代码静默退出。
  - 如果外部需要区分是“业务崩了”还是“锁被抢了”，方案一没有任何边界处理。
- **方案二外层封装的精髓**：
  - 底层 `_lock.release()` 如果发现锁已不存在或被他人持有，会主动抛出 `LockNotOwnedError`（继承自 `LockError`）。
  - 方案二在 `__aexit__` 中主动捕获并 `pass` 掉该异常：**确保代码块内部真实的业务报错（如数据库连接失败、计算错误）能顺畅向外冒泡，而不会被锁释放失败的次生报错所掩盖。**

| **核心组件**   | **方案一（自研原型）**         | **方案二（官方内核 + 业务封装）**                            |
| -------------- | ------------------------------ | ------------------------------------------------------------ |
| **Token 生成** | 实例级别的静态 `uuid4()`       | 获取锁维度的安全随机字节串                                   |

**1. 核心 Lua 脚本与注册机制**



官方库在类加载与初始化时预定义了 Lua 脚本，并通过 `register_script` 封装为可复用的 `Script` 对象：

```
class Lock:
    # 释放锁脚本：比对 token 是否一致，一致则 DEL，否则返回 0
    LUA_RELEASE_SCRIPT = """
        local token = redis.call('get', KEYS[1])
        if not token or token ~= ARGV[1] then
            return 0
        end
        redis.call('del', KEYS[1])
        return 1
    """

    # 续期脚本：比对 token 是否一致，一致则重新设置 PX 毫秒过期时间
    LUA_EXTEND_SCRIPT = """
        local token = redis.call('get', KEYS[1])
        if not token or token ~= ARGV[1] then
            return 0
        end
        local expiration = redis.call('pttl', KEYS[1])
        if expiration < 0 then
            return 0
        end
        redis.call('pexpire', KEYS[1], ARGV[2])
        return 1
    """

    def __init__(self, redis, name, timeout=None, sleep=0.1, blocking=True,
                 blocking_timeout=None, thread_local=True):
        self.redis = redis
        self.name = name
        self.timeout = timeout
        self.sleep = sleep
        self.blocking = blocking
        self.blocking_timeout = blocking_timeout
        # 注册脚本对象：内部会自动维护 EVALSHA 缓存
        self.lua_release = self.redis.register_script(self.LUA_RELEASE_SCRIPT)
        self.lua_extend = self.redis.register_script(self.LUA_EXTEND_SCRIPT)
```

> **机制亮点**：`register_script` 在首次调用时会执行 `SCRIPT LOAD` 将脚本缓存在 Redis 内存中，后续每次执行直接发送 40 位 SHA 校验和（`EVALSHA`），大幅节省网络带宽并减轻 Redis 的 CPU 解析负担。

**2. `acquire()` 实现细节剖析**



`acquire` 核心逻辑包含：Token 动态生成、高精度单调时钟计算、`SET NX PX` 原子设值以及自旋睡眠重试。



Python

```
async def acquire(self, blocking=None, blocking_timeout=None, token=None):
    sleep = self.sleep
    if token is None:
        # 生成 16 字节随机二进制串作为唯一 Token
        token = os.urandom(16) if hasattr(os, "urandom") else uuid.uuid4().hex.encode()
    
    if blocking is None:
        blocking = self.blocking
    if blocking_timeout is None:
        blocking_timeout = self.blocking_timeout

    # 使用高精度单调时钟计算截止时间，避免受系统时钟回拨影响
    stop_trying_at = None
    if blocking_timeout is not None:
        stop_trying_at = time.monotonic() + blocking_timeout

    # 将 timeout 换算为毫秒（用于 PX 参数）
    timeout_ms = int(self.timeout * 1000) if self.timeout else None

    while True:
        # 执行原子加锁命令
        if await self.redis.set(self.name, token, nx=True, px=timeout_ms):
            self.local.token = token  # 记录当前协程/线程持有的 Token
            return True

        if not blocking:
            return False

        # 超时判定
        if stop_trying_at is not None and time.monotonic() > stop_trying_at:
            return False

        # 协程让出控制权，等待下一轮自旋重试
        await asyncio.sleep(sleep)
```

**3. `release()` 实现细节剖析**



`release` 负责保证原子删除并对持有状态做严格的异常断言。



Python

```
async def release(self):
    # 1. 检查本地是否记录了有效的 token
    expected_token = getattr(self.local, "token", None)
    if expected_token is None:
        raise LockError("Cannot release an unlocked lock")

    # 2. 清理本地 token 记录，防止重入或脏状态
    self.local.token = None

    # 3. 调用预编译的 Lua 脚本（优先 EVALSHA，未命中时回退 EVAL）
    res = await self.lua_release(
        keys=[self.name],
        args=[expected_token],
        client=self.redis
    )

    # 4. 如果 Lua 脚本返回 0，说明锁已超时被 Redis 剔除或被他人占用
    if not res:
        raise LockNotOwnedError("Cannot release a lock that's no longer owned")
```

**设计精髓提炼**



- **`time.monotonic()` vs `time.time()`**：排队计时使用单调时钟，不受 NTP 授时同步或管理员手动修改系统时间影响。
- **`px` 毫秒级精度**：使用 `px=timeout_ms` 代替秒级 `ex`，提升短生命周期锁的控制精度。
- **分层的异常模型**：
  - 本地未加锁调用 `release()` $\rightarrow$ 抛出 `LockError`；
  - 锁已过期或被其他人持有 $\rightarrow$ 抛出更具体的子类 `LockNotOwnedError`，方便业务层精细化捕获。
