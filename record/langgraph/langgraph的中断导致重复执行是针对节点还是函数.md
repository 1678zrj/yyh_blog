### 问：langgraph的中断导致重复执行是针对函数还是节点？

LangGraph 的中断机制（无论是静态的 `interrupt_before` 还是动态的 `interrupt()`）导致重新执行时，**是以“节点（Node）”为调度单位，重新执行该节点绑定的整个函数**。



LangGraph 并没有像协程生成器那样冻结并恢复 Python 底层的调用栈帧，而是采用了重放（Re-execution）策略。



**底层执行流程**



以动态中断 `interrupt()` 为例：



1. **初次触发**：节点绑定的函数从第 1 行开始执行；当运行到 `interrupt()` 时，框架内部会抛出一个特殊的 `GraphInterrupt` 异常，中断流程并持久化当前的 Checkpoint。
2. **恢复执行（Resume）**：调用 `Command(resume=...)` 恢复时，LangGraph 重新调度该节点，**从头到尾重新调用该节点对应的函数**。
3. **注入返回值**：当执行流程再次走到同一位置的 `interrupt()` 时，框架拦截该调用，直接将外部传入的 resume 数据作为返回值返回，然后继续向下执行该节点的后续代码。

**函数与节点的具体区别**



- **对节点层面的影响**：调度器的最小回滚单元是节点。只要是在该节点内部，所有执行流程都会从头重来。
- **对普通辅助函数的影响**：如果节点函数内部调用了其他自定义函数（如 `process_data()`、`call_api()`），只要这些调用写在 `interrupt()` **之前**，它们在恢复时同样会被再执行一次。

**常见隐患与规避方式**



如果在 `interrupt()` 之前放置了非幂等操作（如消耗 Token 的 LLM 调用、数据库写入、外部 Webhook 通知），恢复时这些操作会发生**重复调用**。



- **节点拆分（推荐）**：将耗时或有副作用的操作拆分成前置独立节点，持久化到 State；中断逻辑放在后续节点中。
- **State 守卫检查**：在节点函数内部执行昂贵操作前，先判断 State 中是否已缓存结果，若存在则跳过计算。
