### 问：我在学习开发FastAPI程序，现在要实现的是根据课程id查询课程资源表中关于该课程的所有资源，但我不太了解crud层应该怎么写批量查询的代码，我当前的代码如上所示。

在使用 SQLModel 的 `AsyncSession` 时，`await db.exec(stat)` 执行查询后会返回一个结果迭代对象（`ScalarResult`）。要将查询结果作为列表返回，只需要对结果调用 **`.all()`** 即可。



下面是为你完善和优化后的 CRUD 示例代码：



### 优化后的 CRUD 代码

Python

```
from datetime import datetime
from sqlmodel import select
from sqlmodel.ext.asyncio.session import AsyncSession
from app.models.table import CourseResource

class CourseResourceCrud:

    async def create_course_resource(self, db: AsyncSession, course_resource_data: dict) -> CourseResource:
        course_resource = CourseResource(**course_resource_data)
        db.add(course_resource)
        await db.flush()
        return course_resource

    async def get_course_resources_by_course_id(
        self, 
        db: AsyncSession, 
        course_id: int,
        skip: int = 0,
        limit: int = 100
    ) -> list[CourseResource]:
        """根据课程 ID 查询该课程下的所有资源（支持分页与排序）"""
        stat = (
            select(CourseResource)
            .where(CourseResource.course_id == course_id)
            .order_by(CourseResource.created_at.desc())  # 建议按创建时间倒序
            .offset(skip)
            .limit(limit)
        )
        results = await db.exec(stat)
        return results.all()  # 提取所有结果并返回 list

    async def get_course_resource_by_file_id(
        self, 
        db: AsyncSession, 
        file_record_id: int
    ) -> CourseResource | None:
        """根据文件 ID 查询对应资源（因为一个资源只对应一个文件，建议返回单个实体或 None）"""
        stat = select(CourseResource).where(CourseResource.file_record_id == file_record_id)
        results = await db.exec(stat)
        return results.first()  # 返回单条记录，查不到则返回 None


course_resource_crud = CourseResourceCrud()
```

### 关键细节说明

1. **`results.all()` 与 `results.first()`**
   - **`results.all()`**：将查询到的多条记录转换为标准 Python 的 `list[CourseResource]`。
   - **`results.first()`**：获取符合条件的第一条记录（若没找到返回 `None`）。因为你的业务模型中“一个课程资源对应一个文件”，查询文件 ID 时通常只需要返回单一对象 `CourseResource | None`。
2. **生产环境扩展（分页与排序）**
   - 在批量查询接口中（如根据 `course_id` 查资源），建议加上 `skip`（偏移量）和 `limit`（限制数量）参数做分页防爆。
   - 添加 `.order_by(CourseResource.created_at.desc())` 可以让最新上传的资源展示在最前面。

### 💡 设计核心要素提示

1. **响应格式控制（Schema 过滤）**：即使 `CourseResource` ORM 类中包含不需要或敏感的数据库字段，在 `response_model=list[CourseResourceResponse]` 作用下，FastAPI 会自动过滤掉未在 Schema 中定义的属性。
2. **`ConfigDict(from_attributes=True)`**：Pydantic V2 的关键配置，能自动将 SQLAlchemy / SQLModel 对象（模型实例）解析为对应的 Pydantic Response JSON。
3. **分层职责清晰**：
   - **CRUD**：只与数据库打交道，做纯粹的 SQL 查询与增删改查。
   - **Service**：校验业务逻辑，组合 CRUD 调用的同时处理 `HTTPException`。
   - **Router**：接收输入参数（Query/Path/Body），依赖注入（Depends），返回标准化数据。

### 问：其实我最不理解的是service层和crud层的相关查询函数的参数需要有默认值吗？感觉路由层不就做好相关操作了吗

你的直觉**非常敏锐且完全正确**！



如果单纯从“处理一次 HTTP 请求”的执行路径来看，**路由层已经通过 `Query(0)` 给出了默认值**，当请求到达 Service 和 CRUD 层时，参数已经被解析成具体的值（如 `skip=0`, `limit=20`）传下去了。因此，**在 CRUD 和 Service 层的函数签名中不写默认值，程序也完全能够正常运行**。



那为什么大家在写 Python / FastAPI 后端时，依然习惯在 Service 和 CRUD 层把默认值再写一遍呢？这主要是出于以下 3 个软件工程的设计考虑：



## 1. 脱离 HTTP 框架的复用（最核心原因）

CRUD 和 Service 层的定位是**纯粹的 Python 业务/数据访问逻辑**，它们不应该强绑定在“必须由 FastAPI 路由来调用”的前提下。



在实际项目中，这些函数经常会被非 HTTP 场景直接调用：



- **后台定时任务**（如 APScheduler/Celery 脚本）：`await course_resource_service.get_resources_by_course(db, course_id=10)`
- **终端 CLI 交互脚本** 或 数据迁移脚本
- **系统内部事件驱动/消息队列消费者**

如果在 CRUD 层不写默认值，所有这些调用方都必须强制显式传入 `0` 和 `100`，不仅代码冗余，也增加了调用者的负担。



## 2. 单元测试（Unit Testing）更友好

当你对 CRUD 层或 Service 层编写单元测试时，你通常会绕过 FastAPI 路由，直接调用函数：



Python

```
# 有默认值时，测试写起来非常干净：
async def test_get_resources(db_session):
    resources = await course_resource_crud.get_course_resources_by_course_id(db_session, course_id=1)
    assert len(resources) > 0

# 如果没有默认值，你每次写测试都必须补充这些无关紧要的参数：
async def test_get_resources(db_session):
    resources = await course_resource_crud.get_course_resources_by_course_id(db_session, course_id=1, skip=0, limit=100)
    assert len(resources) > 0
```

## 3. 防御性编程（数据库最后的防线）

如果 CRUD 层的 `limit` 参数既没有默认值也没有限制，一旦未来有同事在编写新的业务逻辑时，调用了 CRUD 却忘记传入 `limit` 参数（或者传了 `None`），SQLModel 就可能会执行没有 `LIMIT` 的查询，直接触发 `SELECT *` **把数据库全表查爆**。



在 CRUD 层加上 `limit: int = 100`，相当于在离数据库最近的地方加了一道“安全兜底”。



## 总结：各层的职责划分

| **分层**       | **是否需要默认值**          | **它的核心职责**                                             |
| -------------- | --------------------------- | ------------------------------------------------------------ |
| **Router 层**  | **必须有**（如 `Query(0)`） | 处理 **HTTP 校验与 OpenAPI 文档**（控制前端传参，例如 `ge=0, le=100`）。 |
| **Service 层** | 建议有                      | 处理 **业务逻辑**（作为上层调用的快捷入口）。                |
| **CRUD 层**    | 建议有                      | 处理 **数据库安全**（提供 Python 函数级别的标准默认参数，防全表查询）。 |

> 💡 **实用建议**：在实际开发中，如果不确定怎么写，遵循 **“路由层管 HTTP 格式与文档，CRUD/Service 管 Python 调用的便捷与安全”** 即可。
