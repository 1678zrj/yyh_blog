```python
from fastapi import Depends, HTTPException
from app.file.session_manager import SessionManager, get_session_manager, UploadSession
from app.file.base_storage import BaseStorage
from app.file.storage_factory import get_storage
from app.tasks.merge_tasks import merge_file_chunks_task


class UploadService:
    def __init__(
        self,
        storage: BaseStorage = Depends(get_storage),
        session_manager: SessionManager = Depends(get_session_manager),
    ):
        self.storage = storage
        self.session_manager = session_manager

    # ... init_file_upload, upload_file_chunk 保持不变 ...

    async def trigger_merge(self, upload_id: str) -> str:
        """
        触发异步合并，返回 Taskiq 的 task_id
        """
        try:
            session = await self.session_manager.get_session(upload_id=upload_id)
        except ValueError:
            raise HTTPException(status_code=404, detail=f"Unknown upload session: {upload_id}")

        # 1. 业务校验：检查分片是否全部上传完毕
        if len(session.uploaded_chunks) != session.total_chunks:
            missing_chunks = set(range(session.total_chunks)) - session.uploaded_chunks
            raise HTTPException(
                status_code=400, 
                detail=f"Chunks incomplete. Missing: {list(missing_chunks)}"
            )

        # 2. 防重入校验：如果已经在合并中或已完成
        if session.status in ["merging", "completed"]:
            raise HTTPException(status_code=400, detail=f"File is already in {session.status} state.")

        # 3. 标记状态为合并中
        await self.session_manager.set_status(upload_id, "merging")

        # 4. 派发 Taskiq 任务
        task = await merge_file_chunks_task.kiq(upload_id=upload_id)
        return task.task_id
```

### 问：这段代码是不是无法防止重复合并文件的请求？

**是的，这段代码在并发场景下无法可靠防止重复合并。**



这里存在典型的 **Check-Then-Act（检查-执行之间存在时间差）竞态条件**。



### 问题复现过程

当客户端快速连击、网络抖动重试，或两个请求同时到达时：



Plaintext

```
Request A ──> 1. 读取状态 (status="uploading") ──> 2. 校验通过 ────────────────────────> 3. set_status("merging") ──> 4. 派发 Task A
Request B ──────> 1. 读取状态 (status="uploading") ──> 2. 校验通过 ──> 3. set_status("merging") ────────────────────────> 4. 派发 Task B
```

在 Request A 将状态修改为 `"merging"` 之前，Request B 已经完成了步骤 2 的检查，导致两个请求都会成功派发 Taskiq 异步任务，造成重复合并、文件损坏或存储冲突。



### 解决方案

#### 方案 1：原子状态变更（CAS / 推荐）

将“检查状态”与“修改状态”合并为一个原子操作（由底层 Redis 或数据库执行）。



- **基于 Redis 的原子修改（SessionManager 内部使用 Lua 脚本或事务）：**

Python

```
# SessionManager 中增加原子状态转换方法
# 返回 True 表示抢占状态成功，False 表示状态已被抢先修改
success = await self.session_manager.compare_and_set_status(
    upload_id=upload_id,
    expected_statuses=["uploaded", "pending"],  # 允许流转的前置状态
    target_status="merging"
)

if not success:
    raise HTTPException(status_code=400, detail="Merge is already in progress or completed.")
```

- **基于 SQL 数据库的条件更新：**

SQL

```
UPDATE upload_sessions 
SET status = 'merging' 
WHERE upload_id = :upload_id AND status NOT IN ('merging', 'completed');
-- 检查 affected_rows 是否为 1
```

#### 方案 2：加分布式锁（Redis Lock）

在进入校验前获取基于 `upload_id` 的分布式锁，防止并发执行：



Python

```
async def trigger_merge(self, upload_id: str) -> str:
    # 锁定当前 upload_id 的操作区间
    async with self.session_manager.redis.lock(f"lock:merge:{upload_id}", timeout=10):
        try:
            session = await self.session_manager.get_session(upload_id=upload_id)
        except ValueError:
            raise HTTPException(status_code=404, detail=f"Unknown upload session: {upload_id}")

        if len(session.uploaded_chunks) != session.total_chunks:
            raise HTTPException(status_code=400, detail="Chunks incomplete.")

        if session.status in ["merging", "completed"]:
            raise HTTPException(status_code=400, detail=f"File is already in {session.status} state.")

        await self.session_manager.set_status(upload_id, "merging")
        task = await merge_file_chunks_task.kiq(upload_id=upload_id)
        return task.task_id
```

#### 方案 3：幂等 Task ID / 任务防重

如果使用的是 Taskiq，可以指定确定的 `task_id`（如 `f"merge:{upload_id}"`），并在 Worker 端做幂等防护，确保同一 upload session 的合并任务即使重复派发也不会多次执行。
