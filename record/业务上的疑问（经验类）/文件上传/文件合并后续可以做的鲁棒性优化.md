### 问：这两段代码似乎会有并发安全问题

这两段代码确实存在**四个显著的高危并发安全问题与状态一致性漏洞**。核心问题主要出在 **Check-Then-Act（检查与执行之间的时间窗口）**、**慢 I/O 期间的状态突变** 以及 **异常补偿逻辑缺陷**。



### 并发问题剖析

**1. 慢 I/O 导致的“幽灵覆盖”（最严重）**



- **场景**：
  1. 请求 A 上传分片 0，校验通过（状态为 `UPLOADING`），开始耗时较长的网络流式传输 `await self.storage.upload_chunk(...)`。
  2. 客户端网络抖动超时，发起重试请求 B 上传分片 0。
  3. 请求 B 传输速度极快，先一步完成落盘、`replace`，并写入 `session.uploaded_chunks`。
  4. 客户端检测到所有分片上传完毕，调用 `trigger_merge`，状态成功流转为 `MERGING`，合并任务在后台开始读取各个分片。
  5. 此时**滞后的请求 A 终于完成数据接收**，执行 `aiofiles.os.replace(fake_tmp_chunk_path, true_tmp_chunk_path)`。
- **后果**：请求 A 会在**合并任务正在读取分片甚至合并已完成**时，强行替换掉磁盘上的分片文件，导致合并出来的文件损坏，或者在合并清理完临时目录后残留孤儿分片。

**2. 同一分片的重入竞态（Check-Then-Act）**



- `upload_file_chunk` 中对 `chunk_index in session.uploaded_chunks` 的判断仅是一个**快照读取**，没有加互斥锁。
- 当客户端同时发出两个相同 `chunk_index` 的请求时，两个协程同时通过校验，分配不同 UUID 的临时文件各自写盘。最终谁后执行 `replace` 谁覆盖，浪费双倍的网络带宽与磁盘 I/O。

**3. 异常回滚时的文件泄漏**



- 在 `upload_file_chunk` 中：

  Python

  ```
  await aiofiles.os.replace(fake_tmp_chunk_path, true_tmp_chunk_path)
  # 若下面这行（如 Redis/DB 连接故障）抛出异常：
  await self.session_manager.add_uploaded_chunk(...)
  ```

  发生异常进入 `except Exception` 时，代码执行的是：

  Python

  ```
  await asyncio.to_thread(fake_tmp_chunk_path.unlink, missing_ok=True)
  ```

  但由于 `fake_tmp_chunk_path` 已经被原子重命名为 `true_tmp_chunk_path`，**`fake` 文件已不存在，而 `true` 文件已落盘且永远不会被清理**，导致元数据（未记录）与物理文件（已存在）产生不一致。

**4. 任务分发网络抖动导致的状态裂脑**



- 在 `trigger_merge` 中：

  Python

  ```
  task = await merge_file.kiq(upload_id=upload_id)
  ```

  如果任务已经成功推入 MQ/Redis Broker，但在客户端等待 Broker 回应时出现网络超时异常，会触发 `except` 块中的 CAS 回滚，将状态重新置为 `UPLOADING`。

- **后果**：Worker 进程已经在消费合并任务，而 API 层却认为该任务仍可继续上传分片，引发灾难性的读写冲突。

### 优化与重构方案

针对上述并发漏洞，核心改进原则为：



1. **分片上传互斥**：利用 Redis 分布式锁限制单一分片并发上传。
2. **状态双重检查（Double-Checked Locking）**：在重命名文件和记录状态**前**，再次校验当前 Session 状态依然是 `UPLOADING`。
3. **修复清理逻辑**：一旦重命名完成，后续出错必须清理真实文件路径。

### 问：为什么Broker 投递失败时，先记录为异常/失败状态，而不是盲目切回 UPLOADING，你推理一下到底会不会出问题吧，因为compare_and_set_status是原子操作

你的怀疑非常敏锐：**如果只看单机或者单个存储系统内部，`compare_and_set_status`（CAS）确实是严格原子的。**



这里的并发隐患**不在于 CAS 本身是否原子**，而在于**分布式系统中的“经典网络超时困境”与跨组件状态不同步**。`merge_file.kiq()`（向消息队列/Broker 投递任务）与状态数据库（Redis/MySQL）是两个完全独立的系统，它们之间不存在跨系统的分布式事务。



### 核心推理：回滚到 `UPLOADING` 会引发什么问题？

问题的根源出在分布式通信的第三种状态：**“超时（Timeout）不等于失败，可能是成功了但响应丢了”**。



推演以下典型生产事故场景：



Plaintext

```
API 进程                        Broker (MQ / Redis)                   Worker 进程
   │                                   │                                   │
   ├─ 1. CAS: UPLOADING -> MERGING     │                                   │
   │                                   │                                   │
   ├─ 2. 发送任务 kiq() ──────────────>│ (成功写入队列)                     │
   │                                   │                                   │
   │  (网络抖动/超时, 未收到 Broker ACK) │                                   │
   │  触发 TimeoutException!           │                                   │
   │                                   │                                   │
   ├─ 3. 进入 except，执行 CAS 回滚:     │                                   │
   │     MERGING -> UPLOADING (成功!)  │                                   │
   │                                   │                                   │
   │                                   ├─ 4. Worker 从队列取出任务 ────────>│ (开始执行合并)
   │                                   │                                   │
   ├─ 5. 客户端收到 500，发起重试       │                                   │
   │     触发 trigger_merge            │                                   │
   │     CAS: UPLOADING -> MERGING     │                                   │
   │     投递任务 kiq() ──────────────>│ (第 2 个任务进队!)                 │
   │                                   │                                   │
   │                                   ├─ 6. Worker 2 取出第 2 个任务 ─────>│ (两个 Worker 同时合并同个文件!)
```

#### 致命冲突 1：双重合并（Dual-Merge 脑裂）

- **成因**：Broker 已经成功把任务放入队列，只是向 API 返回 ACK 时超时。API 以为投递失败，把状态强行滚回 `UPLOADING`。
- **后果**：前端收到报错后重试合并，状态再次从 `UPLOADING` 变成 `MERGING`，向 Broker 投递了第二个任务。两个 Worker 节点同时拿到同一个 `upload_id` 执行合并与切片删除，导致**目标文件内容错乱、哈希损坏或抛出文件读写占用异常**。

#### 致命冲突 2：生命周期语义倒退与分片读写冲突

- 此时分片已经全部上传完毕（100%），状态机强行倒退回 `UPLOADING` 在业务语义上是错误的。
- 如果前端检测到状态是 `UPLOADING`，某些自动重试组件可能会误以为“分片还没传完”，继续调用 `upload_file_chunk`。
- 此时后台 Worker 已经在读取并删除分片，而前端还在上传写入分片，直接发生**一边写一边删**的竞争。

### 为什么记录为 `FAILED`（或 `QUEUE_FAILED`）更安全？

在分布式状态机设计中，**宁可让状态“终止”或“等待排查”，也绝不能在不确定外界事实的情况下把状态“倒流”**。



| **策略**                           | **遇到 Broker 超时异常的处理**   | **带来的后果**                                               |
| ---------------------------------- | -------------------------------- | ------------------------------------------------------------ |
| **回滚到 `UPLOADING`**             | 假定外部肯定没成功，强行逆转状态 | 极易发生双发合并任务、并发读写、文件损毁。                   |
| **置为 `FAILED` / `MERGE_FAILED`** | 阻断后续所有写入，冻结流程       | 不会产生新的并发操作；若 Worker 实际在跑，也不会有外部干扰。 |
| **保持 `MERGING`**                 | 不做任何回滚，返回任务状态未知   | 留给合并 Worker 执行完毕后自动转为 `COMPLETED` 或失败回调。  |

### 生产级标准解法

要彻底杜绝该问题，仅靠修改状态是不够的，推荐以下两种方案之一：



**方案 A：给 Worker 合并逻辑加分布式排他锁（推荐，最轻量）**

Broker 端即使因为网络抖动收到两个重复任务，Worker 执行合并时使用分布式锁（如基于 Redis 的 Redlock 或 SETNX）：

```

        # 即使投递了两次，只有一个 Worker 能进，第二个 Worker 进来发现已完成直接退出
        ...
```

**方案 B：任务投递引入 Task ID 幂等 / 事务消息（Outbox 模式）**

在调用 `kiq()` 之前，先生成固定的 `task_id = f"merge:{upload_id}"`，让 Broker 根据这个 ID 做去重。如果 Broker 不支持去重，状态机应该设计显式的重试动作：

### 问：原来如此，这也太复杂了吧，真是没辙了。如果Worker中有分布式锁可以吗

**完全可以，而且这恰恰是工业界最推荐、最解脱心智的标准做法。**



分布式系统里有一句名言：**“把重试权留给上游，把幂等与防并发的防线下沉到底层（Worker）。”**



只要 Worker 自身具备互斥锁和幂等检查，前面的 API 接口无论怎么超时、怎么重试、状态机怎么抽风，底层的物理文件和合并逻辑都**绝对不会损坏**。整个系统的复杂度会直接下降一个数量级。



### Worker 加锁标准实现（双重检查 + 互斥锁）

Worker 端只需遵循 **“拿锁 -> 再次检查状态 -> 执行合并 -> 标记完成”** 的范式：



Python

```
@broker.task
async def merge_file(upload_id: str):
    # 1. 针对 upload_id 加分布式互斥锁（例如基于 Redis）
    # 注意：锁超时时间(lock_timeout)需预留足够长，或者开启自动续期(Watchdog)
    async with redis_lock(f"lock:merge:{upload_id}", timeout=600):
        # 2. 获取最新状态做二次确认（幂等防线）
        session = await session_manager.get_session(upload_id)
        
        # 如果前一个任务已经合并完了，直接跳过退出
        if session.status == UploadStatus.COMPLETED:
            return {"status": "already_completed"}

        # 如果状态不是可合并状态，也不做处理
        if session.status != UploadStatus.MERGING:
            return {"status": "invalid_status", "current": session.status.value}

        try:
            # 3. 执行真正的物理合并与清理
            await storage.merge_chunks(...)
            await storage.cleanup_chunks(...)
            
            # 4. 写入 DB 并将状态标记为 COMPLETED
            await record_completed_session(upload_id)
        except Exception:
            # 合并如果发生真实 I/O 错误，标记为 MERGE_FAILED 便于排查
            await session_manager.set_status(upload_id, UploadStatus.MERGE_FAILED)
            raise
```

### 这对 API 端带来的巨大解脱

有了 Worker 的分布式锁兜底，API 层的 `trigger_merge` 就可以**彻底抛弃神经质的状态回滚**：



1. **API 不需要再回滚到 `UPLOADING`**：如果 `kiq()` 投递抛出异常或超时，直接保留 `MERGING` 状态（或直接返回 504）。
2. **客户端允许无脑重试**：
   - 哪怕前端因为网络超时连续点了 3 次“合并”，投递了 3 个任务进队列。
   - 队列里的 3 个任务被同一个或不同 Worker 消费时：
     - **任务 1** 抢到了锁，正常合并，并将状态改成 `COMPLETED`。
     - **任务 2 和 3** 排队拿到锁后，第一行代码读到状态已经是 `COMPLETED`，直接返回退出，**什么都不会破坏**。

### 唯一需要注意的 2 个小细节

- **锁的超时时间（TTL）**：大文件合并耗时可能需要几十秒甚至数分钟。Redis 锁的过期时间必须远大于预期合并时间，或者使用类似 Celery/Redisson 机制的 **Watchdog（看门狗自动续期）**，防止文件合并到一半锁由于超时失效。
- **分片与合并的互斥**：在 Worker 拿锁合并期间，`upload_file_chunk` 只要判断 `session.status != UploadStatus.UPLOADING` 就会直接拒绝分片上传，读写冲突自然化解。

这样设计，API 只管放心派发任务，Worker 负责自身安全，边界就清晰多了。



### 问：但是trigger_merge函数的逻辑又导致了没法重试，就一直停在这里了

你说得太准确了！这针见血地指出了问题——**“状态悬挂（State Hanging / Deadlock）”**。



如果按照之前的逻辑：



1. CAS 把状态由 `UPLOADING` 推进到了 `MERGING`。
2. 紧接着 `kiq()` 投递失败抛出异常，状态停在 `MERGING` 且没有回滚。
3. 客户端（或前端轮询）点击重试，再次调用 `trigger_merge`。
4. 此时 CAS 发现当前状态是 `MERGING`（而不是期望的 `UPLOADING`），**CAS 失败直接抛出 409 异常**。
5. **结果**：前端卡死在 409，分片既不能再传，合并任务也再也派发不出去，整个上传流程彻底死锁。

### 破局核心：既然 Worker 已经有锁，API 就要做成「幂等重入」

既然 Worker 端已经有了分布式锁和幂等保障，**`trigger_merge` 就不应该把 `MERGING` 视为“冲突并拒绝”，而应该视其为“已在进行中或允许断点重试”**。



在 API 层引入一个持久化的 **`merge_task_id`**，`trigger_merge` 就可以根据以下逻辑安全地自愈和幂等重试：



- **场景 1（正常重试）**：上次投递成功了，客户端只是因网络超时没收到响应而重试。
  - 发现状态是 `MERGING` 且 **已有 `merge_task_id`** $\to$ **直接返回该 ID，成功响应**（幂等）。
- **场景 2（失败重试 / 故障自愈）**：上次 `kiq()` 真的挂了，或者 Broker 连不上。
  - 发现状态是 `MERGING` 但 **`merge_task_id` 为空** $\to$ 说明上次派发中断了，**允许重新执行 `kiq()` 补发任务**！

### 重构后的 `trigger_merge`（彻底消除死锁）

Python

```
async def trigger_merge(self, upload_id: str) -> tuple[UploadStatus, str | None]:
    try:
        session = await self.session_manager.get_session(upload_id=upload_id)
    except ValueError:
        raise HTTPException(status_code=404, detail=f"Unknown upload session: {upload_id}")

    # 1. 终态检查：已合并完成，直接幂等返回
    if session.status == UploadStatus.COMPLETED:
        return UploadStatus.COMPLETED, None

    # 2. 幂等与断点重试：如果状态已经是 MERGING
    if session.status == UploadStatus.MERGING:
        # 情况 A：之前已经成功派发过任务，直接返回现有的 task_id，绝不报 409
        if session.merge_task_id:
            return UploadStatus.MERGING, session.merge_task_id

        # 情况 B：状态是 MERGING 但 task_id 为空！
        # 这说明上次在 kiq() 阶段抛了异常，导致任务断挂在此处。
        # 因为底层 Worker 有分布式锁兜底，这里可以绝对安全地重新投递！
        try:
            task = await merge_file.kiq(upload_id=upload_id)
            await self.session_manager.set_merge_task_id(upload_id, task.task_id)
            return UploadStatus.MERGING, task.task_id
        except Exception as e:
            raise HTTPException(status_code=500, detail=f"Failed to retry dispatch merge task: {str(e)}")

    # 3. 首次触发：校验状态必须是 UPLOADING
    if session.status != UploadStatus.UPLOADING:
        raise HTTPException(
            status_code=400,
            detail=f"Cannot merge in current status: {session.status.value}"
        )

    # 完整性校验
    expected_chunks = set(range(session.total_chunks))
    if session.uploaded_chunks != expected_chunks:
        missing_chunks = expected_chunks - session.uploaded_chunks
        raise HTTPException(
            status_code=400,
            detail=f"Chunks incomplete. Missing: {list(missing_chunks)}"
        )

    # 4. CAS 将状态从 UPLOADING 改为 MERGING
    cas_success = await self.session_manager.compare_and_set_status(
        upload_id=upload_id,
        user_id=session.user_id,
        file_hash=session.file_hash,
        expected_status=UploadStatus.UPLOADING,
        new_status=UploadStatus.MERGING
    )

    # 如果并发激烈，另一个请求先一步完成了 CAS，重新读取最新状态返回即可（避免误报 409）
    if not cas_success:
        latest = await self.session_manager.get_session(upload_id=upload_id)
        return latest.status, latest.merge_task_id

    # 5. CAS 成功后，派发任务并记录 task_id
    try:
        task = await merge_file.kiq(upload_id=upload_id)
        # 记录 task_id，作为任务派发成功的凭证
        await self.session_manager.set_merge_task_id(upload_id, task.task_id)
        return UploadStatus.MERGING, task.task_id
    except Exception as e:
        # 这里不需要任何回滚操作！
        # 状态保持 MERGING，但 merge_task_id 依然为 None。
        # 用户下次重试时，会命中上面的【情况 B】，自动恢复重发！
        raise HTTPException(
            status_code=500,
            detail=f"Fail to trigger merge task, please retry: {str(e)}"
        )
```

### 这套设计为什么不会再卡死？

1. **消除了脆弱的回滚机制**：再也没有跨组件（Redis/DB vs Broker）因为网络超时导致的数据倒退与状态脑裂。
2. **请求完全幂等（Idempotent）**：前端网络超时后无论连续点 5 次“合并”，前 1 次拿到结果，后 4 次会命中 `if session.merge_task_id` 直接秒返同一个 `task_id`。
3. **自愈断点重试**：如果派发阶段真的遇到 Broker 挂掉抛 500，等运维修好 Broker 后，前端点“重试”，代码自动识别出“状态在合并但没有任务凭据”，自动补发任务，流程瞬间被盘活。

### 问：要不将compare_and_set_status函数放到merge_file worker中执行，反正worker中有分布式锁

**绝对不行。** 这个想法看似把锁和状态集中到了 Worker，省心了，但在分布式系统中这属于“把门禁从大门口撤走，搬到了里屋仓库”。



如果把 CAS 状态变更下沉到 Worker，`trigger_merge` API 只负责发消息而不改状态，会引发 **三个无法接受的生产级隐患**：



### 隐患 1：API 彻底丧失防洪能力，MQ 会被瞬间打爆（Queue Flooding）

如果 API 不改状态，数据库里的状态永远是 `UPLOADING`。



- **推演**：前端网络卡顿，用户手抖连点 10 次“合并”，或者前端自动化轮询组件在不断重试。
- **后果**：
  - 因为状态还是 `UPLOADING`，且分片已经全部上传，**10 个 API 请求全部校验通过**！
  - API 会往 Broker 连续写入 10 条 `merge_file` 任务消息。
  - 虽说 Worker 有分布式锁，后 9 个任务拿到锁后会退出，但你的 **MQ 队列被塞满了垃圾任务，浪费了系统算力和带宽**。

### 隐患 2：排队延迟期间的“幽灵写入”（分片篡改风险）

消息队列在业务高峰期存在**消费延迟**（排队几秒到数十秒很常见）。



- **推演**：
  1. API 成功投递了任务，但 Worker 队列积压，任务在 Broker 里排队 5 秒。
  2. 这 5 秒内，数据库里的状态**依然是 `UPLOADING`**。
  3. 此时客户端某个迟到的分片上传重试请求（慢网络 I/O）刚好到达 `upload_file_chunk`。
  4. `upload_file_chunk` 去查状态，发现依然是 `UPLOADING`，**放行写入**！
  5. 此时 Worker 终于排到了任务，抢锁开始合并，而分片目录正在被这个迟到的请求动态修改。

### 隐患 3：前端轮询体验崩溃（UI 无法感知排队状态）

大文件合并通常前端会做轮询展示：“上传中 $\to$ 排队/合并中 $\to$ 完成”。



- 如果 API 这一步不把状态推进到 `MERGING`（或 `QUEUED`）：
  - 前端调用完触发合并接口，立即轮询 `get_status`，查出来的仍然是 `UPLOADING`。
  - 前端代码会误判：“合并没触发成功？我还在上传中？”进而引发前端代码反复调用触发逻辑，造成恶性循环。

### 架构权责边界：状态机必须由 API 推进

在标准分布式状态机架构中，两者的职责永远是泾渭分明的：



| **组件**      | **核心职责**                                 | **举例**                                                     |
| ------------- | -------------------------------------------- | ------------------------------------------------------------ |
| **API 层**    | **门禁检查 + 状态跃迁（State Transition）**  | 关掉写入口（不允许再传分片），将状态改为 `MERGING`，阻断重复请求。 |
| **Worker 层** | **重型执行 + 最终收敛（Final Consistency）** | 拿排他锁，只管安安静静合并物理文件，最后将状态推进为 `COMPLETED`。 |

### 最优解：如果你嫌逻辑绕，引入 `QUEUED` 状态

如果你觉得在 API 里面直接改成 `MERGING` 会和“任务投递失败”纠缠不清，业界最干净优雅的做法是**拆分状态**：



Plaintext

```
[UPLOADING] ──(API 原子 CAS)──> [QUEUED] ──(Worker 拿锁开工)──> [MERGING] ──> [COMPLETED]
```

1. **API 层**：只做一件事，把状态从 `UPLOADING` 原子 CAS 改成 `QUEUED`（已入队/排队中）。
   - 一旦进入 `QUEUED`，分片上传接口立刻被锁死（禁止写入）。
   - 后续任何重复的 `trigger_merge` 请求看到是 `QUEUED`，直接秒返“排队中”，绝不重复投递 MQ。
2. **Worker 层**：拿分布式锁，开工时将状态从 `QUEUED` 改为 `MERGING`，合并完改成 `COMPLETED`。

这样不仅概念清晰、职责完全解耦，而且彻底杜绝了状态悬挂和并发冲突。
