async def cleanup_resources(
    files: list[Path | str] | None = None,
    dirs: list[Path | str] | None = None,
):
    """统一在后台线程中清理临时文件与目录，自动忽略不存在及权限异常"""
    def _sync_clean():
        if files:
            for file_path in files:
                try:
                    Path(file_path).unlink(missing_ok=True)
                except Exception:
                    pass
        if dirs:
            for dir_path in dirs:
                try:
                    shutil.rmtree(dir_path, ignore_errors=True)
                except Exception:
                    pass

    await asyncio.to_thread(_sync_clean)

### 问：这是我的文件分配合并代码和文件表定义，但是在大文件上传合并过程中报错了

报错的根本原因是 **MySQL 中 `INT` 类型的数值溢出**。

SQLModel/SQLAlchemy 默认将 Python 的 `int` 映射为 MySQL 的 32 位有符号 `INT` 类型，其最大取值范围为 **$2,147,483,647$ 字节（约 2GB）**。当前上传的文件大小为 **`4,194,304,000` 字节（约 3.9GB）**，超出了有符号 `INT` 的上限，导致数据库抛出 `1264: Out of range value for column 'total_size'`。

---

### 1. 修改模型定义

引入 SQLAlchemy 的 `BigInteger`，通过 `sa_type` 将该字段映射为 MySQL 的 `BIGINT`（最大支持约 9EB，彻底解决大文件字节数溢出问题）：

```python
from datetime import datetime

### 问：你说以字节为单位是不是太小了

**不会太小，以字节（Byte）存储恰恰是工业界最标准、最正确的做法。**



上次报错的原因并非“字节太小”，而是字段类型选用了 32 位的 `INT`。一旦改用 64 位的 `BIGINT`，以字节存储不仅完全够用，还能避免一系列后续架构隐患。



**1. 空间完全不是瓶颈（BIGINT 支持到 9 EB）**



- MySQL 的 `BIGINT` 占用 8 字节存储空间。
- 最大取值约为 $9.22 \times 10^{18}$ 字节，折算下来约为 **92 亿 GB（9 EB）**。
- 现实中单文件几乎不可能达到 EB 级别，无论多大的视频或数据包，`BIGINT` 的字节计数绝对不会溢出。

**2. 核心网络协议与文件系统均强依赖“精确字节”**



- **断点续传与分片：** HTTP 请求头中的 `Content-Range: bytes 0-1048575/4194304000`、`Content-Length` 以及分片下载（Range Requests），底层通信单位全部是精确到 1 字节的整数。
- **数据校验与完整性：** 文件传输是否完整、哈希校验是否正确，都必须比对精确字节大小；若存储为 KB 或 MB，只要有 1 个字节截断或丢失都无法感知。
- **避免浮点数精度灾难：** 如果存成以 MB/GB 为单位的浮点数（如 `3.90625 MB`），不同编程语言的 float/double 解析存在舍入误差，极易引发相等判断失效或计算对不齐。

**3. “存储存原始数据，展示做单位转换”原则**



数据库中保存**最小不可分割的客观事实（即绝对字节整数）**，业务展示层按需动态格式化为人类可读格式：



Python

```
def format_size(size_bytes: int) -> str:
    """人类可读的文件大小转换"""
    if size_bytes <= 0:
        return "0 B"
    units = ["B", "KB", "MB", "GB", "TB", "PB"]
    i = 0
    size = float(size_bytes)
    while size >= 1024 and i < len(units) - 1:
        size /= 1024
        i += 1
    return f"{size:.2f} {units[i]}"

# 示例: 4194304000 -> 3.91 GB

### 问：那如果要适合人类读取的话是不是前端加一个转换逻辑就可以了？

**是的，完全可以在前端做，而且这通常是现代化架构的最佳实践。**

让后端专注返回最纯粹的机器数据（原始字节数 `total_size: 4194304000`），由前端全权负责格式化与视图渲染，兼具灵活性与解耦优势。

---

**为什么前端做转换更好**

* **职责分离：** 后端 API 保持纯粹与规范，避免返回冗余或格式固化的展示字段。
* **灵活控制精度：** 不同视图对精度的要求不同（如列表页只需要保留整数 `4 GB`，详情页或传输进度条需要精确到 `3.91 GB`），前端可按组件需求随意调整，无需修改后端。
* **适配国际化（i18n）：** 方便结合前端本地化方案（例如某些语系的小数点用逗号 `,`，或者按需切换 `GiB` 与 `GB`）。

---

**前端通用格式化实现 (TypeScript / JavaScript)**

```typescript
/**
 * 将字节大小格式化为人类可读字符串
 * @param bytes 字节数 (number 或 BigInt)
 * @param decimals 小数位数，默认为 2
 */
export function formatBytes(bytes: number | bigint, decimals: number = 2): string {
  const num = typeof bytes === 'bigint' ? Number(bytes) : bytes;
  if (!num || num <= 0) return '0 B';

  const k = 1024;
  const dm = Math.max(0, decimals);
  const units = ['B', 'KB', 'MB', 'GB', 'TB', 'PB'];

  // 计算单位所在的阶数
  const i = Math.floor(Math.log(num) / Math.log(k));
  const safeIndex = Math.min(i, units.length - 1);

  // 格式化并去除末尾无效的 0 (如 4.00 GB -> 4 GB)
  const formattedSize = parseFloat((num / Math.pow(k, safeIndex)).toFixed(dm));
  return `${formattedSize} ${units[safeIndex]}`;
}

// 使用示例：
// formatBytes(4194304000)      => "3.91 GB"
// formatBytes(1048576)         => "1 MB"
// formatBytes(0)               => "0 B"

```

---

**只有一种情况建议后端补一个转换**

如果你的业务涉及**导出 Excel/CSV 报表**、**发送邮件/短信通知**，或对接**第三方服务端 Webhook**，由于这些下游场景没有前端渲染引擎，在后端的导出逻辑或只读 DTO 里加一个计算属性输出人类可读文本会更方便。在普通的 Web / App 交互中，完全交给前端处理即可。
