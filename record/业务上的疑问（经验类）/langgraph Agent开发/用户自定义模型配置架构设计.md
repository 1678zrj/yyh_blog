### Gemini:

### 问：我在做FastAPI后端开发和langgraph Agent开发，当前的一个主要问题是关于模型适配层，基于langchain给用户提供多个provider选择，但我主要的疑问在于如果用户修改了自己的模型配置（包括provider,api_key,model_name,base_url），这些配置应该是持久化到数据库，然后用户修改后就更新数据库中的数据，然后graph运行之前都从数据库中读取配置。还是有其它方案？

将用户自定义的模型配置（Provider、API Key、Model Name、Base URL）**持久化到数据库是绝大多数 SaaS 和 Agent 平台的核心基石方案**，但单纯的“运行前查数据库”在架构设计上有多种权衡与进阶替代方案。



针对模型适配与配置管理，业界主要有四种实现架构。



### 一、 主流方案对比

| **方案**                                                  | **核心机制**                                                 | **优势**                                                     | **劣势 / 适用场景**                                          |
| --------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **方案 1：DB 持久化 + 运行时动态解析（基线方案）**        | DB 存密文，FastAPI 在收到请求时拉取配置，动态实例化 ChatModel 注入 Graph | 简单直观、状态集中、天然支持多端多会话复用                   | 每次运行依赖 DB；若节点内部多次重构 Client 可能会有轻微开销。**最推荐的标准做法**。 |
| **方案 2：DB 持久化 + Redis / 内存缓存层**                | DB 为持久化真源，写入/更新时双写或淘汰 Redis 缓存，Graph 运行前读缓存 | 降低 DB 读压力，适合高并发或分布式 Worker（如 Celery/TaskIQ） | 引入缓存一致性维护（修改配置需主动驱逐 Key）。               |
| **方案 3：无状态透传（Ephemeral / Request-Level BYOK）**  | 配置不存后端 DB，由前端存储（如 localStorage）随请求 Header/Body 动态传入 | 后端零存储成本、零泄密合规风险（GDPR/等保友好）              | 跨设备无法同步，用户体验弱，难以支持脱机后台定时任务。       |
| **方案 4：独立 AI Gateway 代理层（如 LiteLLM / OneAPI）** | 后端统一打向本地 Gateway，用户在网关侧分配虚拟 Token，网关负责 Provider 适配与密钥路由 | 业务代码与 LLM 完全解耦，自带重试、负载均衡、花费统计与故障转移 | 增加运维复杂度，需要部署额外中间件服务。                     |

### 二、 推荐的最佳实践架构（方案 1 + 2 的融合落地）

对于大多数 FastAPI + LangGraph 系统，最稳健的做法是：**数据库持久化（加密存储） + FastAPI 请求层解析注入 + LangGraph 动态 `configurable` 机制**。



#### 1. 数据库存储与密钥安全

API Key 绝不可明文存放在数据库中。应当采用应用层对称加密（如 AES-256-GCM 或 `cryptography.fernet`），加密密钥作为环境变量注入后端：



Python

```
# security.py
import os
from cryptography.fernet import Fernet

ENCRYPTION_KEY = os.getenv("APP_ENCRYPTION_KEY")  # Fernet.generate_key()
fernet = Fernet(ENCRYPTION_KEY)

def encrypt_key(plain_key: str) -> str:
    return fernet.encrypt(plain_key.encode()).decode()

def decrypt_key(cipher_key: str) -> str:
    return fernet.decrypt(cipher_key.encode()).decode()
```

#### 2. 模型工厂（Model Factory）

针对 LangChain 生态，利用统一的初始化工厂封装 Provider 差异：



Python

```
# model_factory.py
from langchain_core.language_models.chat_models import BaseChatModel
from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic

def get_chat_model(
    provider: str,
    model_name: str,
    api_key: str,
    base_url: str | None = None,
    temperature: float = 0.7,
) -> BaseChatModel:
    if provider == "openai" or provider == "deepseek" or provider == "qwen":
        # 兼容 OpenAI 格式的各类兼容层（DeepSeek, 通义千问, Moonshot 等）
        return ChatOpenAI(
            model=model_name,
            api_key=api_key,
            base_url=base_url,
            temperature=temperature,
        )
    elif provider == "anthropic":
        return ChatAnthropic(
            model_name=model_name,
            api_key=api_key,
            base_url=base_url,
            temperature=temperature,
        )
    else:
        raise ValueError(f"Unsupported provider: {provider}")
```

#### 3. LangGraph 的解耦接入：不要在编译期绑定 Model

在构建 LangGraph 时，**绝不能在全局或 Graph 构建函数外写死 `llm = ChatOpenAI(...)`**。应当通过 LangGraph 的 `RunnableConfig` 传入运行时配置，并在 Node 执行时即时解析：



Python

```
# agent_graph.py
from typing import Annotated, TypedDict
from langchain_core.runnables import RunnableConfig
from langgraph.graph import StateGraph, START, END

class AgentState(TypedDict):
    messages: list

async def chatbot_node(state: AgentState, config: RunnableConfig):
    # 从 config["configurable"] 中提取动态配置
    configurable = config.get("configurable", {})
    provider = configurable.get("provider")
    model_name = configurable.get("model_name")
    api_key = configurable.get("api_key")
    base_url = configurable.get("base_url")

    # 即时获取 LLM 实例（可加入针对 client 的轻量 lru_cache 优化）
    model = get_chat_model(
        provider=provider,
        model_name=model_name,
        api_key=api_key,
        base_url=base_url
    )
    
    response = await model.ainvoke(state["messages"])
    return {"messages": [response]}

# 静态构建 Graph 结构，完全不依赖特定的模型实例
builder = StateGraph(AgentState)
builder.add_node("chatbot", chatbot_node)
builder.add_edge(START, "chatbot")
builder.add_edge("chatbot", END)
graph = builder.compile()
```

#### 4. FastAPI 请求链路

在 FastAPI 路由中，通过用户 Session/Token 查询用户当前配置并解密，然后一并打入 Graph 的执行配置：



Python

```
# main.py
from fastapi import FastAPI, Depends
from sqlalchemy.ext.asyncio import AsyncSession

app = FastAPI()

@app.post("/api/chat")
async def chat_endpoint(
    request: ChatRequest,
    current_user = Depends(get_current_user),
    db: AsyncSession = Depends(get_db)
):
    # 1. 从 DB 读取用户当前配置（若量大，可在服务内加一层 Redis 缓存，Key: f"user_llm_cfg:{current_user.id}"）
    user_config = await get_user_model_config(db, current_user.id)
    decrypted_api_key = decrypt_key(user_config.encrypted_api_key)

    # 2. 组装 Graph 运行时配置
    run_config = {
        "configurable": {
            "provider": user_config.provider,
            "model_name": user_config.model_name,
            "api_key": decrypted_api_key,
            "base_url": user_config.base_url,
            "thread_id": request.session_id,  # LangGraph checkpoint 线程 ID
        }
    }

    # 3. 异步调用 Graph
    result = await graph.ainvoke(
        {"messages": [request.message]},
        config=run_config
    )
    return result
```

### 三、 几个关键工程问题的权衡

1. **“每次运行前读 DB 是否是性能瓶颈？”**
   - **不是**。一次 LLM 网络调用通常在 500ms 到数秒不等，而一次带索引的 DB 查询耗时通常在 1~3ms。
   - 如果并发较高，直接在 FastAPI 依赖项中包裹一层 Redis 缓存即可（用户通过 `PUT /api/user/model-config` 修改配置时，直接 `DEL` 对应的 Redis Key）。
2. **“如果 Graph 内部有 5 个不同的 Node 都要用 LLM，会反复解密/初始化吗？”**
   - 如果直接在每个 Node 调用 `get_chat_model`，会有微小的对象实例化开销。
   - 可以在 FastAPI 入口层直接调用工厂生成好 `model` 实例，直接通过依赖注入传给业务 Service，或通过 Python 运行时的 `functools.lru_cache` 缓存 `(provider, model_name, api_key, base_url)` 生成的 Client 实例，避免重复创建底层 HTTP 连接池（`httpx.AsyncClient` 复用连接非常关键）。
3. **何种情况应该引入第三方 Gateway（LiteLLM Proxy）？**
   - 当你需要给用户配置 Fallback 机制（例如：DeepSeek 接口超时自动降级到 Qwen/GPT-4o）。
   - 当你需要精确限制每个用户的 Token 配额或统计调用成本时，把这种逻辑放在代理网关层比手写在 FastAPI 里更干净。

这 6 个核心字段已经覆盖了最基础的连通性，但在实际落地 FastAPI + Agent 业务系统时，如果只保留这几个字段，很快会遇到**多模型管理、特定 Provider 差异、以及缓存同步**三个维度的瓶颈。



以下是补充建议与推荐的数据库表结构设计。



### 一、 核心缺漏与工程考量

1. **单模型 vs 多模型（1:1 还是 1:N）**
   - 如果表只存一条记录，用户想切换“用 DeepSeek 跑代码”和“用 Claude 写文章”时，就必须每次覆盖配置。
   - **建议**：设计为 `1:N`（一个用户可保存多套模型配置），并增加 `name`（配置别名，如“我的 DeepSeek-V3”）和 `is_default`（是否为当前默认激活配置）。
2. **扩展参数 `extra_params` / `custom_headers` (JSON 字段)**
   - 不同 Provider 的参数并不通用：
     - **Azure OpenAI**：需要 `api_version`。
     - **OpenRouter / 自建网关**：需要特定的 HTTP Header（如 `HTTP-Referer`, `X-Title`）。
     - **特殊模型调优**：用户可能希望针对某个模型单独配置默认 `temperature`, `max_tokens`。
   - 用一个 `JSON` / `JSONB` 字段承载这些动态差异，避免频繁改动表结构。
3. **安全防呆：命名区分明文与密文**
   - 字段名建议命名为 `encrypted_api_key`，从代码审查（Code Review）层面杜绝将未加密的字符串直接落库。
4. **时间戳与缓存失效关联**
   - `updated_at` 字段至关重要：在方案二中，你可以利用 `updated_at` 做轻量的版本比对或判定 Redis 缓存是否过期。
5. **连通性校验状态（可选但极大改善前端体验）**
   - 增加 `status`（如 `active`, `invalid`）或 `last_tested_at`。当用户在前端输入完 Key 点击“测试连通性”后，标记该配置可用，防止坏 Key 触发后续 Agent 执行中断。

### 二、 数据库表设计（以 SQLModel / SQLAlchemy 为例）

Python

```
from datetime import datetime, timezone
from typing import Optional, Dict, Any
from uuid import UUID, uuid4
from sqlmodel import SQLModel, Field, Column
from sqlalchemy.dialects.postgresql import JSONB  # 若使用 MySQL 可换成 JSON

class UserModelConfig(SQLModel, table=True):
    __tablename__ = "user_model_configs"

    # 主键与归属
    id: UUID = Field(default_factory=uuid4, primary_key=True, index=True)
    user_id: UUID = Field(foreign_key="users.id", index=True, nullable=False)

    # 显示与区分
    name: str = Field(max_length=64, description="配置别名，例如：实验室 A800 本地模型 / 个人 DeepSeek")
    is_default: bool = Field(default=False, description="是否为该用户当前的默认选用模型")

    # 核心模型四要素
    provider: str = Field(max_length=32, description="供应商标识：openai, anthropic, deepseek, ollama, custom")
    model_name: str = Field(max_length=128, description="实际调用模型名：gpt-4o, claude-3-5-sonnet, deepseek-chat")
    encrypted_api_key: Optional[str] = Field(default=None, description="AES 对称加密后的 API Key（Ollama/本地私有模型可为空）")
    base_url: Optional[str] = Field(default=None, max_length=512, description="API 基础地址，适配自建中转、vLLM 或本地 Ollama")

    # 弹性扩展配置
    extra_params: Dict[str, Any] = Field(
        default_factory=dict,
        sa_column=Column(JSONB),
        description="模型专有扩展参数，如 {'temperature': 0.7, 'api_version': '2024-02-01', 'timeout': 60}"
    )

    # 状态与审计
    is_active: bool = Field(default=True, description="是否启用（软删除标记）")
    created_at: datetime = Field(
        default_factory=lambda: datetime.now(timezone.utc),
        nullable=False
    )
    updated_at: datetime = Field(
        default_factory=lambda: datetime.now(timezone.utc),
        sa_column_kwargs={"onupdate": lambda: datetime.now(timezone.utc)},
        nullable=False
    )
```

### 三、 方案二下的 Redis 缓存设计配合

既然采用方案二，建议在业务层约束以下几个数据交互细节：



#### 1. Redis Key 的设计粒度

避免把用户所有的模型配置打包成一个不可拆分的 String，建议使用 Hash 或独立 String：



- **当前生效模型 Key**：`user:{user_id}:active_model_config`
  - 存放反序列化后的 JSON 字符串（包含解密后的数据，**注意 Redis 自身的访问安全与内网隔离**）。
  - 或者存**密文**在 Redis 中，取到 FastAPI 本地进程内存后再做轻量解密（更安全，防止 Redis 泄露直接暴雷 Key）。
- **TTL 策略**：设置合理的过期时间（例如 `TTL = 86400` 即 1 天），采用 Cache-Aside 模式（命中则读，未命中查 DB 并回填）。

#### 2. 写穿 / 淘汰策略（Cache Invalidation）

当用户触发配置更新（新增、编辑、设为默认、删除）接口时：



1. **第一步**：开启 DB 事务，更新数据库表数据。
2. **第二步**：若更新了 `is_default=True`，需在 DB 中将其余配置的 `is_default` 刷成 `False`。
3. **第三步**：事务 Commit 成功后，**立即显式 `DEL user:{user_id}:active_model_config`**。
4. **不要在写接口里直接重写 Redis**，让下一次 Graph 运行请求进来时自发回查 DB 并重建缓存，避免并发更新时的脏写。

#### 3. Graph 运行前的读取流

Plaintext

```
FastAPI 请求到达 (/api/chat)
        │
        ▼
Redis.get("user:{user_id}:active_model_config")
        ├── [命中] ──► 反序列化 ──► 注入 Graph config
        │
        └── [失效/未命中] ──► 查 DB (WHERE user_id=X AND is_default=True)
                                │
                                ├── 回填 Redis (设置 TTL)
                                └── 注入 Graph config
```

在业务逻辑上确实是：**“清除旧默认 -> 激活新默认 -> 查默认使用 -> 无则走系统兜底”**。

### 一、 切换 `is_default` 的数据库操作：一步搞定还是两步？

很多开发者会写两条查询语句，但实际上有更优的写法：



#### 方案 A：一条 SQL 搞定全部状态切换（最推荐，单次 IO + 原子性）

利用 SQL 的布尔表达式，你可以在**一条 UPDATE 语句**中同时完成“旧的设为 False”和“新的设为 True”：



SQL

```
UPDATE user_model_configs
SET is_default = (id = :new_config_id)
WHERE user_id = :user_id;
```

> **原理**：只有 `id` 等于传入的 `:new_config_id` 的行，`is_default` 才会计算为 `True`，该用户下的其余行会自动计算为 `False`。既省去了一次数据库网络往返，又天然保证了原子性。

用 SQLAlchemy / SQLModel 异步写法：



Python

```
from sqlmodel import update

async def set_default_config(session: AsyncSession, user_id: UUID, new_config_id: UUID):
    stmt = (
        update(UserModelConfig)
        .where(UserModelConfig.user_id == user_id)
        .values(is_default=(UserModelConfig.id == new_config_id))
    )
    await session.execute(stmt)
    await session.commit()
```

#### 方案 B：分两步操作（必须包裹在同一个事务内）

如果你依然习惯分两步（例如业务上要在两步之间记录审计日志），**切记必须包裹在数据库事务中**，防止第一步执行成功、第二步因网络闪断或约束冲突失败，导致用户没有任何默认配置：



Python

```
async def set_default_config_two_steps(session: AsyncSession, user_id: UUID, new_config_id: UUID):
    async with session.begin():  # 开启事务
        # 1. 将原先所有配置重置为 False
        await session.execute(
            update(UserModelConfig)
            .where(UserModelConfig.user_id == user_id, UserModelConfig.is_default == True)
            .values(is_default=False)
        )
        # 2. 将指定配置设置为 True
        await session.execute(
            update(UserModelConfig)
            .where(UserModelConfig.id == new_config_id, UserModelConfig.user_id == user_id)
            .values(is_default=True)
        )
```

#### 数据库层面的防护：部分唯一索引（Partial Unique Index）

在 PostgreSQL 中，强烈建议加一个**部分唯一索引**，从底层防止并发写操作导致一个用户出现多个 `is_default=True`：



SQL

```
CREATE UNIQUE INDEX uq_user_default_config 
ON user_model_configs (user_id) 
WHERE is_default = TRUE;
```

### 二、 获取配置与系统兜底策略（Get & Fallback）

你的获取逻辑设计很规范，在代码架构上建议分为 **三级检索**：



Plaintext

```
[发起请求] 
   │
   ├─► 1. 临时指定覆盖？ (请求参数里是否带了特定的 config_id)
   │         │
   │         └─► 有 -> 查询该 config_id 并使用
   │
   ├─► 2. 查用户默认 (Redis 缓存 -> DB: WHERE user_id = X AND is_default = True)
   │         │
   │         └─► 有 -> 解密并使用
   │
   └─► 3. 系统兜底配置 (System Fallback)
             │
             └─► 读取 .env 或全局 Config 表 (如系统自带的免费体验模型)
```

#### 代码实现参考（Service 层）：

Python

```
# service.py
import json
from typing import Optional
from sqlmodel import select
from pydantic import BaseModel

class ResolvedModelConfig(BaseModel):
    provider: str
    model_name: str
    api_key: str
    base_url: Optional[str] = None
    extra_params: dict = {}
    is_system_fallback: bool = False

class ModelConfigService:
    @staticmethod
    async def get_effective_config(
        db: AsyncSession,
        redis,
        user_id: UUID,
        override_config_id: Optional[UUID] = None
    ) -> ResolvedModelConfig:
        
        # 1. 如果请求中明确指定了某次运行要使用的模型配置（如前端下拉框单次选定）
        if override_config_id:
            cfg = await db.get(UserModelConfig, override_config_id)
            if cfg and cfg.user_id == user_id and cfg.is_active:
                return ResolvedModelConfig(
                    provider=cfg.provider,
                    model_name=cfg.model_name,
                    api_key=decrypt_key(cfg.encrypted_api_key) if cfg.encrypted_api_key else "",
                    base_url=cfg.base_url,
                    extra_params=cfg.extra_params
                )

        # 2. 尝试从 Redis 读当前默认配置
        cache_key = f"user:{user_id}:active_model_config"
        cached_data = await redis.get(cache_key)
        if cached_data:
            data = json.loads(cached_data)
            # 缓存中存储的是密文，在内存中完成快速解密
            return ResolvedModelConfig(
                provider=data["provider"],
                model_name=data["model_name"],
                api_key=decrypt_key(data["encrypted_api_key"]) if data.get("encrypted_api_key") else "",
                base_url=data.get("base_url"),
                extra_params=data.get("extra_params", {})
            )

        # 3. 缓存未命中，查 DB 找 is_default = True 的配置
        stmt = select(UserModelConfig).where(
            UserModelConfig.user_id == user_id,
            UserModelConfig.is_default == True,
            UserModelConfig.is_active == True
        )
        result = await db.execute(stmt)
        user_default = result.scalars().first()

        if user_default:
            # 回填 Redis (设置 1 天过期)
            cache_payload = {
                "id": str(user_default.id),
                "provider": user_default.provider,
                "model_name": user_default.model_name,
                "encrypted_api_key": user_default.encrypted_api_key,
                "base_url": user_default.base_url,
                "extra_params": user_default.extra_params
            }
            await redis.setex(cache_key, 86400, json.dumps(cache_payload))

            return ResolvedModelConfig(
                provider=user_default.provider,
                model_name=user_default.model_name,
                api_key=decrypt_key(user_default.encrypted_api_key) if user_default.encrypted_api_key else "",
                base_url=user_default.base_url,
                extra_params=user_default.extra_params
            )

        # 4. 都没有，回退到系统公共默认配置（从 settings / .env 读取）
        return ResolvedModelConfig(
            provider=settings.DEFAULT_LLM_PROVIDER,     # 如 "openai" / "deepseek"
            model_name=settings.DEFAULT_LLM_MODEL,       # 如 "deepseek-chat"
            api_key=settings.DEFAULT_LLM_API_KEY,       # 平台提供的全局 Key
            base_url=settings.DEFAULT_LLM_BASE_URL,
            is_system_fallback=True
        )
```

### 三、 更新配置时的联动注意点

当用户调用 `PUT /api/user/model-configs/{id}/set-default` 或修改配置内容时：

1. **执行更新**：使用上述方案 A 一条 SQL 更新 DB。
2. **清除缓存**：立即执行 `await redis.delete(f"user:{user_id}:active_model_config")`。
3. **前端反馈**：接口直接返回当前激活的新配置基本信息（脱敏后的 API Key，例如 `sk-****abcd`），前端直接更新 UI 上的选中状态。

# 2. 改造 LLMClientManager

你的原代码中最值得保留的就是：

```python

```

因为你现在已经意识到一个关键问题：

> 不应该每创建一个 `ChatDeepSeek` 就重新创建 HTTP Client。

所以继续复用它。

```
app/core/llm/manager.py
from __future__ import annotations

import httpx
from langchain_core.language_models import BaseChatModel

from app.core.config import settings
from app.core.llm.factory import LLMFactory


class LLMClientManager:
    """
    LLM 客户端生命周期管理器。

    职责：
    1. 管理全局 httpx.AsyncClient
    2. 提供统一的 ChatModel 创建入口
    3. 不负责 LangGraph 生命周期
    """

    def __init__(self):
        self._async_client: httpx.AsyncClient | None = None
        self._factory: LLMFactory | None = None

    async def startup(self):
        if self._async_client is not None and not self._async_client.is_closed:
            return

        self._async_client = httpx.AsyncClient(
            limits=httpx.Limits(
                max_keepalive_connections=50,
                max_connections=200,
                keepalive_expiry=30.0,
            ),
            timeout=httpx.Timeout(
                connect=10.0,
                read=120.0,
                write=10.0,
                pool=10.0,
            ),
        )

        self._factory = LLMFactory(
            http_async_client=self._async_client,
        )

    async def shutdown(self):
        if self._async_client is not None:
            if not self._async_client.is_closed:
                await self._async_client.aclose()

        self._async_client = None
        self._factory = None

    def get_model(
        self,
        provider: str,
        *,
        api_key: str | None = None,
        base_url: str | None = None,
        model_name: str | None = None,
    ) -> BaseChatModel:

        if self._factory is None:
            raise RuntimeError(
                "LLMClientManager has not been started. "
                "Call startup() first."
            )

        return self._factory.create(
            provider=provider,
            api_key=api_key,
            base_url=base_url,
            model_name=model_name,
        )


llm_client_manager = LLMClientManager()
```

# 3. 真正的 Provider Factory

```
app/core/llm/factory.py
from __future__ import annotations

from typing import Any

import httpx
from langchain_core.language_models import BaseChatModel
from langchain_deepseek import ChatDeepSeek
from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic
from langchain_ollama import ChatOllama

from app.core.config import settings
from app.core.llm.providers import LLMProvider


class LLMFactory:

    def __init__(
        self,
        http_async_client: httpx.AsyncClient,
    ):
        self._http_async_client = http_async_client

    def create(
        self,
        provider: str,
        *,
        api_key: str | None = None,
        base_url: str | None = None,
        model_name: str | None = None,
    ) -> BaseChatModel:

        try:
            provider_enum = LLMProvider(provider)
        except ValueError:
            raise ValueError(
                f"Unsupported LLM provider: {provider}"
            )

        factory = {
            LLMProvider.DEEPSEEK: self._create_deepseek,
            LLMProvider.OPENAI: self._create_openai,
            LLMProvider.ANTHROPIC: self._create_anthropic,
            LLMProvider.OLLAMA: self._create_ollama,
        }.get(provider_enum)

        if factory is None:
            raise ValueError(
                f"Provider {provider} is not implemented"
            )

        return factory(
            api_key=api_key,
            base_url=base_url,
            model_name=model_name,
        )

    def _create_deepseek(
        self,
        *,
        api_key: str | None,
        base_url: str | None,
        model_name: str | None,
    ) -> ChatDeepSeek:

        return ChatDeepSeek(
            model_name=model_name or settings.model_name,
            api_key=api_key or settings.api_key,
            base_url=base_url or settings.base_url,
            http_async_client=self._http_async_client,
        )

    def _create_openai(
        self,
        *,
        api_key: str | None,
        base_url: str | None,
        model_name: str | None,
    ) -> ChatOpenAI:

        return ChatOpenAI(
            model=model_name or settings.openai_model_name,
            api_key=api_key or settings.openai_api_key,
            base_url=base_url or settings.openai_base_url,
            http_async_client=self._http_async_client,
        )

    def _create_anthropic(
        self,
        *,
        api_key: str | None,
        base_url: str | None,
        model_name: str | None,
    ) -> ChatAnthropic:

        return ChatAnthropic(
            model=model_name or settings.anthropic_model_name,
            api_key=api_key or settings.anthropic_api_key,
            base_url=base_url or settings.anthropic_base_url,
            http_async_client=self._http_async_client,
        )

    def _create_ollama(
        self,
        *,
        api_key: str | None,
        base_url: str | None,
        model_name: str | None,
    ) -> ChatOllama:

        return ChatOllama(
            model=model_name or settings.ollama_model_name,
            base_url=base_url or settings.ollama_base_url,
        )
```

这里有一个很重要的设计：

```python
self._http_async_client
```

仍然只有一个。

所以：

```text
                    AsyncClient
                        │
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
    ChatDeepSeek   ChatOpenAI   ChatAnthropic
```

多个 ChatModel 可以共享 HTTP 连接池。

# 7. 但这里有一个很重要的坑：不要把 `AsyncClient` 理解成“所有 Provider 都一定能共享”

这个地方我建议你注意。

例如：

```python

    http_async_client=client

```

通常可以共享同一个 `httpx.AsyncClient`。

但 Provider-specific client 的 API 可能还有：

```text

Anthropic
```

各自不同的 HTTP transport / headers / timeout / proxy / authentication 行为。

因此你的抽象应该是：


而**不要设计成**：

```text

       ↓
必须共享同一个 HTTP client
```

也就是说，共享连接池是优化手段，而不是架构约束。
