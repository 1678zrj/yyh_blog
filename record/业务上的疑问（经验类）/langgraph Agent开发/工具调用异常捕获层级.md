### 问：我在学习langchain、langgraph Agent开发，当前遇到的一个问题是工具函数执行时发生异常，当然要进行异常捕获，这个异常捕获是在工具函数中进行，还是在执行工具调用的节点中统一进行？

最佳实践是**分层处理（两层结合）**，而不是非此即彼：**业务层面的预期异常在工具函数内部捕获并转化为语义提示；系统层面的意外异常在工具节点中统一兜底**。



### 第一层：工具函数内部捕获（面向业务，赋能 Agent 自愈）

当错误属于**业务逻辑异常**或**用户输入引起的错误**时，应在工具函数内部捕获。



**原因**：

Agent 具备自我修正（Self-Correction）能力。如果工具直接抛出未捕获异常导致程序崩溃，Agent 无法感知发生的事情；如果工具捕获后返回**人类/模型可读的提示信息**，这个信息会作为 `ToolMessage` 的内容返回给大模型，模型便能据此调整参数并重新尝试。



Python

```
from langchain_core.tools import tool

@tool
def calculate_growth_rate(current: float, previous: float) -> str:
    """计算两个数值的增长率"""
    try:
        if previous == 0:
            return "错误：基准值（previous）不能为 0，无法计算增长率。请检查输入参数。"
        rate = (current - previous) / previous * 100
        return f"增长率为: {rate:.2f}%"
    except TypeError as e:
        # 参数类型转换失败等预期错误
        return f"参数类型错误: {str(e)}，请确保传入合法的数值。"
```

*适合场景*：



- 参数校验失败（如日期格式不符、ID 格式错误）。
- 业务资源不存在（如「未查找到用户张三，请确认姓名拼写」）。
- 权限校验或范围超界。

### 第二层：工具节点统一捕获（面向系统，保障 Graph 健壮性）

无论单个工具写得多严密，代码依然可能抛出意料之外的未处理异常（如网络突然超时、依赖库底层崩溃、OOM 等）。若不在节点层统一兜底，整个 LangGraph 状态图会直接中断崩溃。



在 LangGraph 中，官方推荐使用内置的 `ToolNode`，它提供了开箱即用的 `handle_tool_errors` 参数。



Python

```
from langgraph.prebuilt import ToolNode

# 方式 1：直接开启默认兜底（会将异常转换为通用 ToolMessage 错误内容返回给模型）
tool_node = ToolNode(tools=[calculate_growth_rate], handle_tool_errors=True)

# 方式 2：使用自定义兜底函数，统一规范错误格式
def custom_error_handler(e: Exception) -> str:
    # 可以在这里记录日志 / 告警监控
    # logger.error(f"Tool execution failed: {e}")
    return f"工具执行发生底层故障：{str(e)}。请尝试使用其他工具或向用户报告该问题。"

tool_node = ToolNode(
    tools=[calculate_growth_rate], 
    handle_tool_errors=custom_error_handler
)
```

如果使用自定义函数节点执行工具（而非 prebuilt `ToolNode`），做法是在执行循环中做 `try...except`，构造一个 `ToolMessage(content=..., status="error")` 写入状态，确保图状态能够正常流转到下一个节点。



### 职责划分与决策参考

| **维度**     | **工具函数内部处理**                       | **工具节点统一处理**                       |
| ------------ | ------------------------------------------ | ------------------------------------------ |
| **主要定位** | 业务提示与引导重试                         | 全局安全兜底与服务高可用                   |
| **错误类型** | 预期内异常（找不到资源、除以零、校验失败） | 未预期异常（网络断开、系统崩溃、底层 Bug） |
| **返回内容** | 针对具体业务的指导文本（让 LLM 修正参数）  | 通用的系统故障提示或降级通知               |
| **副作用**   | 适合针对单工具记录业务日志                 | 适合统一接入 Sentry、Prometheus 等工程监控 |

### 不应吞掉异常的例外场景

如果遇到**致命系统级错误**（如数据库主库宕机、API Key 无效/欠费、严重鉴权失败），**不应该**让工具或节点吞掉错误后继续丢给大模型猜测重试。这会导致大模型反复陷入死循环调用。



针对这类错误，应在工具节点抛出自定义系统异常，或者在 Graph 中通过条件边（Conditional Edge）将流程直接路由到**人工介入（Human-in-the-loop）\**或\**系统报警分支**中断执行。

### 这种在工具调用函数内部捕获的异常，status到底是success还是error呢？（PS：不要考虑langgraph自带的ToolNode等机制，这样过程很不透明）

在语义、模型理解和工程规范上，**应当赋值为 `status="error"`**。



虽然在 Python 代码层面，工具函数用 `try...except` 吞掉了异常并正常 `return` 了一个字符串（没有造成程序崩溃），但对于 Agent 而言，这次工具调用**在业务上是失败的**。



### 为什么要标记为 `error` 而不是 `success`？

#### 1. 触发大模型的底层纠错机制（核心原因）

不同大模型厂商对 Tool 调用的协议支持不同。以 **Anthropic (Claude)** 为例：



- 其底层 API 的 `tool_result` 原生包含一个参数：`"is_error": true/false`。
- 当你构造 `ToolMessage(..., status="error")` 时，LangChain 的底层适配器会将它直接映射为 Claude API 的 `"is_error": true`。
- **效果差异**：
  - **如果标为 `success`**：模型会认为这是工具正常产出的数据。面对某些指令遵从性稍弱的模型，它甚至可能把“参数类型错误……”当成真实的用户业务数据输出给下游。
  - **如果标为 `error`**：模型在底层协议上明确接收到了“执行失败”的信号，会更稳定地触发反思与自愈逻辑（例如：“参数填错了，我需要换一个合法值重试”）。

#### 2. 可观测性与指标统计（Observability）

如果把包含错误提示的字符串标为 `success`，在接入链路追踪（如 LangSmith、OpenTelemetry 或自定义日志）时，该次调用的追踪状态会显示为 **200 OK / Success**。这会导致工具调用的成功率指标虚高，掩盖模型频繁传错参数的真实问题。



### 脱离 ToolNode 黑盒：透明的手写实现方案

如果在工具函数内部直接 `return f"参数类型错误: ..."`，外部执行工具的代码拿到的只是一个普通的 `str`，外部无法直观知道这个返回值到底代表“成功”还是“失败”（除非去做字符串匹配 `if "错误" in result:`，这极不优雅）。



要让整个执行过程透明、可控，推荐以下两种模式：



#### 方案 A：工具抛出 `ToolException`，手写执行循环捕获并打标（最推荐）

利用 LangChain 的 `ToolException`。工具函数内部识别到参数不合法时，不直接 `return` 假成功文本，而是抛出 `ToolException`；外部手写的节点捕获它，并明确写入 `status="error"`：



Python

```
from langchain_core.messages import ToolMessage
from langchain_core.tools import ToolException, tool

# 1. 定义工具：出现预期内错误，抛出 ToolException
@tool
def calculate_growth_rate(current: float, previous: float) -> str:
    """计算两个数值的增长率"""
    if previous == 0:
        # 抛出异常，携带指导模型自愈的提示
        raise ToolException("基准值 previous 不能为 0，无法计算增长率，请检查参数。")
    return f"增长率为: {((current - previous) / previous * 100):.2f}%"

# 2. 完全透明的手写工具执行节点（不依赖 ToolNode）
def custom_tool_executor_node(state):
    last_message = state["messages"][-1]
    tool_messages = []
    
    # 模拟工具字典
    tools_by_name = {"calculate_growth_rate": calculate_growth_rate}

    for tool_call in last_message.tool_calls:
        tool_name = tool_call["name"]
        tool_args = tool_call["args"]
        call_id = tool_call["id"]
        
        target_tool = tools_by_name[tool_name]
        
        try:
            # 正常执行
            result = target_tool.invoke(tool_args)
            tool_messages.append(
                ToolMessage(
                    content=str(result),
                    tool_call_id=call_id,
                    status="success"  # 正常成功
                )
            )
        except ToolException as e:
            # 捕获预期内的业务/参数异常 -> 标记为 error，内容给模型看
            tool_messages.append(
                ToolMessage(
                    content=f"工具执行失败: {str(e)}",
                    tool_call_id=call_id,
                    status="error"    # 明确打上 error 标记
                )
            )
        except Exception as e:
            # 捕获意料之外的系统级故障
            tool_messages.append(
                ToolMessage(
                    content=f"系统发生未知异常: {str(e)}",
                    tool_call_id=call_id,
                    status="error"
                )
            )
            
    return {"messages": tool_messages}
```

#### 方案 B：工具返回结构化对象

如果坚持在工具函数内部捕获所有异常且绝不 `raise`，工具函数就不应该只返回纯文本，而应返回一个包含状态标识的结构体（例如字典）：



Python

```
@tool
def calculate_growth_rate(current: float, previous: float) -> dict:
    """计算两个数值的增长率"""
    try:
        if previous == 0:

        return {"ok": True, "msg": f"增长率为: {rate:.2f}%"}
    except TypeError as e:
        return {"ok": False, "msg": f"参数类型错误: {str(e)}"}
```

无论代码在何处捕获，原则始终一致：**只要这次调用没有拿到预期的业务结果、需要模型重新审视并修正行为，对应的 `ToolMessage.status` 就应该明确赋予 `"error"`。**

### 问：所以我总结一下，工具函数内部异常统一在工具函数内部捕获，然后统一转化成对应的异常抛到节点层。这样一来的话对于多种多样的工具函数也可以针对性地捕获异常了。而只在节点中统一捕获异常几乎无法针对性地进行处理.

你的总结**完全准确，直击痛点**。这正是构建工业级 Agent 时标准的“异常归一化（Exception Normalization）”设计模式。



如果不把异常捕获下沉到工具内部，节点层将面临严重的架构缺陷；而通过这种分层设计，系统能获得以下三个核心优势：



### 1. 领域上下文与错误转译（Domain Translation）

只有工具函数自己最清楚内部依赖库抛出的底层异常意味着什么：



- 工具内部知道 `requests.exceptions.HTTPError: 404` 意味着“未找到该资源，请检查 ID”；
- 工具内部知道 `KeyError: 'price'` 意味着“返回数据缺少价格字段，接口暂时无法提供该信息”；
- 工具内部知道 `ZeroDivisionError` 意味着“分母参数不能为 0”。

如果工具直接把原始异常甩给节点，节点层如果想针对性处理，就必须引入 `requests`、`psycopg2`、`pydantic` 等所有工具的底层依赖，导致**节点与具体工具的实现产生严重强耦合**。



### 2. 充当防腐层（Anti-Corruption Layer）

工具函数捕获底层各色各样的原生异常后，将其转译并统一抛出为 **`ToolException`**（或自定义的 `AgentRecoverableError`），此时工具函数充当了防腐层：



- **输入到工具**：各底层库千奇百怪的错误（SocketTimeout、JSONDecodeError、SQLSyntaxError 等）；
- **输出到节点**：统一归一化的异常对象，且带有**专门写给大模型看的纠错引导文本**。

### 3. 节点层专注编排与错误分类（Control Flow）

节点层不再需要关心某个工具具体用了什么库，它只需要做两件事：



Plaintext

```
               ┌───────────────────────────────┐
               │         Tool Function         │
               │  捕获各类底层库异常 (SQL/HTTP/...) │
               └──────────────┬────────────────┘
                              │
                    抛出分类明确的异常
                    (Normalize Exceptions)
                              │
               ┌──────────────▼────────────────┐
               │           Node Layer          │
               └──────────────┬────────────────┘
                              │
            ┌─────────────────┴─────────────────┐
            ▼                                   ▼
    [ToolException]                     [System/Fatal Error]
   (业务可自愈错误)                      (系统级不可恢复故障)
            │                                   │
  写入 ToolMessage(status="error")        终止流程 / 报警 / 
  交由 LLM 自行纠错重试                     路由到人工干预
```

- **遇到 `ToolException`（可恢复）**：节点将其包装为 `ToolMessage(content=str(e), status="error")`，安全放行给 LLM，让模型根据转译后的语义尝试自我修正；
- **遇到未归一化的其他异常（系统级故障）**：说明发生了不可预期的系统崩溃（如内存耗尽、核心凭据失效），节点可以选择直接熔断或路由到告警分支，防止 LLM 在死循环中盲目重试。

你的理解正是 Agent 系统实现“高内聚、低耦合”的标准实践。
