### 问：当前的问题是我要实现学生选课记录，选课记录表有学生id和课程id的唯一性约束，那么为了防止重复选课，我在业务层的代码里是选择先检测是否有记录，有的话抛出异常，还是不检测，而是捕获数据库数据重复插入时的异常，然后抛出异常呢？

在 FastAPI/SQLAlchemy 开发中，**捕获数据库数据重复插入时的异常（结合数据库唯一约束）是正确且最佳的做法**。



单独使用“先检测后插入（Check-Then-Insert）”在实际生产环境中是**不可靠**的。



## 为什么“先检测后插入”不可靠？

### 1. 竞态条件（Race Condition / 并发漏洞）

假设有两个请求（比如用户双击了选课按钮，或者高并发选课）：



```
请求 A (选课) ─────────► SELECT (无记录) ─────────► INSERT ──► 成功
请求 B (并发) ────► SELECT (无记录) ───────────────► INSERT ──► 崩溃 / 报错！
```

1. **请求 A** 和 **请求 B** 几乎同时到达。
2. 两个请求都执行了 `SELECT` 查询，数据库都返回“该学生未选此课”。
3. 两个请求都认为可以选课，随后**同时执行 `INSERT`**。
4. 其中一个插入成功，另一个被数据库唯一约束拦截并抛出异常。

**结论**：即使写了“先检测”，你**依然必须**捕获数据库的异常。既然如此，前面的 `SELECT` 检测在防护重复提交上就显得多余了。



### 2. 数据库开销

“先检测后插入”每次都会多产生一次 `SELECT` 数据库查询网络交互（RTT）。而直接依赖数据库唯一索引（Unique Constraint），不仅保证了**原子性**，还能减少一半的查询开销。



## 你当前代码的问题与重构建议

你的代码整体结构（Router -> Service -> CRUD）很规范，但在处理 `IntegrityError` 时有一个潜在隐患：



Python

```
# 隐患代码：
if "Duplicate entry" in str(e.orig):
```

`"Duplicate entry"` 是 **MySQL 专属**的报错提示字符串。如果后续更换数据库（如 PostgreSQL 的 error code 是 `23505`，SQLite 提示 `UNIQUE constraint failed`），这段代码就会失效，直接触发下面的 `400 BAD_REQUEST`。



### 优雅重构方案

#### 方案 A：在 Service 中通过数据库错误码判断（简易改进）

如果你使用的是 MySQL，可以通过错误码 `1062`（Duplicate Entry）来判断，或者直接根据逻辑将 `IntegrityError` 默认为唯一约束冲突：



Python

```
from sqlalchemy.exc import IntegrityError
from fastapi import HTTPException, status

class EnrollmentService:

    async def register_enrollment(
        self,
        enrollment_in: EnrollmentCreate,
        student_id: int
    ) -> Enrollment:
        # 1. 检查课程是否存在（这是必要的，因为外键或业务逻辑）
        existing_course = await course_crud.get_course_by_id(self.db, enrollment_in.course_id)
        if not existing_course:
            raise HTTPException(
                status_code=status.HTTP_404_NOT_FOUND,
                detail=f"课程ID {enrollment_in.course_id} 不存在"
            )

        enrollment_data = enrollment_in.model_dump()
        enrollment_data["student_id"] = student_id

        # 2. 直接插入，依靠数据库原子约束
        try:
            new_enrollment = await enrollment_crud.create_enrollment(self.db, enrollment_data)
            await self.db.commit()
            return new_enrollment
        except IntegrityError as e:
            await self.db.rollback()
            
            # 方式 1：检查通用或特定数据库错误码（以 PyMySQL/MySQLdb 为例，错误码 1062 代表重复键）
            orig_error = getattr(e, "orig", None)
            # pymysql 的 orig.args[0] 通常是错误码
            if orig_error and hasattr(orig_error, "args") and orig_error.args[0] == 1062:
                raise HTTPException(
                    status_code=status.HTTP_409_CONFLICT,
                    detail="您已选过该课程，请勿重复选课"
                )
            
            # 方式 2：如果在该接口下 IntegrityError 绝大多数情况都是唯一键冲突，可以直接返回 409
            raise HTTPException(
                status_code=status.HTTP_409_CONFLICT,
                detail="选课冲突或已被选过"
            )
```

#### 方案 B：解耦服务层（进阶架构）

在更标准的后端架构中， Service 层不应该直接 raise FastAPI 的 `HTTPException`（这会导致 Service 层与 API 框架强绑定，不利于单元测试）。



可以定义业务异常，并利用 FastAPI 的 `exception_handler` 统一拦截：



Python

```
# 1. app/core/exceptions.py (定义业务异常)
class DuplicateEnrollmentException(Exception):
    def __init__(self, message: str = "请勿重复选课"):
        self.message = message

# 2. app/main.py (全局捕获)
@app.exception_handler(DuplicateEnrollmentException)
async def duplicate_enrollment_handler(request: Request, exc: DuplicateEnrollmentException):
    return JSONResponse(
        status_code=status.HTTP_409_CONFLICT,
        content={"detail": exc.message},
    )

# 3. Service 中抛出业务异常
except IntegrityError:
    await self.db.rollback()
    raise DuplicateEnrollmentException()
```

## 总结

1. **坚持捕获数据库异常**：这是防御高并发重复请求的底层安全网。
2. **避免字符串模糊匹配**：不要用 `in str(e.orig)` 判断错误类型，优先检查 `e.orig.args` 中的数据库标准 Error Code，或者在特定操作下默认将 `IntegrityError` 视作冲突（HTTP 409）。
3. **HTTP 状态码标准**：针对重复数据冲突，返回 `409 CONFLICT` 比 `400 BAD REQUEST` 更符合 RESTful API 规范。
