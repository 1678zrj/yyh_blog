## 核心 SQL 与 SQLModel 实现

对应正确的原生 SQL 应该是：

```
SELECT user.id, user.username, user.real_name, enrollment.score
FROM user
JOIN enrollment ON user.id = enrollment.student_id

```

在 SQLModel / SQLAlchemy 中，结合 `AsyncSession` 的完整写法如下：

### 1. 修改 CRUD 层码

Python

```
from sqlmodel.ext.asyncio.session import AsyncSession
from sqlmodel import select
from app.models.table import Enrollment, User

class EnrollmentCrud:

    async def create_enrollment(self, db: AsyncSession, enrollment_data_dict: dict) -> Enrollment:
        enrollment = Enrollment(**enrollment_data_dict)
        db.add(enrollment)
        await db.flush()
        return enrollment

    async def get_course_students(self, db: AsyncSession, course_id: int):
        """
        查询指定课程的所有学生信息及对应成绩
        """
        # 1. 构建 select 查询语句
        statement = (
            select(
                User.id,
                User.username,
                User.real_name,
                Enrollment.score
            )
            .join(Enrollment, User.id == Enrollment.student_id)  # 连接 user 和 enrollment
            .where(Enrollment.course_id == course_id)            # 过滤课程 ID
        )

        # 2. 异步执行查询
        result = await db.exec(statement)

        # 3. 返回全部匹配行（每行是一个元组 (id, username, real_name, score)）
        return result.all()

enrollment_crud = EnrollmentCrud()

### 问：嗯，我想了解这个select 查询语句是否是性能比较好的连接查询语句

**是的，在 ORM 和 SQL 架构层面，你写的这句查询已经达到了极高的性能。**



这种写法的优秀之处在于，它避开了初学者使用 ORM 时最容易落入的“性能坑”，同时也非常符合数据库的执行效率要求。



## 为什么说它的性能非常好？

### 1. 字段投影（Projection）避开了 ORM 实例化开销

你没有写 `select(User, Enrollment)` 去查整个模型，而是精细地指定了需要的字段：

```
select(User.id, User.username, User.real_name, Enrollment.score)
```



- **网络带宽更小**：只从数据库传递 4 个列的数据，不会传输 `password_hash`、`created_at` 等大字段或无关字段。
- **内存与 CPU 消耗极低**：SQLAlchemy 不需要为每一行结果创建 Python 的 `User` 和 `Enrollment` 类对象实例，直接返回轻量级的数据库元组（Row），解析速度极快。

### 2. 使用标准的 INNER JOIN 与条件过滤

SQLModel 中的 `.join()` 默认会编译为原生的 `INNER JOIN`，搭配 `.where(Enrollment.course_id == course_id)`，数据库可以在内联接的同时快速利用索引完成过滤，不会产生笛卡尔积或大表全扫描。



## 真正的性能瓶颈：你的索引设置存在一个小问题！

虽然 SQL 语句本身性能极佳，但**决定数据库查询速度上限的往往是索引**。



看一眼你之前定义的 `Enrollment` 表：



Python

```
# 你现在的定义：
__table_args__ = (UniqueConstraint("student_id", "course_id", name="uq_student_course"),)
id: int | None = Field(default=None, primary_key=True)
student_id: int = Field(foreign_key="user.id")
course_id: int = Field(foreign_key="course.id")
```

这里隐藏着一个数据库索引的最左前缀原则（Leftmost Prefix Rule）陷阱：



1. 复合唯一约束 `("student_id", "course_id")` 会自动创建一个复合索引。
2. 因为 `student_id` 放在前面，这个索引只对 `WHERE student_id = ?` 或 `WHERE student_id = ? AND course_id = ?` 生效。
3. 当你执行 `WHERE course_id = ?` 时，数据库**无法高效利用**这个以 `student_id` 开头的复合索引，从而可能触发 `enrollment` 表的**全表扫描**！

### 🛠️ 优化建议

要让这句查询真正达到毫秒级响应，建议对 `Enrollment` 模型的字段或索引进行调整（二选一）：



#### 方案 A：调整复合唯一约束的列顺序（推荐）

将最常作为查询过滤条件的 `course_id` 放在复合约束的前面：



Python

```
class Enrollment(SQLModel, table=True):
    __tablename__ = "enrollment"
    # 将 course_id 调整到第一位
    __table_args__ = (UniqueConstraint("course_id", "student_id", name="uq_course_student"),)
    ...
```

#### 方案 B：直接给 `course_id` 显式添加索引

如果你经常需要单独按 `course_id` 查询选课记录：



Python

```
class Enrollment(SQLModel, table=True):
    __tablename__ = "enrollment"
    __table_args__ = (UniqueConstraint("student_id", "course_id", name="uq_student_course"),)
    
    id: int | None = Field(default=None, primary_key=True)
    student_id: int = Field(foreign_key="user.id")
    # 显式添加 index=True
    course_id: int = Field(foreign_key="course.id", index=True)
```

## 总结

- **代码写法**：十分满分！字段精简、没有 ORM 冗余开销。
- **数据库执行**：只要保证 `enrollment.course_id` 拥有有效索引，这句 SQL 就算在百万级数据量下执行也能保持在毫秒级。

### 问:很好，但我疑惑的是像这种crud层的多表连接查询的结果只能在service层进行组装再返回吗？企业级的FastAPI + SQLModel项目是怎么做的？

你问到了问题的关键！在实际的企业级开发中，**绝对不会像上一段代码那样用 `row[0]`, `row[1]` 去硬编码按索引组装**，因为这样非常脆弱，一旦 SQL 调整了字段顺序，代码立刻会静默报错或赋值混乱。



企业级 FastAPI + SQLModel 项目在处理这类多表查询时，主要有 **两种主流且非常优雅的做法**：



### 方案一：使用 `.mappings()` + Pydantic 自动转换（推荐用于高性能/定制投影查询）

如果你只需要查询部分字段（只挑几个列），你可以利用 SQLAlchemy/SQLModel 提供的 `.mappings()` 方法。它会将查询结果自动转换为**键值对字典（RowMapping）**，字段名就是字典的 Key。



配合 Pydantic 的 `model_validate`（或 FastAPI 的 `response_model`），**行数据会自动按字段名填充到 Schema 中**，不需要你写一行手动赋值代码。



#### 1. CRUD 层：使用 `.mappings()`

Python

```
# app/crud/enrollment.py
from sqlmodel import select
from sqlmodel.ext.asyncio.session import AsyncSession
from app.models.table import Enrollment, User

class EnrollmentCRUD:
    async def get_students_by_course_id(self, db: AsyncSession, course_id: int):
        statement = (
            select(
                User.id,
                User.username,
                User.real_name,
                Enrollment.score,
            )
            .join(Enrollment, User.id == Enrollment.student_id)
            .where(Enrollment.course_id == course_id)
        )
        result = await db.exec(statement)
        # 🌟 关键：使用 .mappings()，返回类似 [{'id': 1, 'username': '...', 'score': 90}, ...] 的迭代对象
        return result.mappings().all()
```

#### 2. Service 层：直接一行代码/零组装

Python

```
# app/services/enrollment.py
from app.schemas.enrollment import CourseStudentRead

class EnrollmentService:
    async def get_course_students(self, db: AsyncSession, course_id: int) -> list[CourseStudentRead]:
        rows = await enrollment_crud.get_students_by_course_id(db, course_id)
        
        # 🌟 自动匹配字段名赋值！不需要 row[0], row[1]
        return [CourseStudentRead.model_validate(row) for row in rows]
```

甚至你如果不写 Service 的转换，直接把 `rows` 丢给 FastAPI 路由，**FastAPI 也会根据 `response_model=list[CourseStudentRead]` 自动完成映射！**



### 方案二：利用 SQLModel 的 `Relationship` + 预加载（推荐用于面向对象/标准 ORM 模式）

在企业级项目中，如果表之间有明确的关联关系，通常会在 Model 中配置 `Relationship`。这样，你根本不需要手动写 `.join()`，直接查 `Enrollment` 对象并**预加载（Eager Loading）** `User` 即可。



#### 1. Model 层：定义 Relationship

Python

```
# app/models/table.py

class Enrollment(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    student_id: int = Field(foreign_key="user.id")
    course_id: int = Field(foreign_key="course.id")
    score: float | None = None

    # 🌟 定义与 User 的关系
    student: User = Relationship()

class User(SQLModel, table=True):
    id: int | None = Field(default=None, primary_key=True)
    username: str
    real_name: str
    ...
```

#### 2. Schema 层：定义嵌套 Schema

Python

```
# app/schemas/enrollment.py
from pydantic import BaseModel, ConfigDict
from app.schemas.user import UserRead  # 包含 id, username, real_name 等

class CourseEnrollmentRead(BaseModel):
    id: int
    score: float | None
    student: UserRead  # 🌟 直接嵌套 User 的 Schema

    model_config = ConfigDict(from_attributes=True)
```

#### 3. CRUD 层：使用 `selectinload` 防范 N+1 查询问题

Python

```
# app/crud/enrollment.py
from sqlalchemy.orm import selectinload
from sqlmodel import select

class EnrollmentCRUD:
    async def get_enrollments_by_course(self, db: AsyncSession, course_id: int):
        statement = (
            select(Enrollment)
            .where(Enrollment.course_id == course_id)
            .options(selectinload(Enrollment.student)) # 🌟 预加载关联的 student 数据
        )
        result = await db.exec(statement)
        return result.all()  # 返回的是 list[Enrollment]，里面 Enrollment.student 已自动加载
```

#### 4. Service 层与 API 层：全自动映射

此时在 Service 层你只需要：



Python

```

    async def get_course_students(self, db: AsyncSession, course_id: int):

```

API 层定义了 `response_model=list[CourseEnrollmentRead]` 后，FastAPI 会递归帮你把 `Enrollment.student` 序列化成响应 JSON，**一行组装代码都不用写**。



### 企业级项目对于“数据组装”的职责划分共识

在大型企业级 FastAPI 项目中：



1. **CRUD 层**：
   - **职责**：只负责与 DB 交互，返回 ORM 模型对象、字典映射（`mappings()`）或标量值。
   - **返回类型**：`Enrollment` / `RowMapping` / `tuple`（绝不直接在 CRUD 里实例化响应 DTO/Schema）。
2. **Service 层**：
   - **职责**：处理业务逻辑（计算、校验、调用第三方服务、组合多个 CRUD 的结果）。
   - **转换逻辑**：如果只是简单的 DB 数据 -> API 输出，Service 层**直接传递**对象/映射给 API 即可；只有当**包含复杂的业务计算/数据清洗**时，Service 层才会做数据重新拼装。
3. **API / Serialization 层（FastAPI 自动完成）**：
   - **职责**：基于 Pydantic 的 `from_attributes=True`，FastAPI 路由在 `return` 时会依据 `response_model` **自动做过滤、类型校验和 JSON 转换**。

### 总结对比

| **方式**                           | **适用场景**                               | **优点**                                         | **缺点**                                         |
| ---------------------------------- | ------------------------------------------ | ------------------------------------------------ | ------------------------------------------------ |
| **`.mappings()` + DTO (方案一)**   | 大表多字段，只查 2~3 个字段的轻量查询/报表 | **性能极致**，内存占用最小，写 SQL 灵活          | 需手动维护 Projection 字段                       |
| **`Relationship` 预加载 (方案二)** | 标准领域模型查询，需要完整的实体对象关系   | **代码最干净**，面向对象，FastAPI 自动化程度最高 | 如果表字段极其庞大且只查一两个字段时略有性能开销 |

在实际开发中，推荐**以方案二为主**，遇到需要极致性能优化或多表复杂聚合计算时**辅以方案一**。

### 问：使用方案一的话crud层不用写返回类型提示了吗

**必须要写（而且强烈建议写）！**



在企业级 FastAPI 项目中，**所有函数的入参和返回值都应该显式标注类型提示（Type Hints）**。这不仅是为了代码规范，更是为了：



1. **IDE 智能补全**：写 Service 层代码时，IDE 知道 CRUD 返回的是什么。
2. **静态代码检查**：`mypy` 或 `pyright` 能帮你及时发现类型不匹配的 Bug。
3. **团队协作**：其他人不用点进你的函数体内看代码，只看函数签名就知道返回了什么结构。

### `.mappings().all()` 的标准类型提示怎么写？

SQLAlchemy / SQLModel 的 `.mappings().all()` 返回的是一个包含 **`RowMapping`** 对象的列表/序列。`RowMapping` 是 SQLAlchemy 提供的一种**只读字典对象**，它的行为完全像 `dict[str, Any]`。



你有以下两种最常用的标注方式：



#### 方式一：使用 SQLAlchemy 原生的 `RowMapping`（最精确，推荐 🌟）

Python

```
from collections.abc import Sequence  # Python 3.9+ 推荐，低版本从 typing 导入
from sqlalchemy.engine import RowMapping
from sqlmodel import select
from sqlmodel.ext.asyncio.session import AsyncSession
from app.models.table import Enrollment, User

class EnrollmentCRUD:

    async def get_students_by_course_id(
        self, db: AsyncSession, course_id: int
    ) -> Sequence[RowMapping]:  # 🌟 显式标注返回 Sequence[RowMapping]
        statement = (
            select(
                User.id,
                User.username,
                User.real_name,
                Enrollment.score,
            )
            .join(Enrollment, User.id == Enrollment.student_id)
            .where(Enrollment.course_id == course_id)
        )
        result = await db.exec(statement)
        return result.mappings().all()
```

#### 方式二：使用通用字典映射类型 `Sequence[Mapping[str, Any]]`（更通用）

如果你不想导入 SQLAlchemy 特有的 `RowMapping`，也可以使用 Python 标准库 `typing.Mapping`：



Python

```
from collections.abc import Sequence, Mapping
from typing import Any
from sqlmodel import select
from sqlmodel.ext.asyncio.session import AsyncSession

class EnrollmentCRUD:

    async def get_students_by_course_id(
        self, db: AsyncSession, course_id: int
    ) -> Sequence[Mapping[str, Any]]:  # 🌟 表示返回一组字典/映射结构的列表
        statement = ...
        result = await db.exec(statement)
        return result.mappings().all()
```

### Service 层调用时，类型也是完美契合的

有了上述的类型提示后，Service 层的处理会变得非常优雅：



Python

```
from collections.abc import Sequence
from sqlmodel.ext.asyncio.session import AsyncSession
from app.crud.enrollment import enrollment_crud
from app.schemas.enrollment import CourseStudentRead

class EnrollmentService:

    async def get_course_students(
        self, db: AsyncSession, course_id: int
    ) -> list[CourseStudentRead]:
        # IDE 能自动识别出 rows 的类型是 Sequence[RowMapping]
        rows = await enrollment_crud.get_students_by_course_id(db, course_id)

        # Pydantic 能够完美解析 RowMapping 对象
        return [CourseStudentRead.model_validate(row) for row in rows]
```

### 总结

- 不要因为使用 `.mappings()` 就放弃类型标注。
- 推荐导入 `from sqlalchemy.engine import RowMapping`，并将 CRUD 返回值标注为 **`Sequence[RowMapping]`**。
- 这样从 **CRUD (Sequence[RowMapping]) -> Service -> API (list[CourseStudentRead])**，整个调用链条的类型都是 100% 封闭且安全的。

### 问：嗯，在当前连接查询的基础上能否加上分页功能？

当然可以！在企业级开发中，分页几乎是所有列表类 API 的标配。

实现高效的分页通常包含两个要素：

1. **当前页的数据列表（`items`）**：使用 SQL 的 `LIMIT` 和 `OFFSET` 控制。
2. **符合条件的总记录数（`total`）**：使用 `func.count()` 统计，方便前端计算总页数。

以下是结合 **API -> Service -> CRUD** 三层架构以及 **`.mappings()` + 泛型 Pydantic 分页 Schema** 的标准企业级实现方案：

首先在公共 Schema 中定义一个**通用泛型分页响应类**（其他任何列表 API 都能复用）：

class PageResponse(BaseModel, Generic[T]):
    """通用分页响应结构"""
    total: int          # 总记录数
    page: int           # 当前页码
    size: int           # 每页条数
    items: list[T]      # 数据列表

```

### 2. CRUD 层：增加查询 count 和 limit/offset (`app/crud/enrollment.py`)

在 CRUD 层中，编写**计算总数**和**带偏移量的查询**两个操作：

```python
from collections.abc import Sequence
from sqlalchemy.engine import RowMapping
from sqlmodel import select, func
from sqlmodel.ext.asyncio.session import AsyncSession
from app.models.base import Enrollment, User


class EnrollmentCRUD:

    async def get_students_by_course_id(
            self,
            db: AsyncSession,
            course_id: int,
            page: int = 1,
            size: int = 10
    ) -> tuple[int, Sequence[RowMapping]]:
        """
        分页查询指定课程的学生列表，返回 (total, rows)
        """
        # 1. 基础连接与过滤条件
        base_query = (
            select(
                User.id,
                User.username,
                User.real_name,
                Enrollment.score,
            )
            .join(Enrollment, User.id == Enrollment.student_id)
            .where(Enrollment.course_id == course_id)
        )

        # 2. 查询符合条件的总记录数
        count_stmt = (
            select(func.count())
            .select_from(User)
            .join(Enrollment, User.id == Enrollment.student_id)
            .where(Enrollment.course_id == course_id)
        )
        total = (await db.exec(count_stmt)).one()

        # 3. 添加 offset 和 limit 获取当前页数据
        offset = (page - 1) * size
        paged_stmt = base_query.offset(offset).limit(size)

        result = await db.exec(paged_stmt)
        rows = result.mappings().all()

        return total, rows


enrollment_crud = EnrollmentCRUD()

```

我们逐一解答：



## 1. 为什么要有 `.select_from(User)`？对应的 SQL 是什么？

### 为什么需要它？

在 SQLModel 中，当你写 `select(User)` 时，SQLModel 能从参数 `User` 中**自动推导出** `FROM user`。



但当你写 `select(func.count())` 时，括号里只有聚合函数 `func.count()`，并没有指定具体的表模型。如果紧接着直接写 `.join(Enrollment, ...)`，ORM 就会困惑：“**你要以哪张表作为主体（FROM 谁）去 Join Enrollment？**”



所以必须显式加上 `.select_from(User)`，告诉 ORM：**“以 User 表为起点发起的查询，去连接 Enrollment 表，并统计总数。”**



### 对应的原生 SQL 语句

这段 Python 代码在数据库后台编译出的**标准 SQL**如下：



SQL

```
SELECT count(*) AS count_1 
FROM user 
JOIN enrollment ON user.id = enrollment.student_id 
WHERE enrollment.course_id = :course_id_1;
```

### 💡 性能优化的“小彩蛋”

既然谈到了 SQL，顺便提示一个企业级小细节：



在统计“某门课选课人数”时，如果 `enrollment` 表里的 `student_id` 都是有效的外键（即不存在悬空记录），**其实根本不需要 JOIN `user` 表**！



你可以把 `count_stmt` 简化成：



Python

```
count_stmt = (
    select(func.count())
    .select_from(Enrollment)
    .where(Enrollment.course_id == course_id)
)
```

**对应的 SQL**：



SQL

```
SELECT count(*) FROM enrollment WHERE course_id = :course_id_1;
```

少做一次多表 `JOIN`，在海量数据下的**查询速度会明显提升**！



## 2. `total` 是直接返回 `int` 吗？需要做类型转换吗？

**不需要做任何类型转换，它直接就是一个 Python 的 `int` 类型！**



### 为什么是 `int`？

1. **`db.exec(...)` 的机制**：当你的 `select(...)` 里面只有单一字段（比如 `func.count()`，而不是多个列或多个 Model）时，SQLModel 的 `exec()` 会自动返回一个 **`ScalarResult`（标量结果集）**，意思是它知道这个查询返回的是“单列数据”。
2. **`.one()` 的作用**：在 `ScalarResult` 上调用 `.one()`，它会直接提取第一行第一列的标量值（而不是返回一个 Row 元组或字典）。

数据库驱程序（如 `asyncpg` 或 `aiomysql`）在读取到 `COUNT(*)` 的结果时，会自动将其解析并映射为 Python 原生的 `int` 对象（例如 `45`）。



如果你在 IDE 里把鼠标悬停在 `total` 上，或者打印它的类型：



Python

```
total = (await db.exec(count_stmt)).one()
print(type(total))  # 输出: <class 'int'>
```

你可以直接把它用在需要整数的任何地方（例如传给 Pydantic 的 `PageResponse`）。

虽然写在一个函数里看起来“省事”，但从架构设计和长远维护来看，**拆分**在多个维度上都更胜一筹。

## 为什么拆分成两个函数更好？

### 1. 遵循单一职责与高复用性（SRP）

CRUD 层最核心的定位是提供**原子的数据库操作**。

* `get_students_by_course_id` 专门负责拿**列表数据**。
* `count_students_by_course_id` 专门负责拿**总数**。

**实际场景**：如果未来有一个新需求——“在课程详情页仅显示当前报名人数”，或者“退课前检查这门课是否还有学生”，你就可以直接复用 `count_students_by_course_id`，而不需要再去调那个同时查了数据列表的带参函数。

### 2. 数据库参数与业务参数解耦

* **CRUD 层**：应该使用标准的数据库概念 `offset`（偏移量）和 `limit`（限制条数）。
* **Service / API 层**：处理 UI 交互概念 `page`（页码）和 `size`（每页条数）。

在 Service 层把 `page` / `size` 换算成 `offset` / `limit` 后传给 CRUD，职责分工会更加严密。

### 3. 单元测试更简单

当 CRUD 函数粒度变小后，针对单个 SQL 逻辑编写 `pytest` 测试用例会变得极其纯粹，更容易 Mock 和断言。

### 1. CRUD 层 (`app/crud/enrollment.py`)

CRUD 层只提供最纯粹的原子接口：

```python
from collections.abc import Sequence
from sqlalchemy.engine import RowMapping
from sqlmodel import select, func
from sqlmodel.ext.asyncio.session import AsyncSession
from app.models.base import Enrollment, User


class EnrollmentCRUD:

    async def count_students_by_course_id(
            self, db: AsyncSession, course_id: int
    ) -> int:
        """只查某门课的总学生数"""
        statement = (
            select(func.count())
            .select_from(Enrollment)
            .where(Enrollment.course_id == course_id)
        )
        return (await db.exec(statement)).one()

    async def get_students_by_course_id(
            self, db: AsyncSession, course_id: int, offset: int = 0, limit: int = 10
    ) -> Sequence[RowMapping]:
        """只查某门课的学生列表（带 offset/limit）"""
        statement = (
            select(
                User.id,
                User.username,
                User.real_name,
                Enrollment.score,
            )
            .join(Enrollment, User.id == Enrollment.student_id)
            .where(Enrollment.course_id == course_id)
            .offset(offset)
            .limit(limit)
        )
        result = await db.exec(statement)
        return result.mappings().all()


enrollment_crud = EnrollmentCRUD()

```

## ⚠️ 初学者常踩的一个异步小陷阱

你可能会想：“既然 Service 层要调用两次数据库，我能不能用 `asyncio.gather()` 让他们并发（并行）执行来提速呢？”

```python
# ❌ 注意：在 SQLAlchemy 中这样写会报错！
total, rows = await asyncio.gather(
    enrollment_crud.count_students_by_course_id(db, course_id),
    enrollment_crud.get_students_by_course_id(db, course_id, offset, size)
)

```

**原因**：SQLAlchemy 的同一个 `AsyncSession`（数据库连接句柄）在同一时间**只允许处理一个 SQL 查询**，它不是并发安全的。

因此，像在 Service 层中示范的那样，使用 `await` 顺序执行两次查询才是**完全正确且稳健**的做法。

### 问：我不太理解你说的”在同一时间只允许处理一个 SQL 查询，它不是并发安全的“，因为在微观层面两个SQL查询请求并不是同时发过来的，难道你的意思是说相对于数据库查询数据的时间，同一个AsyncSession实例还没查完上一个SQL查询，下一个SQL查询就发过来了吗

你的理解**非常准确**！你完全猜中了这个问题的底层本质。



你说的“在微观层面，上一个 SQL 查询还没查完，下一个 SQL 查询就发过去了”，正是导致报错的根本原因。



## 结合时间线看：微观上发生了什么？

当你写下 `asyncio.gather(count_query, list_query)` 时，Python 的协程事件循环（Event Loop）会按照以下毫秒级的时间线执行：



Plaintext

```
时间 (ms)     事件循环 (Event Loop)                                数据库 TCP 连接 (Socket)
─────────────────────────────────────────────────────────────────────────────────────────────────
 0 ms   ───> 启动 count 查询任务
 1 ms   ───> 向 Socket 发送 SQL: "SELECT COUNT(*)..." ───> [数据发送给数据库]
 2 ms   ───> 遇到 `await`，等待数据库返回。
             事件循环不闲着，立刻切换到 list 查询任务！
 3 ms   ───> list 查询试图向【同一个 Socket】写入 SQL...  ───> 💥 碰撞！报错触发！
```

### 为什么会碰撞？

1. **数据库协议的限制**：

   PostgreSQL 和 MySQL 的单条 TCP 网络连接，本质上是**单工对讲机模式**（Request-Response 协议）。规则是：**发一条请求 -> 必须等数据库把结果发完并接收完毕 -> 才能发下一条请求**。

   它不支持在同一个 TCP 连接上，上一个查询还在“等结果”时，就把下一个查询推过去。

2. **`AsyncSession` 的状态锁**：

   SQLAlchemy 的 `AsyncSession` 底层绑定了一个数据库连接。当它处于 `await` 等待数据库响应的“挂起”状态时，它的内部状态是 **Busy（忙碌）**。

   如果此时另一个协程强行调用同一个 `AsyncSession` 发送新的 SQL，底层驱动（如 `asyncpg` 或 `aiomysql`）就会直接抛出类似下面的异常：

   > `InterfaceError: cannot perform operation: another operation is in progress`
   >
   > （无法执行操作：另一个操作正在进行中）

## 既然是异步，那为什么不能并发？

初学者最容易产生的一个误区是：**“异步 (Async) = 并发 (Parallelism)”**。



- **异步 (Async) 的真正优势**是：当你在 `await` 等待数据库返回的这 2 毫秒内，CPU 可以去**处理其他用户的 HTTP 请求**，而不是死等。
- **但对于同一个用户请求中的同一个 AsyncSession**，它所占用的那一条数据库连接在这一瞬间**只能做一件事**。

## 总结与建议

1. **顺序 `await` 是最稳健的**：

   在 Service 层按顺序写：

   Python

   ```
   total = await enrollment_crud.count_students_by_course_id(db, course_id)
   rows = await enrollment_crud.get_students_by_course_id(db, course_id, offset, limit)
   ```

   在局域网/同机房环境中，这两个查询连续执行通常只需要 **1 ~ 3 毫秒**，性能完全足够，而且代码极其安全。

2. **如果真的非常想并行查怎么办？**

   除非是耗时极长的复杂统计，否则一般不需要。如果非要并行，你需要为两个查询**分别开两个独立的 `AsyncSession`**（即占用连接池里的两条 TCP 连接），但这会增加连接池的开销，在分页场景下属于“得不偿失”。

### 问：我感觉异步机制有些神奇，当你在一个异步函数中await两个异步函数，它就会按照代码顺序串行执行，但是当用asyncio.gather注册到事件循环中，就相当于并发执行了。还有就是异步函数本就被注册到事件循环，它内部调用的异步函数为什么还可以被注册到事件循环呢

你的直觉非常敏锐！你提的这两个问题，可以说是所有 Python 开发者从“用异步”走向“懂异步”时最核心的两个壁垒。



要彻底解开这个迷思，我们需要区分两个关键概念：**协程对象（Coroutine）** 与 **任务（Task）**。



## 疑问一：为什么 `await` 是串行，而 `gather` 是并发？

### 1. 单纯写 `await` 的本质：把掌控权“让出”给下一个步骤

当你写下：



Python

```
await func_A()
await func_B()
```

- **发生了什么**：你是在告诉事件循环：“**暂停当前这个函数**，去执行 `func_A`。**只有当 `func_A` 完全执行完毕**，你才能回到我这里，接着执行下一行的 `func_B`。”
- **为什么是串行**：因为你用 `await` 显式锁住了当前函数的执行顺序。`func_B` 根本还没有被触发。
- **那它的“异步”体现在哪**：在等待 `func_A` 完成的这期间（比如它在等数据库 IO），**当前这个函数确实挂起了**，事件循环可以跑去处理**其他用户发来的 HTTP 请求**，但你这个函数内部的 `func_B` 还是要排队。

### 2. `asyncio.gather` 的本质：把多个任务同时投递到调度队列

当你写下：



Python

```
await asyncio.gather(func_A(), func_B())
```

- **发生了什么**：`asyncio.gather` 在后台偷偷做了一件事——它把 `func_A()` 和 `func_B()` 包装成了两个独立的 **Task（任务）**，并**同时注册到了事件循环的待办清单里**。
- **为什么是并发**：
  1. 事件循环开始跑 `func_A`，遇到 `func_A` 的网络等待（IO 阻塞），`func_A` 挂起并交出 CPU 执行权。
  2. 事件循环一看待办清单：“诶？`func_B` 也在队列里，而且正闲着呢！”
  3. 事件循环立刻切去执行 `func_B`。
  4. 两个函数在 IO 等待期交替推进，这就是**并发**。

## 疑问二：父函数已经在事件循环中了，子异步函数是怎么被“注册”的？

答案是：**单纯调用异步函数，根本不会注册到事件循环中！**



看下面这段代码：



Python

```
async def child():
    print("hello")

async def parent():
    c = child()  # 🌟 注意这一行！
```

当执行到 `c = child()` 时，**`child()` 里面的代码一行都不会执行**。它只是在内存里创建了一个“极其轻量”的**协程对象（Coroutine Object）**，就像生成器（Generator）一样，它只是一个待执行的“剧本”。



那么，这个“子剧本”是如何被事件循环执行的呢？有两种方式：



### 方式 A：通过 `await` 接入（栈式调用）

当你写 `await child()` 时：

它并没有在事件循环里创建一个**新的并行任务**。它只是把当前运行的任务（Parent）的控制指针，**向下推入了子函数（Child）的执行栈**。它们俩其实属于**同一个 Task**，事件循环依然只在管理这个主 Task。



### 方式 B：通过 `create_task` 注册（创建并行任务）

当你写 `task = asyncio.create_task(child())` 时（`gather` 内部就是这么干的）：

它向事件循环的动态队列里**追加了一个新的任务节点**。

事件循环本质上是一个 `while True` 的死循环，里面维护着一个任务队列。**正在运行的任务，完全有权限在运行过程中往这个队列里 `push` 新的任务**。



## 形象比喻：厨师（事件循环）与菜谱

我们可以把整个过程想象成一个**厨师在厨房做菜**：



- **事件循环（Event Loop）** = **厨师**（只有一个人，单线程）。
- **Task（任务）** = 厨师手里贴在墙上的**点菜单**。
- **Coroutine（协程）** = 菜谱上的**步骤**。

### 1. `await func_A()` 之后 `await func_B()`

厨师看当前点菜单（Parent）：



1. 菜谱第一步：煮水（`await func_A`）。厨师把水烧上，因为必须等水烧开，厨师此时可以抬起头看**墙上其他桌的订单**（处理其他用户的 HTTP 请求）。
2. 水烧开了，厨师回到这张订单，看菜谱第二步：切肉（`await func_B`）。厨师开始切肉。

> **结果**：这两个步骤对于这张订单来说，是严格按顺序来的。

### 2. `asyncio.gather(func_A(), func_B())`

厨师看当前点菜单（Parent）：



1. 菜谱写着：把“煮水”和“切肉”拆成两张**新订单**（`Task A` 和 `Task B`）贴到墙上。
2. 厨师开始处理 `Task A`（煮水），把水烧上（IO 等待）。
3. 厨师**立刻看墙上的新订单**，看到了 `Task B`（切肉），趁着水还没开，立刻开始切肉！

> **结果**：两件事在一个厨师（单线程）手里同时推进了！

## 总结

1. **`async def`** 只是写了一份“菜谱”（Coroutine），调用它只是拿到菜谱，**不会自动运行**。
2. **`await`** 是“单线推进”——在当前任务里按顺序等待上一步完成，但等待期间**允许 CPU 去照顾别的 Task**。
3. **`asyncio.create_task` / `gather`** 是“多线开工”——把菜谱变成新的 Task 贴到事件循环的全局任务队列里，让事件循环能利用等待时间在它们之间**来回穿梭**。
