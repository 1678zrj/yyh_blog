### 问：FastAPI run命令如何设置启动的进程数

在使用 FastAPI 官方自带的 CLI 工具时，可以通过追加 **`--workers`** 参数来设置 `fastapi run` 启动的进程数（Worker 数量）。  

### 1. 基本命令  

Bash

```
fastapi run main.py --workers 4
```

*注：假设你的应用入口文件是 `main.py`，上述命令会启动 4 个工作进程来共同处理请求。*

### 2. 进程数应该设置多少？

进程数并不是越多越好，通常取决于你的服务器配置和业务类型。一个普遍的经验法则是：

- **计算密集型业务**（如复杂数据处理、图像渲染）：
  - **建议进程数** = `CPU 核心数`
- **I/O 密集型业务**（如大量数据库查询、读写文件、请求外部 API，这也是大多数 Web 应用的常态）：
  - **建议进程数** = `(CPU 核心数 × 2) + 1`

启动多进程后，底层服务器（Uvicorn）会自动将客户端的请求分发给空闲的进程，从而充分利用多核 CPU 的性能。

### 3. 需要注意的细节  

- **`fastapi dev` 模式不支持**：`--workers` 参数专门用于生产环境命令（`fastapi run`）。如果你使用的是开发环境命令 `fastapi dev`，为了支持代码热重载（Hot Reloading），它默认只会以单进程运行。  

- **容器化部署（Docker / K8s）中的流派**：

  - **单容器多进程**：如果你的服务器是一台配置很好的大机器（比如 8 核 16G），直接跑 `docker run`，可以在启动命令里加上 `--workers 8` 来榨干单机性能。  
  - **单容器单进程 + 外部伸缩**：如果你部署在 Kubernetes (K8s) 中，官方更推荐的最佳实践是**在容器内只跑 1 个进程**（不加 `--workers`），然后利用 K8s 的 `ReplicaSet`（副本机制）来横向扩缩容容器的数量。

- **老版本或替代方案**：`fastapi run` 是近期新版 FastAPI 加入的功能（底层调用 Uvicorn）。如果你需要更高级的进程管理（比如进程崩溃后自动重启、守护进程等），业界通常会配合 Gunicorn 使用：

  Bash

  ```sh
  gunicorn main:app -w 4 -k uvicorn.workers.UvicornWorker
  ```

### 问：按照你说的，现在连笔记本的CPU似乎核心数都很多

确实如此。现在的笔记本动辄 10 核、14 核甚至更多（特别是采用了“大小核”架构的 Intel 和 Apple M 系列芯片）。如果生搬硬套 `(核心数 × 2) + 1` 这个公式，算出来可能会有二三十个进程。

但在实际操作中，**真没必要在笔记本上开这么多进程**。以下是几个关键原因：

### 1. 内存与上下文切换的惩罚

在 Python 中，每个 Worker 都是一个独立的进程，拥有自己独立的内存空间。如果你在笔记本上启动 30 个进程，应用可能还没开始处理请求，几个 G 的内存就先被占满了。此外，CPU 在这几十个进程之间频繁进行上下文切换（Context Switch）所带来的开销，反而会拖垮整体的处理速度。

### 2. 数据库连接池的灾难

每个独立进程都会初始化自己的资源。尤其是在处理高并发的系统时（比如需要处理文件分片合并、或者涉及数据库悲观锁的逻辑），每个 Worker 都会建立自己的数据库连接池。

假设 1 个进程配置了 10 个连接，30 个进程就是 300 个连接。在本地测试时，这种数量级很容易直接把本地数据库的连接数打满，导致连接超时或拒绝服务。

### 3. 大小核调度的不可控性

现在的笔记本 CPU 往往是“性能核（P核）+ 能效核（E核）”。如果塞满几十个 Web 进程，操作系统可能会把一部分繁重的请求丢给算力较弱的能效核去处理，导致接口响应时间忽快忽慢，极不稳定。

### 真正的适用场景在哪？

那个计算公式真正适用的场景，是部署在诸如 A800 这类拥有大量同构计算核心、且配备海量内存的实验室服务器或生产级云主机上。在那类机器上，尽可能多地开启 Worker 才能真正“榨干”硬件算力。

### 笔记本上的最佳实践

如果你现在是在笔记本上进行开发或压测：

- **日常写代码**：直接用 `fastapi dev main.py`（单进程，支持热重载），专注于逻辑正确性。
- **本地模拟并发测试**：如果你想测试并发竞争状态，手动指定 **`--workers 4`** 或 **`--workers 8`** 就完全足够填满本地网络和磁盘 I/O 的吞吐量瓶颈了。

### 问：怎么在本地测试 FastAPI 接口在多进程下的并发性能，看看瓶颈在哪？

在本地压测并定位 FastAPI 应用的性能瓶颈，核心思路分为三步：**制造稳定的并发压力**、**监控系统资源表现**，以及**剖析代码执行耗时**。

我们可以通过以下标准流程来进行排查。



**1.以生产多进程模式启动应用：**关闭开发模式，模拟真实环境。

确保关闭所有的 Debug 模式和日志打印（控制台日志 I/O 非常拖慢性能），并以多进程启动：

Bash

```
fastapi run main.py --workers 4
```

**2.施加并发压力：**使用压测工具打满接口吞吐量。

对于单一接口的纯粹性能摸底，推荐使用 **`wrk`**（C 语言编写，极度轻量且性能极高）。

在另一个终端执行：

Bash

```
# 使用 4 个线程，保持 200 个并发连接，持续压测 30 秒
wrk -t4 -c200 -d30s http://127.0.0.1:8000/api/your-target-endpoint
```

*如果你的业务逻辑非常复杂（比如需要先登录拿 Token 再请求），可以使用 Python 编写的 **Locust** 来模拟真实用户操作路径。*

**3.监控硬件资源，初步定性瓶颈方向：**

在压测进行时，打开 `htop` 或系统的活动监视器，观察这 4 个 Python Worker 进程的状态：

- **CPU 跑满 (接近 100%)**：说明瓶颈在代码计算上（比如复杂的循环、序列化/反序列化）。
- **CPU 没跑满，但响应极慢**：说明程序在“等”。这通常是 I/O 瓶颈（等数据库返回、等文件读写完成、等外部 API 响应）。
- **内存飙升甚至 OOM**：说明存在内存泄漏，或者一次性把过大的数据（如超大文件或上万条记录）加载到了内存中。

**4.使用 py-spy 绘制火焰图，精准定位慢代码：**无需修改业务代码的性能剖析利器。

如果确认了是代码执行慢，可以使用 `py-spy` 这个非侵入式的 Python 性能分析工具。

Bash

```
pip install py-spy

# 找到其中一个 worker 进程的 PID，抓取 10 秒的执行采样并生成 SVG 火焰图
sudo py-spy record -o profile.svg --pid  --duration 10
```

用浏览器打开生成的 `profile.svg`，就能直观地看到哪个函数占用了最多的执行时间。



## FastAPI 常见的“隐形瓶颈”排查指南

结合 FastAPI 的异步特性和后端常见的业务场景，如果压测数据不理想，通常是以下几个重灾区：

### 1. 异步循环中混入了同步阻塞代码

这是 FastAPI 最常见的性能杀手。如果在被 `async def` 定义的路由中，调用了同步的 I/O 操作（例如 `time.sleep`、同步版本的 `requests.get`，或者没加异步驱动的传统 SQLAlchemy 查询），整个 Event Loop 就会被卡死，并发能力瞬间跌至谷底。

### 2. 数据库锁与连接池耗尽

在高并发场景下，如果仅仅关注 CPU 可能会被误导。例如，在处理多租户环境下的扣费或配额分配逻辑时，可能会使用**悲观锁**（`SELECT ... FOR UPDATE`）。因为悲观锁是能够完全阻止其它事务或线程读取当前数据的，在并发压测下，大量的请求会排队等待锁释放。此时 CPU 占用极低，但接口会大面积超时。

此外，如果没有合理配置 SQLAlchemy 等 ORM 的连接池大小（Pool Size）和溢出值（Max Overflow），压测瞬间打过来的几百个并发会直接报出 `QueuePool limit of size X reached` 错误。

### 3. I/O 密集型操作未解耦

在处理高频的磁盘操作时（比如高并发场景下的大文件分片上传与合并逻辑），如果让数据库会话（Session）与耗时的分片合并函数绑定在同一个执行上下文里，会导致数据库连接被长时间白白占用，从而拖垮整个应用的吞吐量。**将耗时的本地文件 I/O 与数据库交互逻辑解耦**，是提升此类接口并发能力的关键。

`py-spy` 生成的 SVG 文件是可交互的。在浏览器中打开它后，你需要牢记以下核心法则：

## 1. 怎么读这两条轴？

- **X 轴不是时间线，是“占用比例”（样本数）**：这是新手最容易误解的地方。X 轴是从左到右排列的采样快照汇总。如果一个函数块的宽度占了整个屏幕的 60%，就说明在压测期间，CPU 有 60% 的时间都在执行这个函数（及其子函数）。**结论：越宽，越耗时。**
- **Y 轴是调用栈（Call Stack）深度**：从下往上，反映了函数的调用层级关系。最底部通常是 `uvicorn.run` 或底层 `asyncio` 事件循环的调度代码。顺着方块往上找，越往上越接近你写的业务逻辑。最顶层的“塔尖”，就是 CPU 在被采样的那一瞬间真正正在执行的叶子函数。

> **不要被颜色欺骗**：很多人以为“越红的块代表越慢”。实际上，标准工具生成的火焰图颜色通常是根据模块名或函数名**随机哈希**生成的暖色调，仅仅是为了在视觉上区分相邻的方块。**判断性能唯一的标准就是方块的宽度。**

## 2. 抓内鬼：三大关键视觉特征

当你拿到一张火焰图时，用肉眼快速扫描以下三种形态：

### 特征一：寻找“平顶山”（Plateaus）—— 真正的 CPU 杀手

当你在最顶部看到一个**非常宽，且上方没有任何子函数**的矩形块时，这就是典型的“平顶山”。

这说明该函数本身在疯狂消耗 CPU，而不是因为它调用了别的慢函数。如果你在处理算法或数据，比如在执行手写的快速排序、归并排序，或者在处理大规模的数据库对象实体映射（ORM Mapping）、超大 JSON 的解析，相关的底层计算函数或 `session.commit` 往往会呈现出这种平顶山形态。

### 特征二：警惕“断层”阻塞—— 异步 Event Loop 的毒药

在 FastAPI 这种基于异步事件循环的框架里，最怕的不是算得慢，而是“干等”。

如果在你的业务逻辑上方，突然出现了一个极宽的底层同步 I/O 函数（如来自 `socket` 的 `recv`，或者传统的同步文件读写操作），并且这个块霸占了极大的宽度，这说明**整个底层线程都在卡着等 I/O 响应**。这种“毒药”操作会直接挂起 Python 的事件循环，导致并发能力跌至单线程水平。

### 特征三：深不见底的“高塔”—— 框架开销

你会看到有些调用栈非常高，像一座座细长的塔。这在使用了复杂路由或拦截器的 Web 框架中很常见。

如果这座塔**很高但是很窄**，说明调用链虽然长，但执行速度极快，不需要去管它。但如果这座塔**既高又宽**，你就需要从塔顶往下顺藤摸瓜，找到第一个属于你业务代码的方块，看看究竟是哪行代码触发了下方如此庞大的开销。

## 3. 高效交互技巧

因为这是一个 SVG 文件，你可以直接在浏览器里进行排查操作：

1. **悬浮（Hover）**：把鼠标移到任何一个可疑的宽块上，它会显示完整的函数名、所在文件路径、确切的行号以及精确的耗时百分比。
2. **点击（Click）放大**：如果你发现某个中间层函数很宽，直接点击它。整个视图会以该块为基准放大至 100% 宽度，隐藏掉其他无关的上下文，方便你专心排查这个分支内部的调用细节。点击左上角的 `Reset Zoom` 即可恢复全局视角。

### 问：如果火焰图查出来是因为我调了一个第三方的同步慢库导致了 Event Loop 阻塞，在 FastAPI 里怎么优雅地用线程池把它异步化？

这是 FastAPI 开发中最经典的“踩坑”场景。由于 FastAPI 运行在单线程的事件循环（Event Loop）上，一旦遇到类似同步发请求、读写大文件，或者调用不支持异步的第三方老库（比如某些专有 SDK），整个主线程就会被挂起，并发能力直接瘫痪。

要把这类同步阻塞代码“优雅”地甩给后台去执行，你有三种层层递进的解法，你可以根据对资源的控制力度来选择。

### 1. 最符合 FastAPI 规范的做法：`run_in_threadpool`

FastAPI 官方底层（通过 Starlette）提供了一个非常轻量级的开箱即用工具。这也是在业务代码里最常见、代码侵入性最小的写法。

Python

```
from fastapi import FastAPI
from fastapi.concurrency import run_in_threadpool
import time

app = FastAPI()

def blocking_third_party_lib(data: str):
    # 模拟一个会卡死 2 秒的第三方同步调用
    time.sleep(2)
    return f"Processed: {data}"

@app.get("/process")
async def process_data(data: str):
    # 将同步函数连同参数一起塞进内置线程池
    # 当前 Event Loop 会挂起等待这个协程完成，但不会阻塞其他并发请求
    result = await run_in_threadpool(blocking_third_party_lib, data)
    return {"result": result}
```

### 2. 纯 Python 3.9+ 原生流派：`asyncio.to_thread`

如果你不想依赖框架特定的 API，更喜欢 Python 标准库原生的解决方案，从 Python 3.9 开始，官方提供了一个非常优雅的语法糖。它的底层逻辑和上面完全一样，都是使用了 `asyncio` 的默认 ThreadPoolExecutor。

Python

```
import asyncio
from fastapi import FastAPI

app = FastAPI()

@app.get("/process")
async def process_data(data: str):
    # 原生 Python 的标准写法
    result = await asyncio.to_thread(blocking_third_party_lib, data)
    return {"result": result}
```

### 3. “高玩”控制流：自定义线程池（防止资源耗尽）

前面两种方法使用的是系统默认的全局线程池。但在服务器环境（尤其是多租户或资源受限的容器内），如果突然涌入几千个并发请求，默认线程池可能会疯狂创建线程，导致上下文切换开销爆炸，甚至把内存吃光。

为了绝对的稳定性，你可以**自定义并全局复用一个 `ThreadPoolExecutor`**，将其最大线程数锁死。

Python

```
import asyncio
from concurrent.futures import ThreadPoolExecutor
from fastapi import FastAPI

app = FastAPI()

# 初始化一个全局线程池，明确限制最多只有 10 个 Worker 线程
# 即使有 1000 个请求过来，也最多只有 10 个在同时执行第三方库，其他的排队
thread_pool = ThreadPoolExecutor(max_workers=10)

@app.get("/process")
async def process_data(data: str):
    loop = asyncio.get_running_loop()
    # 手动将任务丢进我们自定义的线程池中执行
    result = await loop.run_in_executor(thread_pool, blocking_third_party_lib, data)
    return {"result": result}
```

## ⚠️ 核心原理解析：别忘了全局解释器锁（GIL）

既然把同步任务扔进了线程池，那就必须直面 Python 底层运行机制的拷问：**这东西到底能不能真正并发？** 答案取决于那个第三方库在干什么。

- **如果它是 I/O 密集型（如网络请求、数据库操作、文件读写）**：

  完美！Python 的底层机制会在执行 I/O 阻塞操作时**主动释放 GIL**。这意味着即使是多个线程，也能在等待 I/O 时真正实现并发。你的 Event Loop 被彻底解放了。

- **如果它是 C/C++ 编写的底层科学计算库（如 NumPy、OpenCV 处理矩阵）**：

  非常棒！这类优秀的库在进入底层 C 代码执行繁重计算时，也会**手动释放 GIL**，所以放入线程池依然可以发挥多核优势。

- **如果它是纯 Python 写的计算密集型代码（如纯 Python 写的复杂循环、大量字符串处理）**：

  这里会翻车。由于 GIL 的存在，多个线程在执行纯 Python 字节码时无法并行。把它扔进线程池，虽然能勉强保住 Event Loop 不卡死，但整体计算速度依然是单核水平，甚至会因为线程切换的开销变得更慢。
