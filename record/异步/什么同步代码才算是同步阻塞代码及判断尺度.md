### 问：我正在学习FastAPI应用开发，基本所有的异步函数都是异步。然后我就有一点比较疑惑，即使是异步开发方式，大部分的代码其实都是同步代码，只是大多数同步代码的执行事件足够短，不至于阻塞异步事件循环。而对于那种同步阻塞代码，则会阻塞异步事件循环，需要将这类放到线程池中去执行。前面都是我的理解，不知道是否恰当。而基于这个理解，我的疑惑是同步代码中耗时多长的代码才能够算是同步阻塞代码，需要放到线程池去执行，这个判断的标准是什么？

你的理解非常准确。在基于 `asyncio` 的事件循环中，两个 `await` 之间的所有代码都是在主线程上同步串行执行的。所谓的“异步应用”，本质上就是由无数个“极短的同步代码切片”加上“非阻塞的 I/O 挂起点”组成的。



判断一段同步代码是否属于“阻塞代码”、是否需要放入线程池，主要依据**耗时量化指标**与**任务属性分类**。



### 1. 耗时量化的时间基准

衡量是否阻塞，核心看它对事件循环吞吐量（RPS）**和**尾部延迟（P99）的影响：



| **耗时范围**          | **判定类别**               | **推荐处理方式**                  | **典型场景**                                        |
| --------------------- | -------------------------- | --------------------------------- | --------------------------------------------------- |
| **< 1 ms**            | **可忽略**（完全安全）     | 直接写在 `async def` 中           | 内存字典读写、小对象序列化、简单正则匹配            |
| **1 ms ~ 10 ms**      | **临界区**（视并发量而定） | 低并发可保留；高并发建议移出      | 中等大小 JSON 解析、简单 Pydantic 模型深度校验      |
| **10 ms ~ 50 ms**     | **轻度阻塞**               | 放入线程池（`run_in_threadpool`） | 本地小文件读取、单次密码哈希（如 bcrypt）           |
| **> 50 ms / 100 ms+** | **严重阻塞**               | 必须移出主线程（线程池或进程池）  | 同步 HTTP 请求（如 `requests`）、图片缩放、重型计算 |

> **官方参考标准**：Python 的 `asyncio` 调试模式（Debug Mode）默认将超过 **100 ms** 的同步执行标记为 `Slow callback` 并抛出警告。但在生产高并发 Web 服务中，通常建议将阈值收紧至 **5 ms ~ 10 ms**。

### 2. 定性判断标准

**标准一：是否涉及同步 I/O（零容忍原则）**



- **任何同步网络 I/O、数据库 I/O、磁盘 I/O** 无论当下测试有多快，都必须移出主事件循环。
- 原因在于 I/O 操作受网络抖动、磁盘拥堵影响极大，耗时不可控。一旦产生秒级超时，整个进程的所有其他并发请求都会被卡死。

**标准二：任务性质（CPU 密集 vs I/O 密集）**



- **同步 I/O 密集型 / 轻中度 CPU 密集型**（如 `requests.get`、bcrypt 加密、Pillow 图片轻量裁剪）：放入**线程池**执行。
- **重度 CPU 密集型**（如 Pandas 大数据分析、视频转码、复杂数学运算）：放入进程池（`ProcessPoolExecutor`）或独立的后台任务队列（如 Celery/ARQ），因为 Python 的 GIL 会导致多线程无法利用多核 CPU。

### 3. FastAPI 中的落地策略

- **直接使用 `def` 路由**：如果不确定第三方库是否支持异步（例如传统的 `requests` 或同步 ORM），直接将路由函数写为普通函数 `def`，FastAPI 会自动将其放入内置的 ThreadPool 中运行。
- **在 `async def` 中按需分发**：对于大部分异步、仅个别步骤耗时的情况，使用 `anyio.to_thread.run_sync` 或 `asyncio.to_thread` 局部卸载：

Python

```
import asyncio
from fastapi import FastAPI

app = FastAPI()

def heavy_cpu_or_sync_io():
    # 耗时 > 10ms 的同步操作
    ...

@app.get("/items")
async def read_items():
    # 局部丢进线程池，不阻塞事件循环
    result = await asyncio.to_thread(heavy_cpu_or_sync_io)
    return {"result": result}
```

### 问：在 FastAPI/asyncio 中有哪些工具和方法可以定位和监控阻塞事件循环的慢代码？

定位与监控 `asyncio` 事件循环中的阻塞代码，通常分为**开发调试、性能分析（Profiling）、生产环境监控**三个层级。



### 1. 开发阶段：内置 Debug 模式（开箱即用）

Python `asyncio` 原生提供了慢回调检测机制。当某个同步操作执行时间超过设定阈值时，会在日志中直接打印警告及触发位置。



**配置方式：**



Python

```
import asyncio
import logging
from fastapi import FastAPI

# 开启 logging 才能看到 debug 模式输出的 warning
logging.basicConfig(level=logging.WARNING)

app = FastAPI()

@app.on_event("startup")
async def enable_asyncio_debug():
    loop = asyncio.get_running_loop()
    loop.set_debug(True)
    # 将慢回调阈值从默认的 100ms 降低到 20ms（按需调整）
    loop.slow_callback_duration = 0.02
```

> **快捷环境变量**：也可以在启动应用前设置环境变量 `PYTHONASYNCIODEBUG=1` 直接全局开启。

**警告输出示例：**



Plaintext

```
WARNING:asyncio:Executing <Task pending ...> took 0.052 seconds
```

### 2. 定位阶段：非侵入式与异步专用 Profiler

#### py-spy（首选外部采样分析器）

`py-spy` 是用 Rust 编写的高性能采样分析器，无需修改代码，开销极低，可在生产或测试环境直接附加到正在运行的 FastAPI 进程：



- **实时查看卡住的线程/任务：**

  Bash

  ```
  py-spy top --pid <FASTAPI_PID>
  ```

- **一键输出火焰图（包含 C 扩展和 Python 堆栈）：**

  Bash

  ```
  py-spy record -o profile.svg --pid <FASTAPI_PID> --rate 100
  ```

- **实时打印当前堆栈快照（排查死锁或长时间卡住）：**

  Bash

  ```
  py-spy dump --pid <FASTAPI_PID>
  ```

#### yappi（支持 Context/Task 维度的 Profiler）

标准库的 `cProfile` 无法很好地跟踪协程上下文切换。`yappi` 专门支持 `asyncio`，可以统计每个协程维度的 Wall Time（真实耗时）和 CPU Time。



Python

```
import yappi

yappi.set_clock_type("wall") # 关注真实等待时间
yappi.start()

# 运行被测逻辑 ...

yappi.stop()
stats = yappi.get_func_stats()
stats.print_all()
```

### 3. 生产监控：度量事件循环延迟（Event Loop Lag）

在生产环境中，最直接反映事件循环是否被阻塞的指标是 **Event Loop Lag（循环延迟）**。



**核心原理**：后台定时提交一个空回调 `loop.call_later(0.1, check_lag)`。如果事件循环健康，回调应在 100ms 左右执行；如果被阻塞了 500ms，回调就会延迟到 600ms 后才执行，差值就是阻塞时长。



**轻量级监控实现示例：**

Python

```
import asyncio
import time
from fastapi import FastAPI

app = FastAPI()

async def monitor_event_loop_lag(interval: float = 0.1, alert_threshold: float = 0.05):
    loop = asyncio.get_running_loop()
    while True:
        start = time.perf_counter()
        await asyncio.sleep(interval)
        actual_delay = time.perf_counter() - start
        lag = actual_delay - interval
        
        if lag > alert_threshold:
            print(f"[ALERT] Event loop blocked! Lag: {lag * 1000:.2f} ms")
            # 生产环境中可在此处上报至 Prometheus / Sentry

@app.on_event("startup")
async def start_lag_monitor():
    asyncio.create_task(monitor_event_loop_lag())
```

### Python 各类操作耗时基准表

以下是现代 CPU（以 3.0GHz 左右单核性能）下典型 Python 操作的耗时量级与异步安全评估：



| **时间量级**                 | **典型操作**                                                 | **典型耗时**                                                 | **异步安全性与处理建议**                                     |
| ---------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 纳秒级  (< 1 µs)             | • 变量赋值 / 基础四则运算  • 字典查找 `dict[key]` / 列表索引 `list[i]`  • 普通函数调用与协程创建开销 | ~20 - 50 ns  ~30 - 80 ns  ~50 - 150 ns                       | **绝对安全**  属于常规语言执行开销，随意在 `async def` 中运行。 |
| 微秒级  (1 µs ~ 100 µs)      | • 字符串格式化（f-string）  • 短文本正则匹配（`re.match`）  • 小字典/列表推导式（< 100 项）  • 小 JSON（< 2 KB）解析（`orjson` / `json`）  • 简单 Pydantic 模型实例化与基础校验 | ~0.5 - 2 µs  ~2 - 10 µs  ~5 - 20 µs  ~5 - 30 µs  ~10 - 50 µs | **极高安全性**  常规 Web 业务代码的核心组成部分，通常无需干预。 |
| 亚毫秒级  (100 µs ~ 1 ms)    | • 中等 JSON（10 KB ~ 100 KB）序列化/反序列化  • 复杂/深层嵌套的 Pydantic 模型批量校验  • 内存中对 10,000 个基础对象排序  • 命中 OS PageCache 的本地小文件读取 | ~0.1 - 0.5 ms  ~0.2 - 0.8 ms  ~0.5 - 1.0 ms  ~0.1 - 0.5 ms   | **安全（低并发无感）**  超高并发（> 5,000 QPS）场景下，需注意这类代码累加产生的 CPU 瓶颈。 |
| 毫秒级  (1 ms ~ 50 ms)       | • 大型 JSON（> 1 MB）解析  • 本地磁盘未命中缓存的文件读取  • Pillow / OpenCV 进行图片缩放或简单滤镜  • Pandas 进行 10 万行数据的简单过滤与分组  • 单次密码哈希计算（如 `bcrypt` / `argon2`） | ~2 - 10 ms  ~5 - 20 ms  ~5 - 30 ms  ~10 - 50 ms  ~50 - 150 ms | **临界区 / 阻塞**  必须移出主事件循环：  • I/O 与轻计算 → `asyncio.to_thread`  • 纯 CPU 计算 → 视并发考虑进程池 |
| 秒级及以上  (> 50 ms ~ 数秒) | • 同步 HTTP 请求（`requests.get` / `urllib`）  • 同步数据库驱动查询（`psycopg2`、`pymysql`）  • 深度学习 CPU 推理（PyTorch / ONNX）  • 视频转码、PDF/Office 文档大批量生成 | ~50 ms - 2 s+  ~5 ms - 数秒  ~100 ms - 数秒  ~1 s - 30 s+    | **严重阻塞（绝对禁止）**  直接在 `async def` 中调用会导致整个服务假死：  • 改用异步库（`httpx`、`asyncpg`）  • 或分发到 Celery / 独立 Worker |

### 日常编码快速自检经验法则

- **无网络/磁盘/加密计算的纯内存逻辑**（对象拼装、字符串处理、字典操作），99% 的情况下单次耗时都在 **100 微秒以内**，直接写在 `async def` 中没有任何性能负担。
- **只要出现文件读写、密码哈希、外部系统调用**，无论当下测试耗时几毫秒，一律默认视为**阻塞操作**，使用异步版本驱动或放入线程池隔离。
