### 问：大模型应用开发，web后端开发也是一样的异常处理策略吗？主要经常要调用别人写好的Python包中的函数，不知道它里面有什么异常，没法针对性地捕获

是的，Web 后端开发的策略完全一致，甚至要求更加严苛。因为 Web 后端发生的每一个异常，最终都需要精准映射给前端（或客户端）对应的 **HTTP 状态码**（如 400 Bad Request、401 Unauthorized、404 Not Found、500 Internal Server Error）和 **业务错误信息**。

对于“调用第三方 Python 包时不知道里面有啥异常，无法针对性捕获”这个痛点，工业界有一套非常标准的应对机制和工程技巧。

## 一、 第三方包不知道会抛出什么异常，怎么办？

你不需要记住第三方库里的每一个具体异常，只需要掌握以下三个原则：

### 1. 利用第三方库的“顶级基类异常（Base Exception）”

几乎所有规范的 Python 开源库，在其内部定义异常时都遵循同一个设计模式：**继承自该库专有的顶级基类异常**。

你不需要去记几十个细分异常，只要捕获该库的**顶级基类**，就能在“不误伤其他代码”的前提下，精准锁定这个库抛出的所有问题。这比全局捕获 `Exception` 精准得多：

| **第三方库/场景**             | **顶级基类异常 (Base Exception)**      | **作用范围**                                               |
| ----------------------------- | -------------------------------------- | ---------------------------------------------------------- |
| **`requests`** (网络请求)     | `requests.exceptions.RequestException` | 包含 HTTP 超时、DNS 解析失败、连接拒绝等所有该库发起的错误 |
| **`httpx`** (异步网络)        | `httpx.HTTPError`                      | 包含所有 `httpx` 相关的网络错误                            |
| **`SQLAlchemy`** (ORM/数据库) | `sqlalchemy.exc.SQLAlchemyError`       | 包含数据库断开、SQL 语法错误、约束冲突等所有 DB 错误       |
| **`redis`** (缓存)            | `redis.exceptions.RedisError`          | 包含连接超时、Key 类型错误等所有 Redis 错误                |
| **`PyJWT`** (JWT 鉴权)        | `jwt.PyJWTError`                       | 包含 Token 过期、签名非法等所有鉴权错误                    |

只要写 `except requests.exceptions.RequestException:`，就能安全地只处理网络库的异常，而不会把你自己代码里的 `TypeError` 或 `ZeroDivisionError` 误吞掉。

### 2. 查看库的 `exceptions.py` 或利用 IDE

如果使用的是一个不太熟悉的第三方包，可以通过两种快捷方式找到它的异常体系：

- **查看源码**：在 IDE 里快捷键点进该包的根目录，寻找 `exceptions.py` 或 `errors.py` 文件。规范的包都会在这个文件里将所有异常列举得清清楚楚。
- **文档与类型提示**：查看该 package 的官方文档或函数 Docstring，绝大多数库会在文档的 `Raises` 部分说明该函数可能抛出的错误。

### 3. 防线隔离：异常转换（Exception Translation）

在 Web 后端的架构设计中，**服务层（Service Layer）不应该把第三方库的底层异常直接扔给控制层（Controller/Router）**。

标准做法是在调用第三方库的地方进行**捕获并转换**，将第三方异常包装成你自己定义的**自定义业务异常**：

Python

```
# 假设你在写一个支付服务，调用了第三方 SDK 
from payment_sdk.exceptions import PaymentBaseException # 第三方库的基类异常
from my_project.exceptions import PaymentGatewayError   # 自定义的业务异常

def process_user_payment(user_id: str, amount: float):
    try:
        payment_sdk.charge(user_id, amount)
    except PaymentBaseException as e:
        # 捕获第三方 SDK 的所有异常，转换为自定义的业务异常抛出
        logging.error(f"支付网关调用失败: {e}")
        raise PaymentGatewayError("第三方支付服务暂时不可用，请稍后再试") from e
```

## 二、 那 Web 后端的“全局异常捕获”究竟用在什么地方？

前面提到不能无脑用全局捕获，但 Web 后端**确实存在** `except Exception` 的场景，不过它只被允许放在系统的**最外层（中间件 / 全局异常处理器）**，作为“最后一道安全网”。

### Web 后端的两级防护体系

1. **第一层：业务代码内（精准捕获 & 业务转换）**

   在具体的路由函数或 Service 中，精准捕获已知异常（如用户不存在、密码错误、第三方库基类异常），并返回明确的 HTTP 400/404/502 状态码和提示。

2. **第二层：框架最外层（全局兜底中间件）**

   在 FastAPI / Django / Flask 框架的最外层设置全局异常处理函数（Global Exception Handler）。这里使用 `except Exception` 兜底。

   - **它的唯一职责**：如果业务代码里有程序员漏掉的未知 Bug（比如不小心写了 `1 / 0` 或是空指针），全局兜底会捕获它，**记录详细的日志和堆栈信息**，然后给前端返回一个统一的 `HTTP 500 Internal Server Error`，**防止敏感的服务器堆栈信息暴露给用户**，同时也保证了服务器进程不会因为这个局部 Bug 而崩溃崩溃挂掉。

### FastAPI 架构下的典型范例

Python

```
from fastapi import FastAPI, Request, status
from fastapi.responses import JSONResponse
import logging

app = FastAPI()

# ================= 1. 全局兜底处理器（最后一道安全网） =================
@app.exception_handler(Exception)
async def global_exception_handler(request: Request, exc: Exception):
    # 记录详细堆栈供工程师排查（内部可见）
    logging.critical(f"系统未捕获的严重异常: {exc}", exc_info=True)
    
    # 给外部用户统一返回干净的 500 响应，隐藏内部实现细节
    return JSONResponse(
        status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
        content={"code": "INTERNAL_ERROR", "message": "服务器内部错误，工程师正在紧急修复"}
    )

# ================= 2. 业务路由（精细化捕获） =================
@app.get("/users/{user_id}")
async def get_user_profile(user_id: int):
    try:
        # 假设 db_client 会抛出 sqlalchemy 相关的异常
        user = db_client.get_user(user_id)
        if not user:
            return JSONResponse(
                status_code=status.HTTP_404_NOT_FOUND,
                content={"code": "USER_NOT_FOUND", "message": "用户不存在"}
            )
        return user
    except SQLAlchemyError as e:
        # 精准捕获数据库基类异常
        logging.error(f"数据库查询失败: {e}")
        return JSONResponse(
            status_code=status.HTTP_503_SERVICE_UNAVAILABLE,
            content={"code": "DB_ERROR", "message": "数据库服务暂时不可用"}
        )
```

## 总结

无论是大模型应用还是传统 Web 后端，异常处理的逻辑逻辑是一脉相承的：

1. **不要用 `Exception` 处理业务**：业务层尽量捕获第三方库的**顶级基类异常**或具体异常。
2. **做层级转换**：将底层技术异常（如 SQL 异常、网络异常）转换为上层看得懂的**业务异常**或 **HTTP 状态码**。
3. **全局捕获只做安全兜底**：全局 `Exception` 捕获只放在框架最外层，只用来**记日志**和**挡住 500 报错的敏感堆栈**，绝对不用来做业务重试或逻辑分流。

### 问：请示范如何在 Web 后端（以 FastAPI 为例）设计并实现一套标准化的自定义业务异常体系与全局拦截响应。

在 FastAPI 中设计一套高可维护的异常体系，核心原则是将**业务领域错误**与**HTTP 协议细节**解耦。业务代码中只负责抛出带有明确语义的自定义业务异常，由框架最外层的全局处理器（Exception Handler）统一捕获并格式化为标准 JSON 输出。

一套标准的落地方案划分为四个关键步骤：

## 一、 定义统一的 API 错误响应格式

所有错误响应（无论是业务异常、参数校验失败还是系统崩塌）都遵循统一的 JSON 结构，避免前端处理异常时出现结构混乱。

JSON

```
{
  "code": 40001,
  "message": "用户余额不足",
  "details": {
    "current_balance": 50.0,
    "required": 100.0
  }
}
```

## 二、 构建自定义异常基类与衍生子类

创建一个继承自 Python 原生 `Exception` 的基类 `BusinessException`，再根据不同业务场景派生出具体的子类。

Python

```
# exceptions.py
from typing import Any, Dict, Optional
from fastapi import status

class BusinessException(Exception):
    """
    业务异常基类
    :param code: 自定义业务状态码 (如 40001)
    :param message: 返回给前端的提示信息
    :param status_code: HTTP 状态码 (默认为 400 BAD REQUEST)
    :param details: 额外的错误上下文数据
    """
    def __init__(
        self, 
        code: int, 
        message: str, 
        status_code: int = status.HTTP_400_BAD_REQUEST, 
        details: Optional[Dict[str, Any]] = None
    ):
        self.code = code
        self.message = message
        self.status_code = status_code
        self.details = details or {}
        super().__init__(self.message)

# ================= 预定义常见业务子异常 =================

class UserNotFoundException(BusinessException):
    def __init__(self, user_id: int):
        super().__init__(
            code=40401,
            message=f"ID 为 {user_id} 的用户不存在",
            status_code=status.HTTP_404_NOT_FOUND
        )

class InsufficientBalanceException(BusinessException):
    def __init__(self, current: float, required: float):
        super().__init__(
            code=40001,
            message="账户余额不足，请充值后再试",
            status_code=status.HTTP_400_BAD_REQUEST,
            details={"current_balance": current, "required": required}
        )

class ExternalServiceException(BusinessException):
    def __init__(self, service_name: str, raw_error: str):
        super().__init__(
            code=50201,
            message=f"调用上游服务【{service_name}】异常",
            status_code=status.HTTP_502_BAD_GATEWAY,
            details={"raw_error": raw_error}
        )
```

## 三、 全局拦截处理器（Interceptors / Handlers）

在 FastAPI 实例中注册三层拦截网，分别捕获：

1. **自定义业务异常**（业务已知问题）
2. **Pydantic 参数校验异常**（前端请求参数非法）
3. **未捕获的基类 Exception**（程序员写出的 Bug 或未预料到的系统故障）

Python

```
# handlers.py
import logging
from fastapi import FastAPI, Request, status
from fastapi.responses import JSONResponse
from fastapi.exceptions import RequestValidationError
from exceptions import BusinessException

def register_exception_handlers(app: FastAPI):
    
    # 1. 拦截自定义业务异常 (返回预定义的 HTTP 状态码和业务 Code)
    @app.exception_handler(BusinessException)
    async def business_exception_handler(request: Request, exc: BusinessException):
        logging.warning(
            f"业务异常被拦截: path={request.url.path} | code={exc.code} | msg={exc.message}"
        )
        return JSONResponse(
            status_code=exc.status_code,
            content={
                "code": exc.code,
                "message": exc.message,
                "details": exc.details
            }
        )

    # 2. 统一格式化 Pydantic 参数校验异常 (将默认的 422 格式重构为标准统一结构)
    @app.exception_handler(RequestValidationError)
    async def validation_exception_handler(request: Request, exc: RequestValidationError):
        # 提取字段校验错误的简要信息
        error_details = []
        for error in exc.errors():
            error_details.append({
                "field": " -> ".join([str(loc) for loc in error.get("loc", [])]),
                "msg": error.get("msg")
            })
            
        return JSONResponse(
            status_code=status.HTTP_400_BAD_REQUEST,
            content={
                "code": 40000,
                "message": "请求参数格式错误",
                "details": {"errors": error_details}
            }
        )

    # 3. 拦截未捕获的未知系统异常 (500 全局兜底)
    @app.exception_handler(Exception)
    async def global_unhandled_exception_handler(request: Request, exc: Exception):
        # 必须记录详细的堆栈日志（exc_info=True），以便排查 Bug
        logging.critical(
            f"未知未捕获系统异常: path={request.url.path} | error={exc}", 
            exc_info=True
        )
        
        # 隐藏敏感内部实现细节，给前端统一返回标准 500 结构
        return JSONResponse(
            status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
            content={
                "code": 50000,
                "message": "服务器内部错误，工程师正在排查中",
                "details": {}
            }
        )
```

## 四、 整合与实际应用示范

在应用主程序中使用注册好的异常处理器，并在路由/服务层直接抛出异常，可以看到代码变得极度精简且职责分离。

Python

```

from pydantic import BaseModel, Field
import requests

from exceptions import UserNotFoundException, InsufficientBalanceException, ExternalServiceException
from handlers import register_exception_handlers

app = FastAPI(title="标准化异常处理示例")

# 注册全局异常拦截器
register_exception_handlers(app)

# 模拟请求 Schema

    user_id: int = Field(..., description="用户ID")
    amount: float = Field(..., gt=0, description="转账金额必须大于零")

# 假数据
USERS_DB = {1: {"name": "Alice", "balance": 50.0}}

@app.post("/api/v1/transfer")
async def transfer_money(req: TransferRequest):
    # 1. 检查用户是否存在
    if req.user_id not in USERS_DB:
        raise UserNotFoundException(user_id=req.user_id)
        
    user = USERS_DB[req.user_id]
    
    # 2. 检查余额
    if user["balance"] < req.amount:
        raise InsufficientBalanceException(current=user["balance"], required=req.amount)
        
    # 3. 模拟调用第三方支付 API 并捕获第三方库基类异常
    try:
        # 假设此处调用支付网关失败
        raise requests.exceptions.Timeout("Connection timed out after 5.0s")
    except requests.exceptions.RequestException as e:
        # 捕获第三方 SDK 异常后，转化为业务自定义异常抛出
        raise ExternalServiceException(service_name="PaymentGateway", raw_error=str(e))

    return {"code": 20000, "message": "转账成功", "details": {}}

@app.get("/api/v1/bug")
async def trigger_bug():
    # 4. 模拟程序员不小心写出的意外代码 Bug

    return {"result": result}

### 这套设计的架构优势

- **业务代码高度干净**：在 Service 层不需要手动写任何 `JSONResponse`，只需要在校验不通过时 `raise MyException(...)` 即可，逻辑清晰流畅。
- **接口契约统一**：不论后端内部抛出什么错误，前端收到的 JSON 结构永远是固定的（`code`, `message`, `details`），极大地降低了前后端联调与拦截器的编写成本。
- **安全防泄露**：内部代码崩溃堆栈被日志系统记录，而外部只接收干净的 500 提示，切断了潜在的安全攻击面。

### 问：请示范如何在 FastAPI 中配合异常拦截器实现带有 TraceID 的日志链条追踪。

在 FastAPI 中实现带有 `TraceID` 的链路追踪，关键在于利用 Python 的 **`contextvars`（上下文变量）** 机制。

`contextvars` 能在协程（async/await）调度间隔离并传递变量。通过结合**中间件（Middleware）**、**日志过滤器（Logging Filter）** 和 **异常拦截器（Exception Handler）**，可以确保每个请求生成唯一的 `TraceID`，并在日志记录和异常响应中无缝串联。

## 一、 系统架构设计

链路追踪的运行流程如下：

Plaintext

```
[客户端请求] ──> (1. 中间件生成/提取 TraceID 并存入 ContextVar)
                     │
                     ├──> (2. 日志系统自动读取 ContextVar 打印 trace_id)
                     │
                     ├──> (3. 业务代码抛出异常)
                     │
                     └──> (4. 异常拦截器捕获异常，将 trace_id 写入日志与响应 Header/Body)
```

## 二、 完整可运行示范代码

包含 `ContextVar` 隔离、自定义日志 Filter、中间件和全局异常拦截器的完整方案：

Python

```
import uuid
import logging
from contextvars import ContextVar
from typing import Optional, Dict, Any

from fastapi import FastAPI, Request, status
from fastapi.responses import JSONResponse
from starlette.middleware.base import BaseHTTPMiddleware

# ================= 1. 定义 TraceID 上下文变量 =================
# ContextVar 用于在异步协程上下文中安全地传递 TraceID
trace_id_var: ContextVar[str] = ContextVar("trace_id", default="")

def get_trace_id() -> str:
    """获取当前请求的 TraceID"""
    return trace_id_var.get()


# ================= 2. 配置带 TraceID 的日志系统 =================
class TraceIDLogFilter(logging.Filter):
    """日志过滤器：自动将 ContextVar 中的 trace_id 注入日志记录"""
    def filter(self, record: logging.LogRecord) -> bool:
        record.trace_id = get_trace_id() or "N/A"
        return True

# 初始化 Logger 配置
logger = logging.getLogger("app_logger")
logger.setLevel(logging.INFO)

# 创建控制台 StreamHandler 并绑定 Filter 与 Formatter
console_handler = logging.StreamHandler()
console_handler.addFilter(TraceIDLogFilter())

# 格式化日志，输出格式中加入 [trace_id=%(trace_id)s]
log_formatter = logging.Formatter(
    fmt="[%(asctime)s] [%(levelname)s] [trace_id=%(trace_id)s] %(message)s",
    datefmt="%Y-%m-%d %H:%M:%S"
)
console_handler.setFormatter(log_formatter)
logger.addHandler(console_handler)


# ================= 3. 定义统一异常体系 =================
class BusinessException(Exception):
    def __init__(self, code: int, message: str, status_code: int = 400, details: Optional[Dict[str, Any]] = None):
        self.code = code
        self.message = message
        self.status_code = status_code
        self.details = details or {}
        super().__init__(self.message)


# ================= 4. TraceID 中间件 =================
class TraceIDMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        # 支持优先从上游网关（如 Nginx / APISIX）传递过来的 Header 获取
        trace_id = request.headers.get("X-Trace-ID") or str(uuid.uuid4()).replace("-", "")
        
        # 将 trace_id 绑定到当前协程上下文，并保存 token 用于后续重置
        token = trace_id_var.set(trace_id)
        
        try:
            response = await call_next(request)
            # 将 TraceID 写入响应头，方便前端/调用方对齐日志
            response.headers["X-Trace-ID"] = trace_id
            return response
        finally:
            # 请求结束后清理 contextvar，防止内存泄漏或上下文污染
            trace_id_var.reset(token)


# ================= 5. 构建 FastAPI 应用与注册拦截器 =================
app = FastAPI(title="TraceID 异常追踪示范")

# 注册 TraceID 中间件（最先执行）
app.add_middleware(TraceIDMiddleware)


# 自定义业务异常拦截器
@app.exception_handler(BusinessException)
async def business_exception_handler(request: Request, exc: BusinessException):
    current_trace_id = get_trace_id()
    
    # 日志会自动带上 trace_id
    logger.warning(f"业务报错: code={exc.code}, msg={exc.message}, path={request.url.path}")
    
    return JSONResponse(
        status_code=exc.status_code,
        headers={"X-Trace-ID": current_trace_id},
        content={
            "code": exc.code,
            "message": exc.message,
            "trace_id": current_trace_id,  # 在 JSON Body 中返回 TraceID，方便前端提供给客服/运维排查
            "details": exc.details
        }
    )

# 全局未捕获异常拦截器 (500 兜底)
@app.exception_handler(Exception)
async def global_exception_handler(request: Request, exc: Exception):
    current_trace_id = get_trace_id()
    
    # 发生严重故障时，带上 trace_id 记录完整的报错堆栈
    logger.critical(f"系统未捕获异常崩溃: {exc}", exc_info=True)
    
    return JSONResponse(
        status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
        headers={"X-Trace-ID": current_trace_id},
        content={
            "code": 50000,
            "message": "服务器内部错误",
            "trace_id": current_trace_id,
            "details": {}
        }
    )


# ================= 6. 测试路由 =================

## 四、 核心细节解析

1. **为什么用 `contextvars` 而不用全局变量？**

   在 FastAPI 这类基于 `asyncio` 事件循环的框架中，多个并发请求会在同一个线程内交替执行。全局变量或普通的 `threading.local` 会在并发时导致 `TraceID` 串号。`ContextVar` 能保证每个异步 Task 都有独立且隔离的上下文空间。

2. **`trace_id_var.reset(token)` 的重要性**

   在 `BaseHTTPMiddleware` 的 `finally` 块中使用 `reset(token)` 可以恢复请求前的上下文状态。在协程复用（如连接池或长连接）场景下，能避免上下文残留污染后续逻辑。

3. **前端与用户支撑闭环**

   当接口报错时，把 `trace_id` 返回给前端（存储在 JSON Body 或 Response Header 中）。当用户遇到错误向客服反馈“系统提示报错”时，运维人员只需拿着用户截图中显式的 `trace_id` 即可去日志平台（如 ELK / Grafana Loki）一键检索出报错当时上下文的所有步骤日志。

### 问：嗯，还有一点我想要搞清楚，你前面说”标准做法是在调用第三方库的地方进行捕获并转换，将第三方异常包装成你自己定义的自定义业务异常“，那像crud层是不是只用写查询代码，不需要捕获异常啥的，也就是和你说的调用第三方库同级，还有现在很火的向量数据库，像使用milvus检索文本块，它是不是也和crud层同级

你的理解大体是对的：向量数据库（如 Milvus）在架构上和传统关系型数据库（如 MySQL）完全一样，**都属于数据持久层（Repository / CRUD 层）**。

关于 CRUD 层要不要捕获异常，以及 Milvus 的定位，关键看架构中**各层的职责划分**。

## 一、 CRUD 层到底要不要捕获异常？

在规范的后端架构中，CRUD 层（或 DAO / Repository 层）的唯一职责是**与数据存储打交道**。对于异常处理，业界有两种主流实践：

### 模式 A：透传模式（最常见、最轻量）

- **做法**：CRUD 层**完全不写 `try-except`**，只负责编写查询语句。
- **逻辑**：如果数据库断连或 SQL 语法错误，让 SQLAlchemy、PyMongo 或 PyMilvus 抛出的原生异常**自然向上浮动（Bubble Up）**，由上层的 Service 层去捕获，或者由最外层的全局异常拦截器统一处理。
- **适用场景**：中小型项目、FastAPI / Flask 快速开发。

Python

```
# crud/user.py (透传模式：纯粹的 CRUD，不捕获任何异常)
def get_user_by_id(db: Session, user_id: int) -> Optional[User]:
    # 数据库连接超时或 SQL 错误直接向上抛出，不在 CRUD 层拦截
    return db.query(User).filter(User.id == user_id).first()
```

### 模式 B：防腐层包装模式（严格的架构模式）

- **做法**：CRUD 层**只捕获底层数据库驱动的特定异常**，并将其包装为自己定义的“数据持久层通用异常”（如 `DatabaseQueryException`）后再向上抛出。
- **目的**：**隔离底层技术细节**。Service 层只需要知道“数据库查询失败了”，而不需要关心底层用的是 `SQLAlchemyError`、`pymysql.OperationalError` 还是 `redis.RedisError`。如果以后把 MySQL 换成 PostgreSQL，Service 层的代码一行都不用改。

Python

```
# crud/user.py (包装模式：隔离第三方数据库 SDK 的异常)
from sqlalchemy.exc import SQLAlchemyError
from exceptions import DatabaseQueryException

def get_user_by_id(db: Session, user_id: int) -> Optional[User]:
    try:
        return db.query(User).filter(User.id == user_id).first()
    except SQLAlchemyError as e:
        # 捕获第三方 ORM 异常，转换为自定义的数据持久层异常抛出
        raise DatabaseQueryException(f"数据库查询用户[{user_id}]失败") from e
```

> **CRUD 层的核心铁律**：无论采用哪种模式，CRUD 层都**绝对不能**在里面写业务逻辑（比如“判断余额不足”），也**绝对不能**在 CRUD 层生成 HTTP 响应状态码。

## 二、 向量数据库（Milvus）在架构中处于什么位置？

向量数据库检索文本块（Vector Search），本质上就是针对向量索引进行的 `R`（Read / Retrieve）操作，**完全等同于 CRUD 层**。

在现代化的大模型应用架构（如 RAG 系统）中，你的底层存储通常是多维度的：

Plaintext

```
               ┌────────────────────────┐
               │   API Router / Controller │  (接收请求 / 全局异常拦截)
               └───────────┬────────────┘
                           │
               ┌───────────▼────────────┐
               │      Service Layer     │  (业务编排 / 异常判定 / 降级策略)
               └───────────┬────────────┘
                           │
     ┌─────────────────────┼─────────────────────┐
     │ (关系型 CRUD)        │ (缓存 CRUD)         │ (向量数据库 CRUD)
┌────▼───────────┐    ┌────▼───────────┐    ┌────▼───────────┐
│  MySQL / PgSQL │    │     Redis      │    │ Milvus / Qdrant│
└────────────────┘    └────────────────┘    └────────────────┘
```

### Milvus 在处理异常时的特殊之处：降级容灾（Fallback）

传统数据库如果连不上，业务往往直接报错退出；但在大模型应用中，**向量数据库连不上或超时，Service 层通常会选择“降级”而不是直接崩溃**：

Python

```
# services/rag_service.py (业务层编排)
class RAGService:
    def __init__(self, vector_crud: MilvusCRUD, keyword_crud: ESMetadataCRUD):
        self.vector_crud = vector_crud
        self.keyword_crud = keyword_crud

    def retrieve_context(self, query: str) -> list[str]:
        try:
            # 优先从 Milvus 做向量相似度检索
            return self.vector_crud.search_similar_chunks(query)
        except (MilvusException, PyMilvusError) as e:
            # 捕获向量数据库异常：记录 Warning 日志，触发降级策略！
            logger.warning(f"Milvus 向量检索不可用: {e}，自动降级为 ES 全文关键词检索")
            
            # 降级方案：回退到传统的关键词检索 / BM25 算法，保证系统不瘫痪
            return self.keyword_crud.search_by_keywords(query)
            
        except Exception as e:
            # 未知的致命异常，包装成业务异常抛给上层
            raise RAGServiceException("知识库检索彻底不可用") from e
```

## 三、 各层职责对比一览

为了防范“无脑全局捕获”的固化思维，在未来的开发中可以参照如下职责分工：

| **架构层级**                          | **主要职责**                                | **遇到异常时的做法**                                         |
| ------------------------------------- | ------------------------------------------- | ------------------------------------------------------------ |
| **CRUD 层** (MySQL / Milvus / Redis)  | 纯粹执行底层读写指令                        | **不处理业务**。要么完全透传，要么将第三方 SDK 异常包装为 `DataAccessException` 抛出 |
| **Service 层** (业务逻辑层)           | 业务校验、调用 LLM、组合 CRUD、RAG 检索编排 | **核心处理层**。捕获底层异常，决定是**自动重试**、**降级（Fallback）** 还是转化为 `BusinessException` |
| **Router / Controller 层** (FastAPI)  | 路由转发、参数校验                          | 不做繁琐的 `try-except`，交由全局拦截器                      |
| **Global Exception Handler** (最外层) | 系统安全兜底、统一 JSON 格式                | 捕获残余的 `Exception`，记日志，给前端返回标准的 `500 Internal Error` |
