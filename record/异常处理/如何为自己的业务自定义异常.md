### 问：Python如何自定义异常？

在 Python 中自定义异常，只需**继承内置的 `Exception` 类**（或其子类）。

---

### 1. 最简实现：直接继承

如果只需要一个区分类型的异常标记，直接继承并使用 `pass` 即可：

```python
class BusinessLogicError(Exception):
    """业务逻辑基础异常"""
    pass

# 触发并捕获
try:
    raise BusinessLogicError("操作不符合业务规则")
except BusinessLogicError as e:
    print(f"捕获到异常: {e}")

```

---

### 2. 携带额外数据：重写 `__init__`

当异常需要附带错误码、字段名或详细上下文时，可以重写构造函数：

```python
class ValidationError(Exception):
    def __init__(self, field: str, message: str, code: int = 400):
        # 调用父类构造函数设置默认错误信息
        super().__init__(f"[{field}] {message} (code: {code})")
        self.field = field
        self.message = message
        self.code = code

# 使用示例
def set_age(age: int):
    if age < 0:
        raise ValidationError("age", "年龄不能为负数", code=422)

try:
    set_age(-5)
except ValidationError as err:
    print(f"错误字段: {err.field}")
    print(f"状态码: {err.code}")
    print(f"完整报错: {err}")

```

---

### 3. 项目最佳实践：构建异常继承树

在大型项目或公共库中，通常先定义一个**项目根异常**，其他业务异常均继承自该根异常。这样调用者既可以捕获特定异常，也可以用一个 `except` 捕获该模块的所有异常：

```python
# 1. 模块基础异常
class AppError(Exception):
    """应用层所有自定义异常的基类"""
    pass

# 2. 具体分支异常
class DatabaseError(AppError):
    """数据库操作相关异常"""
    pass

class RecordNotFoundError(DatabaseError):
    """未找到指定记录"""
    def __init__(self, table: str, record_id: int):
        super().__init__(f"在表 '{table}' 中未找到 ID 为 {record_id} 的记录")
        self.table = table
        self.record_id = record_id

class NetworkTimeoutError(AppError):
    """网络超时异常"""
    pass

```

**调用方的捕获层级：**

```python
try:
    raise RecordNotFoundError("users", 42)
except DatabaseError as e:
    # 可以精确捕获数据库层面的错误
    print(f"数据库异常: {e}")
except AppError as e:
    # 也可以兜底捕获应用内的任何已知错误
    print(f"应用通用异常: {e}")

```

---

### 避坑要点

* **不要继承 `BaseException**`：`KeyboardInterrupt` 和 `SystemExit` 继承自 `BaseException`，如果你的异常也继承它，`except Exception:` 将无法拦截到它，容易导致意外穿透或捕获混乱。
* **命名规范**：遵循 PEP 8，类名采用 PascalCase，并以 `Error` 结尾（如 `PaymentError`）。

### 问：请讲解 Python 中的异常链（Exception Chaining）和 raise ... from 的使用场景与原理。

异常链（Exception Chaining，源自 PEP 3134）是 Python 3 引入的机制。当程序在处理一个异常的过程中抛出另一个异常时，异常链能够将新旧异常串联起来，**完整保留原始错误的调用栈和因果关系**，避免调试时线索断裂。



## 核心原理：`__cause__` 与 `__context__`

Python 解释器在内部通过异常对象的两个特殊属性来维护异常链：



- **`__context__`（隐式上下文）**：只要在 `except` 块内抛出新异常，Python 就会自动将捕获到的旧异常挂载到新异常的 `__context__` 上。
- **`__cause__`（显式原因）**：通过 `raise ... from <target>` 语法显式声明异常的成因。设置 `__cause__` 会同时将内部标记 `__suppress_context__` 置为 `True`，优先展示显式因果关系。

三者的具体区别如下：



| **语法**                      | **影响属性**                                      | **终端 Traceback 提示信息**                                  | **语义定位**                             |
| ----------------------------- | ------------------------------------------------- | ------------------------------------------------------------ | ---------------------------------------- |
| `raise NewError`              | `__context__ = old_exc`                           | *During handling of the above exception, another exception occurred:* | 处理旧异常时，**意外发生**了新异常       |
| `raise NewError from old_exc` | `__cause__ = old_exc`                             | *The above exception was the direct cause of the following exception:* | 旧异常是新异常的**直接根因**（主动转换） |
| `raise NewError from None`    | `__cause__ = None`  `__suppress_context__ = True` | *(只显示新异常的 Traceback)*                                 | **故意屏蔽**旧异常，净化调用栈           |

## 典型使用场景与示例

### 1. 显式包装底层异常（`raise ... from e`）

**场景**：编写公共库或分层架构时，不希望上层直接处理底层的具体技术实现细节（如 `sqlite3.OperationalError`、`requests.ConnectionError`），需要将其转换为业务层抽象的异常，但**必须保留底层堆栈以便排查故障**。



Python

```
import sqlite3

class DatabaseConnectionError(Exception):
    """业务层定义的数据库连接失败异常"""
    pass

def connect_to_db(db_uri: str):
    try:
        # 尝试连接非法路径触发 sqlite 错误
        conn = sqlite3.connect(db_uri)
        conn.cursor().execute("SELECT 1")
    except sqlite3.OperationalError as exc:
        # 将底层数据库异常显式包装为业务异常
        raise DatabaseConnectionError("无法连接到核心数据库服务") from exc

connect_to_db("/invalid/path/db.sqlite")
```

**控制台输出特点**：

先打印 `sqlite3.OperationalError` 的完整堆栈，随后明确提示：



Plaintext

```
The above exception was the direct cause of the following exception:

DatabaseConnectionError: 无法连接到核心数据库服务
```

调用者既能统一捕获 `DatabaseConnectionError`，运维或排错人员又能在日志中看到最初具体是哪个文件路径或驱动报错。



### 2. 屏蔽无用的内部细节（`raise ... from None`）

**场景**：底层发生的异常纯属内部实现琐事，将其暴露给终端用户或上层调用者反而会产生误导或视觉噪音。



Python

```
class ConfigurationKeyMissing(Exception):
    pass

def get_config_value(config_map: dict, key: str):
    try:
        return config_map[key]
    except KeyError:
        # 用户不需要关心内部用了 dict 存储，更不需要看到 KeyError
        raise ConfigurationKeyMissing(f"配置文件缺失关键字段: '{key}'") from None

get_config_value({}, "DATABASE_PORT")
```

**控制台输出特点**：

原始的 `KeyError` 堆栈被完全剔除，终端仅会输出 `ConfigurationKeyMissing` 的清晰错误：



Plaintext

```
Traceback (most recent call last):
  File "example.py", line 12, in <module>
    get_config_value({}, "DATABASE_PORT")
  File "example.py", line 9, in get_config_value
    raise ConfigurationKeyMissing(f"配置文件缺失关键字段: '{key}'") from None
ConfigurationKeyMissing: 配置文件缺失关键字段: 'DATABASE_PORT'
```

### 3. 区分隐式与显式（排查意料之外的代码 Bug）

如果不在 `except` 块中加 `from`，一旦你的异常处理逻辑本身写错了，隐式链会自动挽救案发现场：



Python

```
try:
    1 / 0
except ZeroDivisionError:
    # 假设这里程序员不小心写错了变量名
    print(undefined_variable)
```

**控制台输出特点**：



Plaintext

```
Traceback (most recent call last):
  File "...", line 2, in <module>
    1 / 0
ZeroDivisionError: division by zero

During handling of the above exception, another exception occurred:

Traceback (most recent call last):
  File "...", line 5, in <module>
    print(undefined_variable)
NameError: name 'undefined_variable' is not defined
```

Python 会通过 `During handling of the above exception...` 告诉你：原本在处理除以零的问题，结果你的处理代码崩在了 `NameError` 上。



## 最佳实践准则

1. **库代码（Library Code）必须用 `from`**：向外抛出自定义异常时，要么显式关联 `from original_exc`（提供上下文），要么显式切断 `from None`（屏蔽私有细节），避免输出模棱两可的隐式信息。
2. **日志抓取链条**：使用标准库 `logging.exception("...")` 或 `logging.error("...", exc_info=True)` 时，Python 的日志格式化器会自动递归遍历并打印出整条异常链（包含 `__cause__` 和 `__context__`）。

### 底层原理：为什么会这样？

Python 中所有内置异常都继承自 `BaseException`，它的打印机制依赖 `args` 属性：



1. **`args` 元组未被初始化**：

   `BaseException.__init__(*args)` 负责将传入的参数存入 `self.args` 属性中。如果不显式调用父类构造函数，`self.args` 就会是一个**空元组 `()`**。

2. **`__str__` 返回空字符串**：

   异常被打印或转为字符串（如 `print(e)`、`str(e)`、日志记录或终端展示 Traceback）时，默认的 `Exception.__str__()` 实现就是读取并格式化 `self.args`：

   - 如果 `args` 里有 1 个元素，返回该元素。
   - 如果 `args` 为空，返回 `""`（空字符串）。

你可以通过以下代码验证它的内部状态：



Python

```
err = ValidationError("age", "年龄不能为负数")

print(repr(err.args))  # 输出: ()
print(repr(str(err)))   # 输出: ''
print(err.field)        # 依然能访问自定义属性: 'age'
```

### 在实际项目中会引发的问题

1. **日志排查困难**：

   如果线上代码写了 `logger.error("发生错误: %s", e)`，日志输出会变成：

   Plaintext

   ```
   发生错误: 
   ```

   排错人员根本不知道具体错在哪里。

2. **三方库兼容问题**：

   很多框架（如 Sentry 监控、FastAPI/Flask 的全局异常中间件）在序列化异常信息时，都是直接读取 `str(e)` 或 `e.args`。如果没有初始化父类，这些系统抓取到的错误提示都是空白的。

### 替代方案：重写 `__str__`

如果不希望在 `__init__` 里拼接复杂的字符串给父类，也可以通过**显式重写 `__str__`** 达到相同的展示效果：



Python

```
class ValidationError(Exception):
    def __init__(self, field: str, message: str, code: int = 400):
        self.field = field
        self.message = message
        self.code = code

    def __str__(self):
        # 只要重写了 __str__，打印和 Traceback 就能正常显示内容
        return f"[{self.field}] {self.message} (code: {self.code})"
```

> **建议**：绝大多数情况下，直接调用 `super().__init__(f"...")` 是最省心、最符合 Python 惯用习惯（Idiomatic Python）的做法，它同时维护好了 `self.args` 和默认的字符串显示。

### 问：那我平时使用的Python中那么多详细的异常错误信息，其实都是它们通过自定义异常来设置的？而不是本来就有的

**是的，你的理解完全正确！**



没有任何一条错误描述是 Python 解释器“掐指一算”凭空猜出来的。你平时看到的每一句具体而微的报错，背后都是**某位程序员（包括 Python 核心开发者）亲手写格式化代码拼接出来的字符串**。



### 1. 堆栈信息里：哪些是“自动的”，哪些是“人工的”？

当你看到一段报错时，其实它由两部分拼装而成：



Plaintext

```
Traceback (most recent call last):
  File "test.py", line 4, in <module>        <-- 【系统自动追踪】调用栈、文件名、行号
    1 + "hello"                              <-- 【系统自动读取】出错那行的源码
TypeError: unsupported operand type(s) for +: 'int' and 'str'
  ▲                             ▲
  │                             └─────────── 【人工拼接的字符串】传入父类 __init__ 的描述
  └───────────────────────────────────────── 【异常类名】
```

- **系统自动生成的**：Python 虚拟机会随时维护调用栈帧（Frame）。发生异常时，它自动记录“在哪一个文件、哪一行、哪个函数”，这是运行时的物理跟踪机制。
- **人工显式填写的**：最后那行冒号后面的内容（比如 `'int' and 'str'`），**100% 是写这段底层逻辑的人拼好放进去的**。

### 2. 探秘：Python 内置异常也是这样写出来的

哪怕是 Python 最底层的内置类型，其报错信息也是写在 CPython 源码里的模板字符串。



以 `1 + "hello"` 触发的 `TypeError` 为例，在 CPython 的底层 C 语言源码（`typeobject.c`）中，真实的实现长这样：



C

```
// CPython 底层源码片段
PyErr_Format(PyExc_TypeError,
             "unsupported operand type(s) for %s: '%.100s' and '%.100s'",
             op_name,
             left_type->tp_name,
             right_type->tp_name);
```

官方核心开发者在检测到加号两侧类型不兼容时，读取了左边类型的名字（`int`）、右边类型的名字（`str`），然后套用格式化字符串，作为参数抛出了 `TypeError`。



再比如字典取值 `d["age"]` 发生 `KeyError: 'age'`：

也是字典的查询函数在找不到哈希键时，显式执行了类似于 `raise KeyError(key)` 的操作，将你传入的 key 原封不动交给了异常。



### 3. 标准库与第三方库（Requests、Pandas、FastAPI）的做法

平时用到的开源库，之所以报错非常友好、贴心，都是因为开发者在库内部自定义了大量异常类，并且极尽所能地帮你整理排错信息：



#### 标准库 `json` 的实现

当你解析一个非法 JSON 字符串时：



Python

```
import json
json.loads("{name: 123}")
# 报错：json.decoder.JSONDecodeError: Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
```

这并不是 Python 懂 JSON，而是 `json.decoder` 模块自己定义了一个 `JSONDecodeError(ValueError)`，计算出了出错的行号、列号，拼接出这串详细文本传给父类。



#### 第三方库 `requests` 的封装

当你请求一个不存在的网址时：



Python

```

requests.get("https://invalid-domain-xyz.com")
# 报错：requests.exceptions.ConnectionError: ...
```

`requests` 内部捕获了底层 socket 的原生错误，然后提取出目标 URL、失败原因，封装成自己定义的 `ConnectionError` 再抛给你。



### 这种机制对我们自己写代码的启发

明白了这一点，你就会发现：**异常不是程序崩溃的“灾难”，而是你与使用者（或未来的自己）沟通的“说明书”。**



- **糟糕的异常**：

  Python

  ```
  raise ValueError()  # 终端只显示一个空秃秃的 ValueError，毫无头绪
  ```

- **合格的异常**：

  Python

  ```
  raise ValueError("参数错误")  # 知道有参数错了，但不知道是哪个、传了什么
  ```

- **优秀的专业级异常**：

  Python

  ```
  raise ValueError(f"预期 timeout 大于 0，但实际接收到了 {timeout} (类型: {type(timeout).__name__})")
  ```

只要把关键的运行时变量拼进 `super().__init__(f"...")` 里，别人在半夜排查线上 Bug 时，看到 Traceback 的最后一行就能瞬间定位问题，而不需要在代码里加满 `print` 去猜当时变量究竟是什么。

### 问：原来如此，但我的疑问还是出自你写的异常示例的代码：

### super().__init__(f"[{field}] {message} (code: {code})")

### 这个报错信息模板是否能够通用。我感觉最头疼的还是模板的通用性。不知道那么多标准Python库是怎么做的？

你直觉非常敏锐——这种把字段写死在字符串里的模板（如 `f"[{field}] {message} (code: {code})"`），**确实无法通用**。



在实际开发中，如果强行套用这种固定模板，很快就会遇到尴尬情况：



- 某个错误没有关联的具体 `field` 怎么办？（比如“服务器连接超时”）
- 如果调用方想写一段更自由的提示语，模板会不会显得死板冗余？
- 机器端（API 返回 JSON）和人端（终端排查日志）对信息格式的要求冲突怎么办？

Python 标准库和成熟开源框架（如 Django、Requests、FastAPI）并不追求“一个模板打天下”，而是根据不同场景演化出了 **4 种主流方案**。



### 方案 1：调用点现场拼接（Python 标准库最常用的极简方案）

**代表库**：Python 内置异常（`ValueError`, `TypeError`, `KeyError` 等）



Python 官方异常本身几乎**不定义任何格式模板**，异常类只负责传递。模板的通用性问题，交给抛出异常的**调用现场**（Raise Site）去解决。



Python

```
class AppError(Exception):
    pass

# 异常定义极其干净，什么模板都不写
class ValidationError(AppError):
    pass

# 灵活度留给调用点，根据上下文自由拼接
raise ValidationError(f"字段 'age' 必须在 0 到 150 之间，当前输入: {raw_age}")
raise ValidationError(f"配置项 'DATABASE_URL' 不能为空")
```

- **适用场景**：绝大多数通用逻辑、工具函数、小型项目。
- **优点**：最符合 Python 哲学，零维护成本，调用者想写多详细就写多详细。

### 方案 2：动态缺省模板（Django / Celery 风格）

**代表库**：Django 的表单校验、Celery 任务异常



如果希望统一规范报错格式，但又不想失去灵活性，可以在类上定义一个**默认模板**，同时允许调用者传入自定义 `message` 进行覆盖。



Python

```
class ValidationError(Exception):
    # 1. 定义类级别的默认模板
    default_message = "数据校验失败"
    default_code = 400

    def __init__(self, message: str = None, field: str = None, code: int = None):
        self.field = field
        self.code = code or self.default_code
        
        # 2. 如果外部传了 message，用外部的；没传，则使用回退逻辑
        if message is not None:
            self.message = message
        elif field:
            self.message = f"字段 '{field}' 校验未通过"
        else:
            self.message = self.default_message

        # 3. 拼装展示字符串传给父类
        display = f"[{self.code}] {self.message}"
        if self.field:
            display = f"[{self.field}] {display}"
            
        super().__init__(display)
```

**使用时丰俭由人：**



Python

```
# 形式 A：最省事，使用默认文案
raise ValidationError(field="email") 
# 输出: [email] [400] 字段 'email' 校验未通过

# 形式 B：覆盖详细文案
raise ValidationError(message="邮箱格式不合法，缺少 @ 符号", field="email", code=422)
# 输出: [email] [422] 邮箱格式不合法，缺少 @ 符号
```

### 方案 3：结构化数据与人读文案分离（`OSError` / FastAPI 风格）

**代表库**：Python 标准库的 `OSError`（如找不到文件时报的错）



仔细观察 `OSError` 的报错：



Plaintext

```
FileNotFoundError: [Errno 2] No such file or directory: 'config.json'
```

它底层并不是写死的一个字符串，而是保存了结构化属性：`errno`、`strerror` 和 `filename`。



标准库的做法是：**重写 `__str__` 动态判断哪些字段存在，按需拼装**。



Python

```
class APIError(Exception):
    def __init__(self, message: str, code: int = 500, details: dict = None):
        super().__init__(message)
        self.message = message
        self.code = code
        self.details = details or {}

    def __str__(self):
        """只在打印时按需组装，不把脏逻辑塞进 __init__"""
        base = f"Code {self.code}: {self.message}"
        if self.details:
            base += f" | 附加数据: {self.details}"
        return base
```

- **人看日志时**：`str(e)` 触发 `__str__`，输出排版整齐的字符串。

- **程序接口处理时**：Web 框架拦截到 `APIError`，直接读取 `e.code` 和 `e.details`，序列化成 JSON 返回给前端，两者互不干扰：

  JSON

  ```
  {"code": 404, "message": "User not found", "details": {"user_id": 1001}}
  ```

### 方案 4：按“错误类型”细分继承树（彻底放弃“万能模板”）

试图写一个能够容纳“所有情况”的异常模板，本身就是**过度设计（Over-engineering）**。



标准库从来不用一个 `StandardError` 塞满各种参数，而是拆分为不同职责的子类：



- 找不到键？用 `KeyError(key)`
- 属性不存在？用 `AttributeError(obj, attr)`
- 算术溢出？用 `OverflowError(msg)`

在项目中也是同理，拆成专门的小类，模板自然就不需要通用了：



Python

```
class AppError(Exception):
    """所有业务异常基类"""
    pass

class ResourceNotFoundError(AppError):
    def __init__(self, resource: str, identifier: any):
        super().__init__(f"未找到资源 '{resource}' (标识: {identifier})")

class ParameterInvalidError(AppError):
    def __init__(self, param_name: str, reason: str):
        super().__init__(f"参数 '{param_name}' 非法: {reason}")
```

每个类只关心自己的 1~2 个参数，逻辑极其简单，不需要写任何 `if-else` 去兼容复杂场景。



### 实用建议

如果正在搭建自己的项目，推荐这套**平衡度最高**的通用范式：



1. **基类保持极简**：继承 `Exception`，允许接收 `message: str`，保证在任何地方都能像原生异常一样 `raise MyError("任何你想写的文字")`。
2. **需要程序处理的字段单独立项**：如果异常需要被上层代码读取（比如 HTTP 状态码、错误编码 `ERR_USER_NOT_FOUND`），将其作为可选命名参数传入，保存为属性，而不是硬塞在字符串里。
3. **不要追求一个通用大模板**：让通用逻辑用最自由的字符串，特定业务场景（如表单校验）单独派生一个专用的子异常类去实现专用格式。

### 问：像OpenAI python API的异常封装是怎样的？是否有一套统一的风格，我主要是想从它里面提取信息

OpenAI 官方 Python SDK（从 1.0 版本起）采用了一套非常现代、工业级的**结构化异常封装模式**（基于 Stainless 代码生成器和 `httpx` 构建）。



它彻底避免了“把所有信息拼成一个字符串让调用方去正则匹配”，而是**把错误信息拆解为统一、强类型的属性**。



如果你想从异常中提取信息，了解它的**继承层次**和**核心属性**是关键。



### 一、 核心异常继承树

OpenAI 的异常体系结构非常清晰，主要分为三层：



Plaintext

```
OpenAIError (所有 SDK 异常的基类)
├── APIConnectionError (网络连接不上、DNS 失败等，无 HTTP 响应)
├── APITimeoutError (请求超时)
└── APIError (收到服务端响应，但发生错误)
    └── APIStatusError (HTTP 状态码不是 2xx 的情况)
        ├── BadRequestError (400)
        ├── AuthenticationError (401 - API Key 错误/失效)
        ├── PermissionDeniedError (403 - 地区限制/权限不足)
        ├── NotFoundError (404 - 模型不存在等)
        ├── ConflictError (409)
        ├── UnprocessableEntityError (422)
        ├── RateLimitError (429 - 频率超限 / 额度耗尽)
        └── InternalServerError (500+ - 官方服务器内部故障)
```

### 二、 从异常中能提取哪些信息？

当你捕获到 `APIStatusError`（或其子类如 `RateLimitError`、`AuthenticationError`）时，SDK 已经把 OpenAI 服务端返回的标准 JSON 结构解析挂载到了异常对象上。



你可以直接提取以下属性：



| **属性名**          | **类型**         | **说明 / 常见值**                                            |
| ------------------- | ---------------- | ------------------------------------------------------------ |
| **`e.status_code`** | `int`            | HTTP 状态码，例如 `401`, `429`, `500`                        |
| **`e.message`**     | `str`            | 易读的错误原因描述（包含在 `super().__init__` 中展示的文本） |
| **`e.code`**        | `str | None`     | 细分错误代码（机器可读），如 `'invalid_api_key'`, `'insufficient_quota'` |
| **`e.type`**        | `str | None`     | 错误类别，如 `'invalid_request_error'`, `'tokens_exceeded'`  |
| **`e.param`**       | `str | None`     | 导致报错的具体请求参数名，如 `'messages'`, `'model'`         |
| **`e.body`**        | `dict | None`    | 服务端返回的原始完整 JSON 字典：`{"error": {...}}`           |
| **`e.response`**    | `httpx.Response` | 底层的原始 HTTP 响应对象，可提取 Response Headers            |
| **`e.request`**     | `httpx.Request`  | 发起请求时的原始 HTTP 请求对象                               |

### 三、 标准信息提取代码范式

在实际业务中，推荐按照从“具体”到“抽象”的层级进行捕获和提取：



Python

```
import openai
from openai import OpenAI

client = OpenAI(api_key="sk-...")

try:
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": "Hello"}]
    )

except openai.RateLimitError as e:
    # 场景 1：针对 429 单独处理（额度用光 或 频率超限）
    print("触发频率限制或额度耗尽！")
    print(f"具体错误码: {e.code}")          # 例如: 'insufficient_quota'
    print(f"提示信息: {e.message}")
    
    # 从 response headers 中提取官方建议的重试时间
    retry_after = e.response.headers.get("retry-after")
    if retry_after:
        print(f"建议重试等待时间: {retry_after} 秒")

except openai.APIStatusError as e:
    # 场景 2：统一兜底捕获所有服务端 HTTP 错误 (400, 401, 403, 500 等)
    print(f"OpenAI 接口调用失败，状态码: {e.status_code}")
    print(f"错误类型 (type): {e.type}")       # 例如: 'invalid_request_error'
    print(f"出错参数 (param): {e.param}")     # 例如: 'temperature'
    print(f"机器错误码 (code): {e.code}")     # 例如: 'model_not_found'
    print(f"完整原始响应 (body): {e.body}")

    # 获取请求排查 ID（向官方提工单或查排错日志必用）
    request_id = e.response.headers.get("x-request-id")
    print(f"Request ID: {request_id}")

except openai.APIConnectionError as e:
    # 场景 3：物理网络层面失败（连不上、超时等，此时没有 status_code 和 response）
    print(f"网络通信故障: {e.message}")

except openai.OpenAIError as e:
    # 场景 4：SDK 最顶层兜底
    print(f"SDK 发生未知异常: {e}")
```

### 四、 OpenAI 这种设计风格给我们的启示

分析它的源码（`openai/_exceptions.py`），可以发现它解决上一轮讨论中“通用模板”痛点的几个绝妙设计：



1. **分离“人读信息”与“机读数据”**：
   - `super().__init__(message)` 只存人类日志可读的完整汇总句；
   - 把 `code`、`param`、`type` 单独作为类属性保存，业务代码里你可以直接写 `if e.code == "insufficient_quota":` 做逻辑分支，**不需要从错误文本里做字符串搜索**。
2. **保留底层通信上下文**：
   - 异常内部直接保留了 `self.response`（`httpx.Response`）与 `self.body`。如果以后 OpenAI 的 API 返回了新的 HTTP Header（比如限流剩余 Token 数），使用者即便不升级 SDK，也能通过 `e.response.headers` 自行拿到。
3. **按 HTTP 状态码做精细派生**：
   - 状态码相同的错误直接继承自同一个子类（如 429 对应 `RateLimitError`），上层代码可以通过 `except openai.RateLimitError` 专注于业务补偿重试，代码可读性极高。

### 问：如何捕获OpenAI 的异常，然后统一封装为自己的自定义异常呢

在工程实践中，将三方 SDK（如 OpenAI）的异常转换为本项目的领域自定义异常（Domain Exceptions）是一种标准架构做法（防腐层模式，Anti-Corruption Layer）。



这样做有三个核心好处：



1. **解耦**：上层业务代码无需导入 `openai` 库即可处理错误。如果未来切换为 Claude、DeepSeek 或自建开源模型，业务层代码无需改动。
2. **规范化数据**：提取关键属性（状态码、错误编码、Request ID），统一暴露给网关或日志。
3. **保留调试链条**：通过 `raise ... from e` 完整保留底层 traceback。

### 第一步：定义本系统的 LLM 异常体系

定义一个统一的基类和若干代表不同业务意义的子类，同时保留机读属性与人类可读文案：



Python

```
class LLMError(Exception):
    """所有大模型调用相关异常的基类"""
    def __init__(
        self,
        message: str,
        code: str | None = None,
        status_code: int | None = None,
        request_id: str | None = None,
        retry_after: float | None = None,
    ):
        super().__init__(message)
        self.message = message
        self.code = code                  # 业务错误码，如 'quota_exceeded'
        self.status_code = status_code    # HTTP 状态码
        self.request_id = request_id      # 排查日志用的链路 ID
        self.retry_after = retry_after    # 建议重试等待时间（秒）


class LLMAuthenticationError(LLMError):
    """密钥错误、过期或未授权"""
    pass


class LLMQuotaExceededError(LLMError):
    """额度耗尽或并发超限 (Rate Limit)"""
    pass


class LLMInvalidRequestError(LLMError):
    """参数非法、上下文超长、模型不存在等业务请求问题"""
    pass


class LLMNetworkError(LLMError):
    """网络超时、DNS 解析失败或连接断开"""
    pass


class LLMServiceUnavailableError(LLMError):
    """OpenAI 服务端 5xx 故障"""
    pass
```

### 第二步：编写统一的异常转换器（上下文管理器）

使用 Python 标准库的 `contextlib.contextmanager` 实现一个拦截上下文，集中处理映射逻辑：



Python

```
from contextlib import contextmanager
import openai

@contextmanager
def translate_openai_exceptions():
    """将 OpenAI SDK 异常统一捕获并转换为项目自定义异常"""
    try:
        yield
    except openai.AuthenticationError as e:
        raise LLMAuthenticationError(
            message=f"大模型认证失败: {e.message}",
            code=e.code or "AUTH_FAILED",
            status_code=e.status_code,
            request_id=e.response.headers.get("x-request-id") if e.response else None,
        ) from e

    except openai.RateLimitError as e:
        # 尝试提取响应头里的建议重试时间
        retry_after = None
        if e.response and "retry-after" in e.response.headers:
            try:
                retry_after = float(e.response.headers["retry-after"])
            except ValueError:
                pass

        raise LLMQuotaExceededError(
            message=f"调用频次或额度超限: {e.message}",
            code=e.code or "RATE_LIMIT_EXCEEDED",
            status_code=e.status_code,
            request_id=e.response.headers.get("x-request-id") if e.response else None,
            retry_after=retry_after,
        ) from e

    except (openai.BadRequestError, openai.NotFoundError, openai.UnprocessableEntityError) as e:
        raise LLMInvalidRequestError(
            message=f"模型请求参数非法: {e.message}",
            code=e.code or "INVALID_REQUEST",
            status_code=e.status_code,
            request_id=e.response.headers.get("x-request-id") if e.response else None,
        ) from e

    except openai.InternalServerError as e:
        raise LLMServiceUnavailableError(
            message="大模型服务提供商暂时不可用，请稍后重试",
            code="UPSTREAM_SERVICE_ERROR",
            status_code=e.status_code,
            request_id=e.response.headers.get("x-request-id") if e.response else None,
        ) from e

    except (openai.APITimeoutError, openai.APIConnectionError) as e:
        # 物理网络异常通常没有 status_code 和 response
        raise LLMNetworkError(
            message=f"无法连接到模型服务器: {e.message}",
            code="NETWORK_FAILURE",
        ) from e

    except openai.OpenAIError as e:
        # 兜底捕获 OpenAI 的其他未知异常
        raise LLMError(
            message=f"大模型发生未知异常: {e.message}",
            code="UNKNOWN_LLM_ERROR",
        ) from e
```

### 第三步：在业务服务中使用

在实际工程中，将调用逻辑包裹在上下文管理器中。业务上层只需关心自己的 `LLMError`，彻底摆脱对 `openai` 库的依赖：



Python

```
from openai import OpenAI

class LLMService:
    def __init__(self, api_key: str):
        self.client = OpenAI(api_key=api_key)

    def generate_reply(self, prompt: str) -> str:
        # 在上下文作用域内执行 SDK 调用
        with translate_openai_exceptions():
            response = self.client.chat.completions.create(
                model="gpt-4o",
                messages=[{"role": "user", "content": prompt}],
            )
            return response.choices[0].message.content


# 业务调用端示例：
service = LLMService(api_key="sk-invalid-key")

try:
    reply = service.generate_reply("你好")
except LLMQuotaExceededError as e:
    # 针对限流的降级逻辑
    print(f"触发限流，建议等待 {e.retry_after} 秒后重试")
except LLMError as e:
    # 统一兜底处理，同时能取到结构化数据打入系统监控
    print(f"调用失败: {e.message}")
    print(f"错误码: {e.code}, HTTP状态: {e.status_code}, Request-ID: {e.request_id}")
```

### 设计核心要点

1. **必须加上 `from e`**：

   在 `raise MyCustomError(...) from e` 中显式挂载根因。这样排查 Sentry 或后端日志时，依然可以点开底层的原始 `httpx.HTTPStatusError` 和调用栈，排查网络和原始报文细节。

2. **安全提取 `response` 字段**：

   网络层错误（如 `APIConnectionError`、`APITimeoutError`）发生时，**压根没有收到 HTTP 响应**，此时 `e.response` 是 `None`。因此提取 `request-id` 或 `headers` 时，务必通过 `if e.response` 或可选链安全访问。

3. **支持装饰器模式（可选）**：

   若不习惯 `with` 语法，也可以将 `contextmanager` 改造为函数装饰器（`@wrap_llm_exceptions`），直接修饰 `generate_reply` 方法。

### 问：有一个地方我不太理解，就是这些类初始化的时候都可以传入字符串，这个特性是来自它们的基类Exception吗？传入的字符串是给什么属性赋值？

**是的，这个特性完全继承自基类 `Exception`（更底层的根源是 `BaseException`），传入的字符串最终被赋值给了 `self.args` 属性，并以元组（tuple）的形式保存。**



### 1. 它是如何赋值的？

在 Python 底层，`BaseException` 的默认构造函数类似于这样：



Python

```
class BaseException:
    def __init__(self, *args):
        # 接收任意数量的位置参数，统一打包成元组存入 self.args
        self.args = args
```

当你写 `class MyError(Exception): pass` 时，如果不定义自己的 `__init__`，它会一路往上继承这个行为：



Python

```
class MyError(Exception):
    pass

# 传入单个字符串
err1 = MyError("出错了")
print(err1.args)  # 输出: ('出错了',)  <- 是一个只包含 1 个元素的元组

# 甚至可以传入多个不同类型的参数
err2 = MyError("找不到记录", 404, {"table": "users"})
print(err2.args)  # 输出: ('找不到记录', 404, {'table': 'users'})
```

### 2. 常见误区：有 `e.message` 这个属性吗？

**在 Python 3 中，默认没有 `e.message`。**



很多人直觉上以为传入的字符串会变成 `e.message`，甚至会写出 `print(e.message)`。但在 Python 3 中，访问它会直接报 `AttributeError`：



Python

```
try:
    raise ValueError("非法参数")
except ValueError as e:
    # ❌ 错误做法：Python 3 会报错 AttributeError: 'ValueError' object has no attribute 'message'
    # print(e.message)

    #  正确做法 1：直接把异常转为字符串（最推荐）
    print(str(e))       # 输出: "非法参数"

    #  正确做法 2：从 args 中按索引提取
    print(e.args[0])    # 输出: "非法参数"
```

> **历史背景**：早期的 Python 2.5 曾短暂给 `BaseException` 引入过 `message` 属性，但后来发现容易与用户自定义属性产生冲突，因此在 Python 2.6 被标记弃用，并在 **Python 3 中被彻底移除**。

### 3. `self.args` 与终端打印的关系

为什么直接 `print(e)` 能看到那个字符串？因为 `BaseException` 的 `__str__` 方法内部就是根据 `self.args` 的内容来决定输出行为的：



- **如果 `args` 只有 1 个参数**：直接返回 `str(args[0])`（这就是为什么绝大多数异常打印出来就是你传的那句报错）。
- **如果 `args` 有多个参数**：返回整个元组的字符串表示，例如 `str(args)`。
- **如果 `args` 为空**：返回空字符串 `""`。

Python

```
# 1 个参数：打印该参数本身
print(Exception("连接超时"))        
# 输出: 连接超时

# 多个参数：打印整个元组
print(Exception("连接超时", 504))   
# 输出: ('连接超时', 504)

# 0 个参数：什么也不打印
print(Exception())                  
# 输出: (空白)
```

### 4. 为什么我们在自定义异常时要写 `super().__init__(...)`？

回顾之前自定义异常的代码：



Python

```
class ValidationError(Exception):
    def __init__(self, field: str, message: str, code: int = 400):
        # 这一步，就是把拼装好的字符串传递给基类的 *args
        super().__init__(f"[{field}] {message} (code: {code})")
        
        # 下面是你额外绑定的业务属性
        self.field = field
        self.message = message  # 你自己显式赋值后，e.message 才可以使用！
        self.code = code
```

执行 `super().__init__(...)` 本质上就是调用了基类的逻辑，把格式化后的那句文本打包进 `self.args`，从而保证了 `str(e)`、日志记录以及系统终端 Traceback 能够正常读取并显示这行错误。

### 问：那么str(e)到底是触发了什么方法，这个方法会将哪些属性转为字符串

`str(e)` 触发的是对象的魔术方法 **`__str__()`**。



在没有手动重写该方法的前提下，它调用的是最顶层基类 `BaseException.__str__()`。这个方法在底层**只读取且仅读取 `self.args` 这一个属性**，并将其转换为字符串；你在子类中自定义绑定的任何其他属性（如 `self.field`、`self.code` 等）都会被它**完全无视**。



### 一、`BaseException.__str__()` 的底层执行逻辑

在 CPython 底层（C 语言源码 `exceptions.c` 中的 `BaseException_str` 函数），它的逻辑非常纯粹，只根据 `self.args` 的长度分三种情况处理：



1. **`len(self.args) == 1`（最常见）**：
   - 逻辑：直接调用元组唯一元素的 `str()`。
   - 结果：`str(self.args[0])`。
2. **`len(self.args) == 0`（没传任何参数）**：
   - 逻辑：直接返回一个空的字符串对象。
   - 结果：`""`。
3. **`len(self.args) > 1`（传了多个参数）**：
   - 逻辑：直接对整个元组执行转字符串操作。
   - 结果：`str(self.args)`。

用一段 Python 伪代码来表示就是：



Python

```
class BaseException:
    def __str__(self):
        if len(self.args) == 1:
            return str(self.args[0])
        elif len(self.args) == 0:
            return ""
        else:
            return str(self.args)
```

### 二、代码实测：验证自定义属性被忽略

通过下面的实验，可以直观看到它到底读了谁：



Python

```
class MyCustomError(Exception):
    def __init__(self, message, code):
        # 故意不传 code 给父类，只把 message 传给 args
        super().__init__(message)
        self.code = code  # 仅挂在实例属性上

err = MyCustomError("用户未登录", 401)

# 1. str(err) 只触发了 BaseException.__str__
print(str(err))
# 输出: "用户未登录" (因为 self.args 只有 ('用户未登录',)，self.code 完全被忽略)

# 2. 如果把 self.args 清空
err.args = ()
print(repr(str(err)))
# 输出: '' (变成了空字符串)

# 3. 如果篡改 self.args 
err.args = ("完全伪造的错误信息",)
print(str(err))
# 输出: "完全伪造的错误信息" (证明 str() 的输出 100% 绑死在 self.args 上)
```

### 三、补充：`repr(e)` 触发的是什么？

除了 `str(e)`，在调试或控制台交互时经常会用到 `repr(e)`，它触发的是 **`__repr__()`** 方法。



`BaseException.__repr__()` 同样只依赖两个东西：**类名** 和 **`self.args`**。



Python

```
err = Exception("出错了", 500)

print(str(err))   # 触发 __str__  -> 输出: ('出错了', 500)
print(repr(err))  # 触发 __repr__ -> 输出: Exception('出错了', 500)
```

其底层规则是：拼接 `类名 + repr(self.args)`。同样不会去读取你自定义的任何其他实例字段。



### 总结

- **调用的方法**：`e.__str__()`（继承自 `BaseException.__str__()`）。
- **转换的属性**：**只有 `self.args`**。
- **自定义属性要想在 `str(e)` 中呈现**，只有两种途径：
  1. 在 `__init__` 中把数据格式化后传给 `super().__init__(formatted_string)`，让它写入 `self.args`。
  2. 在子类中重写 `def __str__(self):` 方法，手动决定读取并返回哪些属性。

### 问：还有一个是关于异常捕获的规则，我当前的理解是捕获父类异常，那么父类异常的子类也会被捕获。而捕获子类异常，子类异常的父类则不会被捕获，不知道我理解的对不对

Python 的异常匹配机制本质上就是面向对象中的 **`issubclass`（子类检测）**。



当执行 `except TargetError:` 时，解释器会判断：



> **“当前抛出的异常类，是否是 `TargetError` 本身，或者它的子类？”**
>
> 即：`issubclass(type(raised_error), TargetError)` 是否为 `True`。

### 1. 验证两者的表现

假设我们有一组父子异常：



Python

```
class AnimalError(Exception):
    """父类"""
    pass

class DogError(AnimalError):
    """子类"""
    pass
```

#### 情况一：捕获父类，子类会被捕获（成立）

`DogError` 是 `AnimalError` 的派生类，因此 `issubclass(DogError, AnimalError)` 为 `True`：



Python

```
try:
    raise DogError("小狗生病了")
except AnimalError as e:
    print(f"成功捕获: {e}")

# 输出：成功捕获: 小狗生病了
```

#### 情况二：捕获子类，父类不会被捕获（成立）

抛出的是 `AnimalError`，但拦截规则只认 `DogError`。因为 `AnimalError` 不是 `DogError` 的子类，所以无法被捕获，异常会直接向外穿透甚至导致程序崩溃：



Python

```
try:
    raise AnimalError("某种动物生病了")
except DogError as e:
    print(f"成功捕获: {e}")

# 结果：未被拦截，终端直接抛出未捕获异常：
# Traceback (most recent call last):
#   ...
# AnimalError: 某种动物生病了
```

### 2. 这个规则带来的关键开发实践：捕获顺序必须“从窄到宽”

由于父类会“通吃”它所有的子类，如果你的 `try...except` 语句块中需要同时捕获多个层级的异常，**必须将子类写在前面，父类写在后面**。



#### 错误示范：父类在前，子类被“屏蔽”

Python 的 `except` 是自上而下按序匹配的。如果把父类写在上面，子类永远没有机会被执行：



Python

```
try:
    raise DogError("小狗生病了")
except AnimalError:
    # 无论抛出 AnimalError 还是 DogError，都会在这里被截胡
    print("触发了通用的动物异常处理逻辑")
except DogError:
    # ❌ 这里的代码永远不可达（Dead Code）
    print("触发了专门针对狗的特殊处理逻辑")
```

#### 正确示范：子类在前，父类在后（由具体到抽象）

Python

```
try:
    # 业务代码...
    raise DogError("小狗生病了")
except DogError:
    # 1. 优先精确匹配子类，做精细化业务处理
    print("执行针对狗的特殊处理逻辑")
except AnimalError:
    # 2. 如果是其他未指定的动物异常，在此处统筹兜底
    print("执行通用的动物异常兜底")
except Exception:
    # 3. 最后的全局大兜底（因为所有常规异常都是 Exception 的子类）
    print("未知未知异常兜底")
```

这也是为什么通常不建议直接写裸露的 `except Exception:` 或 `except:`：因为 `Exception` 是绝大多数异常的共同祖先，直接捕获它会把诸如拼写错误（`NameError`）、类型传错（`TypeError`）等意外代码 Bug 一并静默吞掉，从而掩盖真正的程序缺陷。

顺着你的思路，我们把这两个场景的最佳工程实践和需要注意的小细节梳理清晰：



### 场景一：复用底层库的异常 `e`

直接提取 `str(e)` 传给自定义异常是完全可行的。但**最专业的做法是配合异常链（`from e`）一起使用**：



Python

```
try:
    # 假设调用底层库（比如 requests 或数据库连接）
    third_party_lib.do_something()
except ThirdPartyError as e:
    # 1. 提取 str(e) 拼入业务提示
    # 2. 关键：加上 `from e` 保留底层真实堆栈
    raise MyBusinessError(f"支付接口调用失败: {e}") from e
```

- **为什么要加 `from e`？**

  因为 `str(e)` 提取出的只是“那句话”（比如 `Connection refused`），万一遇到偶发 Bug 需要看具体是哪一行 socket 崩了，`from e` 能把底层的调用栈完整保留在日志里。

### 场景二：加工或自定义错误信息（两条路径）

正如你所总结的，加工展示信息确实主要有两种途径：



#### 路径 A：在传入前（或 `__init__` 中）把字符串加工好

这是最直接、最常用的做法。把数据拼装好，交给 `super().__init__(message)`，底层会自动写入 `self.args`：



Python

```
class MyBusinessError(Exception):
    def __init__(self, message: str, code: int = 400):
        # 在这里把结构化数据加工成最终展示的字符串
        formatted_message = f"[{code}] {message}"
        super().__init__(formatted_message)
        self.code = code
```

- **适用场景**：逻辑简单直观，大多数日常业务代码用这一种就完全够用。

#### 路径 B：重写 `__str__` 方法（注意是方法，不是参数）

保持原始属性的纯粹，把“怎么展示给人类看”推迟到真正被打印或转成字符串的那一刻：



Python

```
class MyBusinessError(Exception):
    def __init__(self, message: str, code: int = 400, details: dict = None):
        super().__init__(message)  # args 只保留纯粹的文本
        self.code = code
        self.details = details

    def __str__(self):
        # 动态组装：只在 print(e) 或 str(e) 时触发
        res = f"Error {self.code}: {self.args[0]}"
        if self.details:
            res += f" (详情: {self.details})"
        return res
```

- **适用场景**：异常附带较多结构化属性（如字典、列表、错误码），不仅要在日志里打印，还要给上层程序（比如 Web 框架）读取原生字典字段。

### 一句话记忆

- **想复用三方报错**：`raise MyError(f"...: {e}") from e`（文案用 `str(e)`，链路用 `from e`）。
- **想定制报错文案**：简单的直接在 `__init__` 拼好塞给 `super()`；复杂的保存属性、重写 `__str__()`。

### 问：我再理解一下，场景二中的路径A其实就是复用了Exception的__str__函数，而路径B则是重写了Exception的__str__函数，那么路径二还有必要super().__init__(message)吗

你的理解非常透彻：**路径 A 的本质就是复用了 `BaseException.__str__`，而路径 B 则是彻底重写了它。**



既然 `str(e)` 已经被我们自己接管了，那在路径 B 中还有必要写 `super().__init__(message)` 吗？



结论是：**依然很有必要，强烈建议保留。**



虽然此时 `str(e)` 已经不再依赖它，但 Python 的其他底层机制和工具生态仍然高度依赖通过 `super().__init__(...)` 初始化的 `self.args`。主要体现在以下三个方面：



### 1. `repr(e)` 依然依赖 `self.args`（影响调试与 IDE 查看）

重写 `__str__` 只改变了 `str(e)` 和 `print(e)` 的输出，**并没有改变 `repr(e)`**。



当你使用交互式终端、调试器（pdb、VS Code、PyCharm 调试窗口）查看变量，或者在日志中记录容器对象（如包含异常的字典或列表）时，Python 调用的是 `repr(e)`。



- **如果写了 `super().__init__(message)`**：

  Python

  ```
  repr(e)  # 输出: MyError('用户未登录') -> 调试时一目了然
  ```

- **如果漏了 `super().__init__(message)`**：

  `BaseException.__repr__` 读取不到 `self.args`，调试输出就会退化为：

  Python

  ```
  repr(e)  # 输出: MyError() -> 调试器里只能看到一个空壳
  ```

### 2. 多进程与跨进程序列化（Pickle / Celery / `multiprocessing`）

在多进程通信、Celery 异步任务或 Redis 缓存中，异常经常需要被序列化传输。



Python 内置的 `pickle` 模块在序列化 `BaseException` 对象时，默认调用的还原协议（`__reduce__`）依赖的就是 `self.args`：



Python

```
import pickle

class BadError(Exception):
    def __init__(self, message, code):
        # 故意不调 super().__init__
        self.code = code
    def __str__(self):
        return "custom str"

err = BadError("msg", 500)
pickle.dumps(err)  # 反序列化时会通过 BadError(*self.args) 来重建实例！
```

如果未通过 `super().__init__` 把参数填充进 `self.args`，反序列化重建对象时可能会因为参数缺失（例如子类的 `__init__` 要求必填参数）直接抛出 `TypeError: __init__() missing required positional argument`，导致跨进程通信崩溃。



### 3. 三方监控与测试工具的代码兼容

很多成熟库（如 Sentry、pytest、部分自动化测试框架）会直接通过 `e.args` 提取原始错误信息，而不是转成字符串去解析：



Python

```
# 许多框架内部的判断逻辑
if e.args and "timeout" in str(e.args[0]).lower():
    ...
```

如果绕过了 `super().__init__`，`e.args` 会变成空元组 `()`，可能导致这些监控系统抓取到的错误摘要缺失。



### 最佳写法建议

在路径 B 下，最稳健的写法是：**把主错误文本交给 `super().__init__` 兜底基础生态，把定制格式留给 `__str__` 负责展示**。

Python

```
class MyBusinessError(Exception):
    def __init__(self, message: str, code: int = 400, details: dict = None):
        # 1. 喂给基类，保障 args、repr、pickle 正常运作
        super().__init__(message)
        
        # 2. 保存业务属性，供程序提取
        self.code = code
        self.details = details or {}

    def __str__(self):
        # 3. 自定义打印格式，供人类阅读
        base = f"[{self.code}] {self.args[0]}"
        if self.details:
            base += f" - 详情: {self.details}"
        return base
```
