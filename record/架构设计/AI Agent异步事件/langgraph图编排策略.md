### 核心问题

1、Agent可能进行并行工具调用，即一次输出多个工具调用

2、有的工具是只读的，有的工具会进行写操作，要进行中断权限审核

3、如果工具全部放到一个节点中执行，会出现很多问题：
首先是langgraph的checkpointer写入的时机是一个节点执行完毕的时候

```
那么如果前面的工具执行完毕，而当前工具执行抛出异常导致图崩溃；

或者前面的部分工具已然执行完毕，而当前工具执行的时候worker崩溃

都会导致部分工具已经执行完毕，特别是写工具已经造成了影响，但是checkpointer却没有进行记录的问题。

会导致输入给模型的消息列表与实际情况不一致的情况。而消息列表是输入给模型的，

导致模型以为工具执行并未成功，但是实际上已经产生影响的认知差异。
```

其次就是langgraph的中断特性会导致如果某个节点发生了中断，

```
如果工具调用全部集中在一个节点的话，中断恢复的时候，

当前节点会从头开始全部重新执行，如果部分工具调用在中断之前发生，

会出现多次重复执行的情况
```

### 解决方法

设置一个分发器节点。接在获取模型响应的call_model节点之后

想像一个工具调用的执行顺序：读工具1，读工具2，写工具1，写工具2，读工具3，读工具4

这种情况下，先识别两个读工具，对专门执行读工具的节点，进行并发执行

再对于写工具，进入一次执行单个工具的节点。先中断进行审核，再串行执行写工具

再对于读工具，进行并发执行



## 核心问题二

即使是将写工具约束在一个节点进行执行（即一个节点只执行一次工具就更新checkpointer），也会有不一致的问题。核心原因是写工具是在节点中进行的，写完就将数据库更新了。而checkpointer更新的时机却是在节点结束之后。

这里分为写数据库内部系统和调用第三方外部系统API

对于数据库内部系统的写操作工具调用，如果完成了工具调用的数据库写入，然后commit，工具执行成功了，也有了toolmessage，但是在toolmessage写入checkpointer的时候发生了崩溃，导致toolmessage没被写入到checkpointer，但是实际上工具是运行成功了的，就产生了实际结果和消息列表不一致的情况

对于调用第三方外部系统的API的工具调用，如果已经调用了第三方系统的API了，也有了toolmessage，但是在toolmessage写入checkpointer的时候发生了崩溃，导致toolmessage没被写入到checkpointer，但是实际上工具是运行成功了的，就产生了实际结果和消息列表不一致的情况。会导致第三方外部系统的API被重复调用。
