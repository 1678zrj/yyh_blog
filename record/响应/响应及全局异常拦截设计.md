这里包含两个核心问题：一个是前端与后端对响应对象属性命名的差异，另一个是 API 架构设计中“统一响应格式”的权衡。

### 一、 为什么服务端用 `content`，前端用 `response.data`？

这是因为**后端 Python 框架**与前端 JavaScript HTTP 库（如 Axios）对 HTTP 响应对象的属性命名约定不同。它们本质上是对同一个 HTTP 报文的不同封装：

#### 1. 服务端（FastAPI / Starlette）

在 Python 后端，`Response` 类代表**你要发出去的 HTTP 响应**。Starlette 框架设计时，将响应的 Body 载荷命名为 `content`：

Python

```
# 后端构建响应
response = JSONResponse(
    status_code=200,
    content={"message": "ok"}  # FastAPI/Starlette 的属性名是 content
)
```

#### 2. 客户端（Axios / Fetch）

当响应通过网络传输到前端，前端使用 Axios 发起请求时，Axios 会将接收到的 HTTP 报文解析并封装为一个 JavaScript 对象，其默认约定如下：

JavaScript

```
// 前端接收响应 (Axios)
axios.get('/api/user').then(response => {
    console.log(response.status);  // HTTP 状态码，如 200
    console.log(response.headers); // 响应头
    console.log(response.data);    // 响应体 Body（即后端发送的 content）
});
```

- **如果你用原生的 `fetch`**：获取方式是 `const data = await response.json()`。
- **如果你用 `axios`**：Axios 自动帮解析了 JSON，并把解析后的对象挂载在 `response.data` 属性上。

#### 映射关系对比

| **概念**        | **HTTP 报文结构**   | **FastAPI (Response 属性)** | **前端 Axios (response 属性)** |
| --------------- | ------------------- | --------------------------- | ------------------------------ |
| **状态码**      | `HTTP/1.1 200 OK`   | `status_code`               | `status`                       |
| **响应头**      | `Content-Type: ...` | `headers`                   | `headers`                      |
| **响应体/数据** | `{"success": true}` | **`content`**               | **`data`**                     |

### 二、 正常响应是否需要和异常响应统一格式？

这是一个在 API 设计中非常经典的讨论，目前行业内主要有两种主流方案：

#### 方案 A：全面统一格式（“大包办”模式 / 业务码模式）

无论成功还是失败，所有接口一律返回相同结构的 JSON 外壳，甚至 HTTP 状态码一律给 `200 OK`：

JSON

```
// 成功响应 (HTTP 200)
{
  "success": true,
  "code": 20000,
  "message": "success",
  "data": { "id": 1, "name": "Alice" }
}

// 失败响应 (HTTP 200 或 HTTP 422)
{
  "success": false,
  "code": 40001,
  "message": "用户余额不足",
  "data": null
}
```

- **优点**：前端解析逻辑极度统一，Axios 拦截器写起来非常简单（判断 `res.data.code === 20000` 决定走业务逻辑还是弹提示框）。
- **缺点**：
  1. **破坏 FastAPI 原生优势**：FastAPI 的 `response_model` 和 OpenAPI (Swagger) 自动文档生成会变得臃肿，每个 API 都要套一层包装模型。
  2. **混淆 HTTP 语义**：如果 HTTP 状态码全返回 200，网关（如 Nginx）、监控系统（如 Prometheus）和 CDN 将无法通过 HTTP 状态码判断接口是否健康。

#### 方案 B：RESTful / HTTP 状态码模式（FastAPI 推荐方式）

充分利用 HTTP 状态码区分“请求结果”，**正常响应直接返回业务数据，异常响应返回结构化的错误对象**：

- **正常响应 (HTTP 200 / 201)**：

  JSON

  ```
  {
    "id": 1,
    "name": "Alice"
  }
  ```

- **异常响应 (HTTP 400 / 422 / 500)**：

  JSON

  ```
  {
    "success": false,
    "error": {
      "code": "INSUFFICIENT_BALANCE",
      "message": "用户余额不足"
    }
  }
  ```

- **优点**：

  1. **契合 FastAPI 原生设计**：路由函数只需专注于返回 Pydantic 模型，Swagger UI 自动呈现清晰的数据结构。
  2. **利用 Axios 错误处理**：Axios 在收到 `4xx` 或 `5xx` 状态码时，会自动触发 `.catch()` 或进入响应拦截器的 `error` 回调，逻辑天然分离。

### 三、 最佳实践建议

在 FastAPI 开发中，**更推荐使用方案 B**。

前端可以通过 **Axios 拦截器**非常干净地处理这种结构：

```javascript
// 前端 Axios 拦截器设置
axios.interceptors.response.use(
  // 1. 状态码 2xx 走这里 (正常响应)
  (response) => {
    // 此时 response.data 就是干净的业务数据，例如 { id: 1, name: 'Alice' }
    return response.data; 
  },
  // 2. 状态码非 2xx 走这里 (异常响应)
  (error) => {
    if (error.response) {
      // 这里的 error.response.data 就是后端 JSONResponse 里的 content
      const { code, message } = error.response.data.error || {};
      showToast(`错误 [${code}]: ${message}`);
    }
    return Promise.reject(error);
  }
);
```

**总结**：

1. 后端 `Response.content` 经过网络发给前端后，在 Axios 中对应的就是 `response.data`，你的记忆完全没错。
2. 异常统一封成 `JSONResponse` 并带上业务 `code` 非常合理；但**正常数据没必要为了强行统一而额外包裹一层 `data` 属性**，直接返回 Pydantic 模型并在前端利用 HTTP 状态码进行拦截分发是 FastAPI 项目中最普遍且高效的做法。

### 问：请提供一个在 FastAPI 中配置全局 Exception Handler 统一拦截自定义异常并返回自定义 JSON 结构的完整代码示例。

这是一个在 FastAPI 中配置全局异常拦截的完整代码示例，包含了**自定义业务异常类**、**全局异常处理器**以及**重写默认 422 校验异常**（保证整个 API 错误结构完全统一）。

```python
from typing import Any, Dict, Optional
from fastapi import FastAPI, Request, status
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from pydantic import BaseModel

# ==========================================
# 1. 定义自定义业务异常基类
# ==========================================
class BusinessException(Exception):
    def __init__(
        self,
        code: str,
        message: str,
        status_code: int = status.HTTP_400_BAD_REQUEST,
        extra_data: Optional[Dict[str, Any]] = None,
    ):
        self.code = code
        self.message = message
        self.status_code = status_code
        self.extra_data = extra_data or {}


# 扩展具体的子类异常（可选，便于代码复用）
class UserNotFoundException(BusinessException):
    def __init__(self, user_id: int):
        super().__init__(
            code="USER_NOT_FOUND",
            message=f"ID 为 {user_id} 的用户不存在",
            status_code=status.HTTP_404_NOT_FOUND,
            extra_data={"user_id": user_id},
        )


class InsufficientBalanceException(BusinessException):
    def __init__(self, current: float, required: float):
        super().__init__(
            code="INSUFFICIENT_BALANCE",
            message="账户余额不足，无法完成支付",
            status_code=status.HTTP_400_BAD_REQUEST,
            extra_data={"current_balance": current, "required_balance": required},
        )


# ==========================================
# 2. 实例化 FastAPI 并注册全局异常处理器
# ==========================================
app = FastAPI(title="Unified Exception Handling Demo")


# ① 拦截自定义业务异常
@app.exception_handler(BusinessException)
async def business_exception_handler(request: Request, exc: BusinessException):
    return JSONResponse(
        status_code=exc.status_code,
        content={
            "success": False,
            "error": {
                "code": exc.code,
                "message": exc.message,
                **exc.extra_data,  # 展开额外的自定义字段
            },
        },
    )


# ② 重写 FastAPI 默认的 422 参数校验异常，保持错误响应格式统一
@app.exception_handler(RequestValidationError)
async def validation_exception_handler(request: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
        content={
            "success": False,
            "error": {
                "code": "VALIDATION_ERROR",
                "message": "请求参数校验失败",
                "details": exc.errors(),  # 包含具体是哪个参数校验失败
            },
        },
    )


# ③ (可选) 兜底拦截系统未捕获的 500 异常
@app.exception_handler(Exception)
async def unhandled_exception_handler(request: Request, exc: Exception):
    # 此处可接入日志系统 (如 loguru) 记录堆栈信息 logger.error(exc)
    return JSONResponse(
        status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
        content={
            "success": False,
            "error": {
                "code": "INTERNAL_SERVER_ERROR",
                "message": "服务器内部错误，请稍后重试",
            },
        },
    )


# ==========================================
# 3. 编写测试路由
# ==========================================
class UserOut(BaseModel):
    id: int
    username: str


# 正常响应：直接返回模型/数据，不套包装层
@app.get("/users/{user_id}", response_model=UserOut)
async def get_user(user_id: int):
    if user_id == 0:
        # 触发具体的业务子类异常
        raise UserNotFoundException(user_id=user_id)
    if user_id == 99:
        # 触发带额外扩展数据的业务异常
        raise InsufficientBalanceException(current=50.0, required=100.0)

    return {"id": user_id, "username": f"user_{user_id}"}


if __name__ == "__main__":
    import uvicorn

    uvicorn.run(app, host="127.0.0.1", port=8000)
```
