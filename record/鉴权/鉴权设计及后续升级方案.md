### 这和RBAC有关系吗

**是的，这完全就是 RBAC（基于角色的访问控制，Role-Based Access Control）的核心实现。**



你写的这段代码不仅与 RBAC 密切相关，而且是 FastAPI 中非常标准、地道的 RBAC 实现方式。



## 为什么说这就是 RBAC？

RBAC 的核心思想是：**不直接给用户分配具体权限，而是把权限绑定到“角色”（Role）上，再把“角色”分配给用户。系统根据用户当前的角色来判断能否访问某个资源。**



对照你的代码：



1. **用户与角色的绑定**：`current_user.role` 保存了用户的角色（如 `STUDENT`、`TEACHER`、`ADMIN`）。
2. **基于角色的权限判定**：`get_teacher` 和 `get_admin` 作为 FastAPI 的依赖项（Dependency），在请求进入路由前校验 `current_user.role`。
3. **拦截未授权请求**：如果不满足条件，抛出 HTTP `403 FORBIDDEN`，阻止非法访问。

## 你代码中的一个亮点：层级角色（Hierarchical RBAC）

你在代码中使用了比较运算符：



Python

```
if current_user.role < UserRole.TEACHER:
```

这说明你的 `UserRole` 应该是一个带有顺序的枚举（比如 `IntEnum`），定义了角色的等级关系（例如：`STUDENT = 1`, `TEACHER = 2`, `ADMIN = 3`）。



这种方式属于 RBAC 的高级变体——**层级 RBAC（HRBAC）**。它的好处是 **高等级角色自动继承低等级角色的权限**（管理员默认拥有教师的所有权限），避免了反复判断 `role == TEACHER or role == ADMIN` 的繁琐。



## 随着项目变大，当前写法可能的瓶颈

虽然你现在的代码很清晰，但当系统的角色变多（比如新增 `TA`、`PRINCIPAL`、`FINANCE`）时，为每个角色单独写一个依赖函数（`get_teacher`、`get_admin`、`get_ta`...）会导致重复代码激增。



### 优雅的优化方式：可调用类（Callable Class）

利用 FastAPI 的依赖项可以是类实例的特性，你可以把这些检查逻辑封装成一个通用检查器：



Python

```
from typing import List
from fastapi import Depends, HTTPException, status
from app.models.table import User, UserRole

class RoleChecker:
    def __init__(self, allowed_roles: List[UserRole]):
        self.allowed_roles = allowed_roles

    def __call__(self, current_user: User = Depends(get_current_user)) -> User:
        # 假设 UserRole 支持排序/比较
        max_user_role = current_user.role
        
        # 校验用户的角色等级是否达到准入门槛中的最低要求，或是否在允许列表中
        if not any(max_user_role >= role for role in self.allowed_roles):
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="权限不足：无法访问该资源"
            )
        return current_user

# 定义复用检查器
require_teacher = RoleChecker([UserRole.TEACHER])
require_admin = RoleChecker([UserRole.ADMIN])
```

在路由定义时使用：

Python

```
@router.get("/courses/manage", dependencies=[Depends(require_teacher)])
async def manage_courses():
    return {"message": "教师或管理员可查看"}
```

在探讨“企业级 RBAC”之前，我们先用一句话说明你的“迷你学习通”目前遇到的核心痛点：



> **“在学习通这样的系统里，老师 A 能修改老师 B 的课程吗？”**

按你之前的逻辑：只要 `user.role >= TEACHER`，老师 A 就能访问所有需要教师权限的接口。但**实际上老师 A 只能修改“自己教的课”**。这种限制**仅靠传统的 RBAC 是无法解决的**。



下面我们来看看企业级 RBAC 是怎样的，以及针对你的“迷你学习通”模型应该如何改造。



## 一、 企业级 RBAC vs 传统 RBAC

企业级 RBAC（通常指 **RBAC1 ~ RBAC3** 模型）的核心变更是引入了“权限（Permission/Privilege）”的概念，解除“用户”与“硬编码角色逻辑”的强绑定。



```
【传统/简单 RBAC】 (你目前的方案)
User ───(包含)───> Role (Enum) ───(硬编码逻辑)───> if user.role == TEACHER

【企业级 RBAC】 (五表模型)
User <───(多对多)───> Role <───(多对多)───> Permission ───> 校验接口/操作
 (张三)             (教务老师)             (course:delete)
```

### 1. 标准企业级 RBAC 的数据库设计（五表模型）

企业级 RBAC 通常包含 **5 张核心表**：



1. **User** (用户表)
2. **Role** (角色表)
3. **UserRole** (用户-角色关联表)
4. **Permission** (权限表，如 `course:create`, `assignment:grade`)
5. **RolePermission** (角色-权限关联表)

通过这种解耦：



- 增加一个新角色（如“助教 TA”）**不需要修改任何 Python 代码**，只需在数据库加一条 Role，并勾选对应的 Permission 即可。
- 路由鉴权不再判断 `role == TEACHER`，而是判断 `has_permission("course:update")`。

## 二、 迷你学习通真正需要的：ABAC（基于属性的访问控制）/ 数据级权限

在高校教务或学习通系统中，仅有 RBAC 是不够的。因为你面临的核心问题是：**数据所有权与数据范围（Data Scope）**。



在教育系统中有两类权限：



| **权限类型**                 | **例子**                     | **实现机制**                                           |
| ---------------------------- | ---------------------------- | ------------------------------------------------------ |
| **功能权限 (RBAC)**          | 能否打开“发布作业”这个页面？ | RBAC (角色是否有 `assignment:create` 权限)             |
| **数据权限 (ABAC/数据过滤)** | 老师能不能批改这批作业？     | **数据所有权校验** (这个作业属于老师 A 所在的课程吗？) |

## 三、 针对你的项目的“渐进式”改造方案

如果直接重构成完整的企业级 RBAC (5表模型)，对于迷你学习通项目可能有点重。**推荐采用“精简版 RBAC + 资源所有权校验 (Owner Check)”** 的混合架构：



### 1. 架构升级：引入资源所有权校验 (Resource Ownership)

#### ① 编写动态所有权校验依赖项（Policy/Checker）

我们可以利用 FastAPI Depends 的强大特性，动态提取请求参数并校验：



Python

```
from fastapi import Depends, HTTPException, status
from app.models.table import User, Course, UserRole
from app.services.course_service import get_course_by_id  # 假设你有一个查询方法

# 校验当前用户是否是某门课程的“主讲教师”或“管理员”
async def require_course_owner_or_admin(
    course_id: int,  # FastAPI 会自动从 Path/Query 参数中获取 course_id
    current_user: User = Depends(get_current_user),
    db_session = Depends(get_db)
) -> Course:
    # 1. 超级管理员直接放行
    if current_user.role == UserRole.ADMIN:
        course = await get_course_by_id(course_id, db_session)
        if not course:
            raise HTTPException(status_code=404, detail="课程不存在")
        return course

    # 2. 查询课程并校验归属
    course = await get_course_by_id(course_id, db_session)
    if not course:
        raise HTTPException(status_code=404, detail="课程不存在")

    # 3. 核心校验：当前用户 ID 是否等于课程的 teacher_id
    if course.teacher_id != current_user.id:
        raise HTTPException(
            status_code=status.HTTP_403_FORBIDDEN,
            detail="越权操作：你不是这门课程的任课教师"
        )
        
    return course
```

#### ② 在路由中使用

### 2. 数据库扩展：如果一定要做企业级 RBAC 模型

如果你希望在 SQLModel 中将其扩展为企业级的 **角色-权限解耦模型**，可以添加如下表结构：



Python

```
from typing import List, Optional
from sqlmodel import Field, SQLModel, Relationship

# 1. 权限表 (定义具体的操作权限)
class Permission(SQLModel, table=True):
    __tablename__ = "permission"
    id: Optional[int] = Field(default=None, primary_key=True)
    code: str = Field(unique=True, index=True, description="权限标识，如 course:create, assignment:grade")
    name: str = Field(description="权限名称，如 创建课程, 批改作业")

# 2. 角色-权限 中介表
class RolePermissionLink(SQLModel, table=True):
    __tablename__ = "role_permission_link"
    role_id: int = Field(foreign_key="role.id", primary_key=True)
    permission_id: int = Field(foreign_key="permission.id", primary_key=True)

# 3. 角色表 (替代原有的 Enum)
class Role(SQLModel, table=True):
    __tablename__ = "role"
    id: Optional[int] = Field(default=None, primary_key=True)
    name: str = Field(unique=True, description="角色名，如 教师, 助教, 学生")
    code: str = Field(unique=True, description="角色代码，如 TEACHER, TA, STUDENT")
    
# 4. 用户-角色 中介表 (支持一个用户多个角色，比如既是学生又是助教)
class UserRoleLink(SQLModel, table=True):
    __tablename__ = "user_role_link"
    user_id: int = Field(foreign_key="user.id", primary_key=True)
    role_id: int = Field(foreign_key="role.id", primary_key=True)
```

### 问：关于你说的依然无法解决“数据所有权（ABAC/数据级权限）”这种细粒度的问题，为什么不通过service层的业务代码进行判断呢？然后粗粒度的鉴权通过Depends判断呢？企业级做法是怎样的？

**你的想法完全正确！这不仅可行，而且是目前中大型企业中最主流、最务实落地的方式之一。**



你刚才思考的这个方案，在软件架构中被称为 **“分层鉴权（Layered Authorization）”**：



- **网关/入口层（FastAPI `Depends`）**：负责 **粗粒度** 鉴权（身份认证、功能级 RBAC 权限，如“当前用户是不是老师？有没有修改课程的权限？”）。
- **业务/服务层（Service Layer）**：负责 **细粒度** 鉴权（数据级 ABAC / 归属校验，如“这门课是不是这个老师教的？”）。

## 为什么这种做法在企业中大受欢迎？

### 1. 性能与数据库查询的最优解

如果在 FastAPI 的 `Depends` 里做数据归属校验，往往需要先查一次数据库（把课程记录查出来判断 `teacher_id`），进入 Service 层后，Service 又要查一次数据库。

**把细粒度校验放在 Service 层，可以在查询数据（如 `SELECT` 或 `UPDATE`）的同时顺便完成校验，避免重复查询数据库。**



### 2. 符合“单一职责原则”与业务内聚

数据归属逻辑本质上就是**业务逻辑**的一部分（例如：“只有当课程处于草稿状态且作者是当前用户时才能删除”）。这种复杂的组合条件，写在 Service 层比写在路由的依赖项里更清晰、更容易进行单元测试（Unit Test）。



## 企业级 RBAC/ABAC 的主流落地架构

在实际的企业级项目（尤其是中大型后端架构）中，针对细粒度数据权限，通常有以下几种常见的做法：



### 做法一：Service 层显式校验（你的方案）

这是最普遍的做法。在 Service 方法中，获取数据后进行防御性校验。



Python

```
# app/services/course_service.py
class CourseService:
    async def update_course(self, course_id: int, user: User, update_data: dict):
        course = await self.course_repo.get(course_id)
        if not course:
            raise NotFoundException("课程不存在")
            
        # 1. 业务/数据权限校验：超级管理员 或 课程创建者 才能修改
        if user.role != UserRole.ADMIN and course.teacher_id != user.id:
            raise ForbiddenException("无权修改非本人创建的课程")
            
        # 2. 执行更新
        return await self.course_repo.update(course, update_data)
```

- **优点**：简单直接、性能高、非常适合单体（GET/PUT/DELETE）资源操作。
- **缺点**：如果团队规范不够好，开发人员可能会在某个 Service 接口中**漏写**归属校验代码。

### 做法二：数据范围 SQL 过滤（Data Scope / 针对列表查询）

对于 **“获取课程列表”** 这种场景，你不可能把数据库里的几万条课程全部取到内存里，再用 `if course.teacher_id == user.id` 去过滤。



企业级做法是将数据权限写进 **SQL 查询条件（WHERE 子句）** 中：



Python

```
# app/services/course_service.py
class CourseService:
    async def get_teacher_courses(self, user: User) -> list[Course]:
        # 管理员看全部，普通教师只在 WHERE 条件中查自己的
        stmt = select(Course)
        if user.role != UserRole.ADMIN:
            stmt = stmt.where(Course.teacher_id == user.id)
            
        return await self.db.exec(stmt)
```

- **核心思想**：**“不符合权限的数据，根本就不从数据库里查出来”**。

### 做法三：FastAPI 动态依赖项注入（声明式校验）

如果你觉得在 Service 层每次手写 `if course.teacher_id != user.id` 容易漏写，企业中也有人利用 FastAPI 的依赖注入，把“数据查取”和“归属校验”打包成一个通用依赖：



Python

```
# dependencies/permissions.py
def require_resource_owner(model: Type[SQLModel], owner_field: str = "teacher_id"):
    async def checker(
        item_id: int, 
        current_user: User = Depends(get_current_user),
        db: AsyncSession = Depends(get_db)
    ):
        item = await db.get(model, item_id)
        if not item:
            raise HTTPException(404, "资源不存在")
            
        # 动态校验资源上的 owner_field 是否等于当前用户 ID
        if current_user.role != UserRole.ADMIN and getattr(item, owner_field) != current_user.id:
            raise HTTPException(403, "无权操作该资源")
            
        return item # 直接把查出来的资源对象塞给 Router
    return checker

# 路由定义
@router.put("/courses/{item_id}")
async def update_course(
    course: Course = Depends(require_resource_owner(Course, owner_field="teacher_id")),
    service: CourseService = Depends()
):
    # 此处无需再查库，也无需再校验所有权，course 已经是校验通过的对象
    return await service.update(course)
```

### 做法四：集中式 Authorization Policy 引擎（大型微服务架构）

在非常庞大的企业级微服务（如阿里云、腾讯云控制台）中，会引入专门的权限引擎：



- **PyCasbin / OPA (Open Policy Agent)**：把权限规则抽离为独立服务或配置文件。
- 编写声明式规则（Policy）：`p, teacher, course_resource, write, owner == true`。
- 业务服务在处理请求前，调用权限引擎问一句：*“User A 能否对 Course 123 执行 Update 操作？”*

## 六、 文件系统底层（`FileRecord`）—— **最隐蔽的越权盲区**

很多初学者写系统时，只防了业务接口，却忽略了**底层文件的越权获取**。



- **隐患点**：如果你的文件下载接口是 `GET /files/{file_record_id}/download`。
- **致命漏洞**：如果用户只要知道一个 `file_record_id` 就能直接下载，那别人只需要从 `1` 遍历攻击到 `10000`，就能把全站的作业附件、老师课件、学生提交的私人文件**全部拖库下载**。

> **必须鉴权策略**：
>
> 文件下载接口**不能仅通过 `file_record_id` 校验**。必须通过上层业务关系（如：这是 `CourseResource` 还是 `SubmissionFile`），判断当前 `user_id` 是否拥有访问该业务记录的权限，校验通过后再吐出存储路径。

## 总结：你的权限判断逻辑公式

在写接口时，只要带入这套公式，代码安全性就会大幅提升：



$$\text{最终放行条件} = \text{未禁用} \land \text{角色符合 (RBAC)} \land \left( \text{是管理员} \lor \text{是资源所有者 (ABAC)} \right)$$

掌握了这些防范点，你的“迷你学习通”在安全设计上就已经打败了绝大多数学生作品，具备了企业级的安全防御意识！

```
from app.models.table import User, UserRole
from app.core.permissions import Permission, ROLE_PERMISSIONS

# 统一粗粒度权限校验工厂
def require_perm(*required_perms: Permission):
    async def checker(user: User = Depends(get_current_user)) -> User:
        # 管理员直接放行
        if user.role == UserRole.ADMIN:
            return user
            
        user_perms = ROLE_PERMISSIONS.get(user.role, set())
        if not set(required_perms) & user_perms:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail=f"权限不足，需要以下权限之一：{[p.value for p in required_perms]}"
            )
        return user
    return checker
```

## 🛡️ 第二步：打造通用依赖项工厂 (`app/api/deps.py`)

拦截未带权限的角色，保护路由入口。



Python

```
from fastapi import Depends, HTTPException, status
from app.models.table import User, UserRole
from app.core.permissions import Permission, ROLE_PERMISSIONS
from app.services.user_service import UserService
from fastapi.security import OAuth2PasswordBearer

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/v1/auth/login")


async def get_current_user(
    token: str = Depends(oauth2_scheme),
    user_service: UserService = Depends()
) -> User:
    user = await user_service.access_token(access_token=token)
    if not user:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="身份认证凭据无效"
        )
    return user


def require_perm(*required_perms: Permission):
    """
    粗粒度权限校验工厂依赖项
    用例: Depends(require_perm(Permission.COURSE_CREATE))
    """
    async def checker(current_user: User = Depends(get_current_user)) -> User:
        # 管理员通道：直接放行
        if current_user.role == UserRole.ADMIN:
            return current_user

        user_perms = ROLE_PERMISSIONS.get(current_user.role, set())
        
        # 校验是否有需要的权限之一
        if not (set(required_perms) & user_perms):
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail=f"权限不足：需要以下权限之一 {[p.value for p in required_perms]}"
            )
        return current_user

    return checker
```

```
from sqlmodel import select, AsyncSession
from fastapi import HTTPException, status
from app.models.table import User, Course, UserRole, Enrollment


class CourseService:
    def __init__(self, db: AsyncSession):
        self.db = db

    async def update_course(self, course_id: int, current_user: User, update_data: dict) -> Course:
        course = await self.db.get(Course, course_id)
        if not course:
            raise HTTPException(status_code=404, detail="课程不存在")

        # 🔑 ABAC 校验：不是管理员且不是该课任课教师，拦截！
        if current_user.role != UserRole.ADMIN and course.teacher_id != current_user.id:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="越权操作：你不是这门课程的任课教师"
            )

        for key, value in update_data.items():
            setattr(course, key, value)

        self.db.add(course)
        await self.db.commit()
        await self.db.refresh(course)
        return course

    async def get_my_courses(self, current_user: User) -> list[Course]:
        """按用户角色动态追加 WHERE 条件，实现数据隔离"""
        stmt = select(Course)

        if current_user.role == UserRole.TEACHER:
            # 教师只看自己创建的课
            stmt = stmt.where(Course.teacher_id == current_user.id)
        elif current_user.role == UserRole.STUDENT:
            # 学生只看自己选修的课
            stmt = stmt.join(Enrollment, Course.id == Enrollment.course_id)\
                       .where(Enrollment.student_id == current_user.id)

        result = await self.db.exec(stmt)
        return result.all()
```

### 2. 批改与提交服务 (`app/services/submission_service.py`)

Python

```
from sqlmodel import select, AsyncSession
from fastapi import HTTPException, status
from app.models.table import User, Submission, Assignment, Course, UserRole


class SubmissionService:
    def __init__(self, db: AsyncSession):
        self.db = db

    async def grade_submission(self, submission_id: int, score: float, feedback: str, current_user: User) -> Submission:
        # 联表查询 Submission -> Assignment -> Course
        stmt = (
            select(Submission, Course.teacher_id)
            .join(Assignment, Submission.assignment_id == Assignment.id)
            .join(Course, Assignment.course_id == Course.id)
            .where(Submission.id == submission_id)
        )
        res = await self.db.exec(stmt)
        row = res.first()

        if not row:
            raise HTTPException(status_code=404, detail="提交记录不存在")

        submission, course_teacher_id = row

        # 🔑 ABAC 校验：该老师是否有权批改此课程下的作业
        if current_user.role != UserRole.ADMIN and course_teacher_id != current_user.id:
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail="越权操作：你无法批改非本人课程的作业"
            )

        submission.score = score
        submission.feedback = feedback
        self.db.add(submission)
        await self.db.commit()
        await self.db.refresh(submission)
        return submission
```

## 1. 关于闭包与 `Depends` 传参：你的理解 100% 正确！

FastAPI 的 `Depends(fn)` 规定必须传入一个**可调用对象（Callable）**。



- 如果写成普通的函数：

  Python

  ```
  async def check_perm(user: User = Depends(get_current_user)):
      ...
  ```

  `Depends(check_perm)` 没法给 `check_perm` 额外传参告诉它“当前接口要检查哪个权限”。

- **闭包（工厂函数）的做法：**

  Python

  ```
  def require_perm(*required_perms: Permission):  # 1. 外层接收你想配置的参数
      async def checker(user: User = Depends(get_current_user)): # 2. 内层才是真正的依赖项
          # 闭包捕获了外层的 required_perms
          ...
      return checker # 3. 把定制好的函数返回出去
  ```

  在路由里写 `Depends(require_perm(Permission.COURSE_CREATE))` 时：

  1. Python 首先执行 `require_perm(...)`；
  2. 它返回了一个**记住了所需权限**的 `checker` 函数；
  3. `Depends` 拿到了这个 `checker` 并交给 FastAPI 去执行。

> 💡 **补充一个小知识**：除了闭包，Python 的 **可调用类（Class with `__call__`）** 也是实现这一目的的经典企业级写法，两者本质上是一样的。

## 2. 关于 `*args: Permission` 的类型注解机制

你的直觉很敏锐，但这里有一个 Python 官方类型注解（PEP 484）的设计规范：



### ① `*args` 打包成的是元组（Tuple）

在 Python 运行时，`*required_perms` 会将所有传入的位置参数自动打包为一个 **`tuple`（不可变元组）**，而不是 `list`。



### ② 为什么类型注解写 `Permission` 而不是 `list[Permission]`？

在 Python 的 Type Hint 规范中：**给 `\*args` 标注类型时，标的是“每一个单独参数的类型”，而不是外层容器的类型。**



- **正确写法**：

  Python

  ```
  def require_perm(*required_perms: Permission):
      # 表示每一个传进来的参数都必须是 Permission 枚举
      # 在函数体内部，required_perms 的类型自动推导为 tuple[Permission, ...]
  ```

- **如果写成 `\*required_perms: list[Permission]` 会发生什么？**

  IDE（如 VS Code / PyCharm）和类型检查器（MyPy）会认为你希望传入多个**列表**，比如必须这样调用：

  `require_perm([Permission.COURSE_CREATE], [Permission.COURSE_UPDATE])`，这显然与我们的初衷不符。

## 3. 路由中可以传入多个权限吗？

**完全可以！** 这正是使用 `*required_perms` 的精妙之处。



你可以传 1 个、2 个甚至更多权限作为参数，逗号隔开即可：



Python

```
# 示例 1：只需要 1 个权限
@router.post("/courses")

    _: User = Depends(require_perm(Permission.COURSE_CREATE))
):
    ...

# 示例 2：传入多个权限（只要满足其中任意一个即可通过）
@router.get("/courses/{course_id}/management-view")
async def view_course_management(
    course_id: int,
    # 只要有 COURSE_UPDATE 或 COURSE_DELETE 权限之一，就能进入
    _: User = Depends(require_perm(Permission.COURSE_UPDATE, Permission.COURSE_DELETE))
):
    ...
```

### 为什么能支持多个？

因为我们在函数体内部使用了**集合交集运算**：



Python

```
# 1. 传入的元组转为集合：set(required_perms) -> {Permission.COURSE_UPDATE, Permission.COURSE_DELETE}
# 2. 当前用户拥有的权限：user_perms
# 3. & 计算两者的交集：如果交集非空，说明用户至少满足其中一个权限！
if not (set(required_perms) & user_perms):
    raise HTTPException(...)
```

这种写法既保证了单权限校验的简洁（直接传一个即可），又兼顾了多权限场景（OR 条件）的扩展性。

## 1. 如果 `*args` 接收的参数类型不止一种，怎么做类型注解？

## 2. 关于 `set(required_perms) & user_perms` 的疑问

### ① `&` 是专门计算集合交集的吗？

**是的！**

在 Python 中，当操作数是 `set`（集合）时，`&` 运算符被重载为**集合交集运算（Intersection）**，即找出两个集合共同拥有的元素。



Python 为 `set` 提供了一整套专用的数学集合运算符：



| **运算符** | **数学概念**                   | **说明**                 | **示例**                                    |
| ---------- | ------------------------------ | ------------------------ | ------------------------------------------- |
| **`&`**    | **交集** ($A \cap B$)          | 两边都有的元素           | `{1, 2} & {2, 3}` $\rightarrow$ `{2}`       |
| **`|`**    | **并集** ($A \cup B$)          | 两边的所有元素去重合并   | `{1, 2} | {2, 3}` $$\rightarro$ `{1, 2, 3}` |
| **`-`**    | **差集** ($A \setminus B$)     | 在 A 中但不在 B 中的元素 | `{1, 2, 3} - {2, 3}` $\rightarrow$ `{1}`    |
| **`^`**    | **对称差集** ($A \triangle B$) | 只在 A 或只在 B 中的元素 | `{1, 2} ^ {2, 3}` $\rightarrow$ `{1, 3}`    |

### ② 计算交集的对象类型必须一致吗？为什么要把元组转成 `set`？

**使用 `&` 运算符时，两边的类型必须都是 `set`（或 `frozenset`），不能一边是元组一边是集合！**



如果在 Python 中直接用元组和集合做 `&` 运算，会直接触发 `TypeError` 崩溃：



Python

```
# 错误示范：
required_perms_tuple = (Permission.COURSE_CREATE,)
user_perms_set = {Permission.COURSE_CREATE, Permission.COURSE_UPDATE}

# 运行时会报错：TypeError: unsupported operand type(s) for &: 'tuple' and 'set'
result = required_perms_tuple & user_perms_set 
```

这就是为什么代码里必须写 `set(required_perms)` 的原因：

`*required_perms` 在接收参数后打包成的是一个 `tuple`，必须先用 `set(...)` 将其转换为集合，才能与 `user_perms` 进行 `&` 运算。



### 💡 补充：`&` 运算符与 `.intersection()` 方法的区别

Python 集合其实提供了两种计算交集的方式：



Python

```
# 方式 1：使用 & 运算符（要求两边都必须是 set）
set(required_perms) & user_perms

# 方式 2：使用 .intersection() 方法（参数可以是任何可迭代对象，包括 tuple、list）
user_perms.intersection(required_perms)
```

如果你不想显式写 `set(required_perms)`，也可以利用方法调用的特性改写为：



Python

```
# .intersection() 会自动把传入的 tuple/list 转为集合去比较
if not user_perms.intersection(required_perms):
    raise HTTPException(...)
```

两种写法在性能和结果上几乎完全一致，不过 `&` 运算符因为符号化、简洁，在现代 Python 代码中更加常用。

### 问：请帮我写出标准五表 RBAC 模型在 SQLModel 下的定义，包含用户、角色、权限以及对应的中间表。

在 SQLModel 中实现标准的**企业级五表 RBAC 模型**，核心在于利用 `Relationship` 和 `link_model` 处理两组多对多（Many-to-Many）关系：



- **用户与角色**：一个用户可以拥有多个角色，一个角色可以分配给多个用户。
- **角色与权限**：一个角色可以包含多个权限，一个权限可以被多个角色共享。

```
        foreign_key="sys_role.id",
        primary_key=True,
        description="角色ID"
    )
    permission_id: int = Field(
        foreign_key="sys_permission.id",
        primary_key=True,
        description="权限ID"
    )

# 2. 核心实体表 (Entity Tables)
# =====================================================================

class Permission(SQLModel, table=True):
    """权限表：定义系统所有的原子操作权限"""
    __tablename__ = "sys_permission"

    id: Optional[int] = Field(default=None, primary_key=True)
    code: str = Field(

        link_model=RolePermissionLink
    )

    """用户表"""
    __tablename__ = "sys_user"

    id: Optional[int] = Field(default=None, primary_key=True)

    real_name: str = Field(description="真实姓名")

    avatar: Optional[str] = Field(default=None, description="头像 URL")
```

## ⚡ 核心配套：基于五表高效查询用户权限

升级为五表模型后，鉴权时最核心的操作是**一次性拉取用户拥有的所有权限代码**。在 SQLAlchemy / SQLModel 异步引擎下，可以通过三张表的 `JOIN` 语句单次查询完成：



Python

```
from sqlmodel import select
from sqlmodel.ext.asyncio.session import AsyncSession


async def get_user_permission_codes(user_id: int, db: AsyncSession) -> set[str]:
    """
    通过联表查询，一次性获取某用户所拥有的所有权限 code 集合
    SQL: UserRoleLink -> RolePermissionLink -> Permission
    """
    stmt = (
        select(Permission.code)
        .join(RolePermissionLink, RolePermissionLink.permission_id == Permission.id)
        .join(UserRoleLink, UserRoleLink.role_id == RolePermissionLink.role_id)
        .where(UserRoleLink.user_id == user_id)
        .distinct()
    )
    result = await db.exec(stmt)
    return set(result.all())
```

## 💡 五表模型的设计亮点

1. **联合主键设计**：

   中间表 `UserRoleLink` 和 `RolePermissionLink` 将两个外键字段同时设为 `primary_key=True`。这保证了**复合主键约束**，既能在数据库层面杜绝重复给同一个用户赋予相同角色，又无需额外生成自增 `id` 字段。

2. **唯一索引规范**：

   `Permission.code` 和 `Role.code` 均设置了 `unique=True, index=True`，保证权限字符（如 `course:create`）在全局唯一且索引检索效率极高。

3. **ORM 双向导航**：

   通过 `Relationship(..., link_model=...)` 声明后，可以直接通过 `user.roles` 获取所有角色，或者通过 `role.permissions` 获取该角色拥有的权限列表。

### 问：如何重构之前的 require_perm 依赖项，使其通过数据库动态读取五表模型中的用户权限并进行校验？

在五表模型下，由于用户的角色和权限都存储在数据库中，`require_perm` 依赖项需要注入**数据库会话（`AsyncSession`）**，在请求进入时动态完成**联表查询与权限集合比对**。



## 1. 编写权限查询服务 (`app/services/rbac_service.py`)

首先封装一个通用的权限查询函数，负责从数据库提取指定用户的全部权限代码（Code），并处理超级管理员放行逻辑：



Python

```
from typing import Set
from sqlmodel import select
from sqlmodel.ext.asyncio.session import AsyncSession
from app.models.table import Permission, Role, UserRoleLink, RolePermissionLink


class RBACService:
    @staticmethod
    async def get_user_permission_codes(user_id: int, db: AsyncSession) -> Set[str]:
        """查询用户拥有的全部权限 Code 集合"""
        stmt = (
            select(Permission.code)
            .join(RolePermissionLink, RolePermissionLink.permission_id == Permission.id)
            .join(UserRoleLink, UserRoleLink.role_id == RolePermissionLink.role_id)
            .where(UserRoleLink.user_id == user_id)
            .distinct()
        )
        result = await db.exec(stmt)
        return set(result.all())

    @staticmethod
    async def is_admin(user_id: int, db: AsyncSession) -> bool:
        """检查用户是否具有超级管理员 (ADMIN) 角色"""
        stmt = (
            select(Role.id)
            .join(UserRoleLink, UserRoleLink.role_id == Role.id)
            .where(UserRoleLink.user_id == user_id, Role.code == "ADMIN")
        )
        result = await db.exec(stmt)
        return result.first() is not None
```

## 2. 重构 `require_perm` 依赖项 (`app/api/deps.py`)

在 `checker` 闭包内部，同时依赖 `get_current_user` 和 `get_db`：



Python

```
from typing import Union
from fastapi import Depends, HTTPException, status
from sqlmodel.ext.asyncio.session import AsyncSession

from app.core.database import get_db          # 你的 AsyncSession 生成器
from app.models.table import User
from app.services.user_service import UserService
from app.services.rbac_service import RBACService
from fastapi.security import OAuth2PasswordBearer

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/api/v1/auth/login")


async def get_current_user(
    token: str = Depends(oauth2_scheme),
    user_service: UserService = Depends()
) -> User:
    user = await user_service.access_token(access_token=token)
    if not user:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="身份凭据无效或已过期"
        )
    if not user.is_active:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="该账号已被禁用"
        )
    return user


def require_perm(*required_perms: str):
    """
    五表 RBAC 动态权限校验依赖项工厂
    支持传入多个权限，只要满足其中任意一个即可放行 (OR 关系)
    """
    async def checker(
        current_user: User = Depends(get_current_user),
        db: AsyncSession = Depends(get_db)
    ) -> User:
        # 1. 超级管理员拥有全量特权，直接放行
        if await RBACService.is_admin(current_user.id, db):
            return current_user

        # 2. 从数据库拉取当前用户的权限集合
        user_perms = await RBACService.get_user_permission_codes(current_user.id, db)

        # 3. 校验交集：判断用户权限集是否覆盖了所需权限
        if not (set(required_perms) & user_perms):
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail=f"权限不足：需要拥有以下权限之一：{list(required_perms)}"
            )

        return current_user

    return checker
```

## ⚡ 性能进阶优化：单次请求内的上下文缓存

五表模型会导致每个带鉴权的请求多执行一次 `JOIN` 查询。如果在同一个请求中需要执行多次权限判断，建议将权限集合缓存到 `request.state` 中，实现**单次请求只查一次 DB**：

Python

```

    if not hasattr(request.state, "user_perms"):
        request.state.user_perms = await RBACService.get_user_permission_codes(user_id, db)
    return request.state.user_perms
```

### 问：如何在 FastAPI 中结合 Redis 缓存用户的权限列表，并在用户角色变更时进行缓存清除？

在权限系统中，使用 **Cache-Aside（旁路缓存）** 模式将权限集合存入 Redis 是最高效的做法：读取时优先查 Redis，未命中时回源查询数据库并写入 Redis；当用户角色或权限发生变更时，**主动删除缓存（Cache Eviction）**，实现强一致与高性能。



## 1. 核心架构与 Key 设计

Plaintext

```
[鉴权请求] ──► 1. 查 Redis (Key: "rbac:user:{user_id}:perms")
                   ├─► [命中] ──► 直接执行内存交集运算 (耗时 < 1ms)
                   └─► [未命中] ──► 查 DB (五表 JOIN) ──► 写入 Redis (带 TTL) ──► 返回

[角色/权限变更] ──► 1. 更新 MySQL ──► 2. 淘汰/删除对应用户的 Redis Key
```

- **用户权限 Key**：`rbac:user:{user_id}:perms`（使用 Redis **Set** 结构存储所有 `permission:code`，方便利用 `SISMEMBER` 或直接取回整集）。
- **角色关联用户 Key**：`rbac:role:{role_id}:users`（可选，记录哪些用户拥有该角色，用于角色权限修改时的精准批量淘汰）。

## 3. RBAC 服务层：结合 Redis 读写与失效 (`app/services/rbac_service.py`)

Python

```
from typing import Set
import redis.asyncio as aioredis
from sqlmodel import select
from sqlmodel.ext.asyncio.session import AsyncSession
from app.models.table import Permission, Role, UserRoleLink, RolePermissionLink

CACHE_TTL_SECONDS = 3600  # 缓存 1 小时


class RBACService:
    @staticmethod
    def _get_user_perm_key(user_id: int) -> str:
        return f"rbac:user:{user_id}:perms"

    @classmethod
    async def get_user_permission_codes(
        cls,
        user_id: int,
        db: AsyncSession,
        redis: aioredis.Redis
    ) -> Set[str]:
        """优先从 Redis 读取，未命中则回源查库并回写"""
        cache_key = cls._get_user_perm_key(user_id)

        # 1. 尝试从 Redis 读取 (获取 Set 中的所有成员)
        cached_perms = await redis.smembers(cache_key)
        if cached_perms:
            return cached_perms

        # 2. Cache Miss：从数据库执行五表 JOIN 查询
        stmt = (
            select(Permission.code)
            .join(RolePermissionLink, RolePermissionLink.permission_id == Permission.id)
            .join(UserRoleLink, UserRoleLink.role_id == RolePermissionLink.role_id)
            .where(UserRoleLink.user_id == user_id)
            .distinct()
        )
        result = await db.exec(stmt)
        perms = set(result.all())

        # 3. 写入 Redis 并设置过期时间 (管道批量操作)
        if perms:
            async with redis.pipeline(transaction=True) as pipe:
                pipe.sadd(cache_key, *perms)
                pipe.expire(cache_key, CACHE_TTL_SECONDS)
                await pipe.execute()
        else:
            # 即使没有任何权限，也可以存一个空标记（防止缓存穿透）
            await redis.setex(f"rbac:user:{user_id}:empty", 300, "1")

        return perms

    @classmethod
    async def is_admin(
        cls,
        user_id: int,
        db: AsyncSession,
        redis: aioredis.Redis
    ) -> bool:
        """判断是否为管理员，同样支持缓存"""
        admin_key = f"rbac:user:{user_id}:is_admin"
        cached_val = await redis.get(admin_key)
        if cached_val is not None:
            return cached_val == "1"

        stmt = (
            select(Role.id)
            .join(UserRoleLink, UserRoleLink.role_id == Role.id)
            .where(UserRoleLink.user_id == user_id, Role.code == "ADMIN")
        )
        result = await db.exec(stmt)
        is_admin_user = result.first() is not None

        # 缓存结果 1 小时
        await redis.setex(admin_key, CACHE_TTL_SECONDS, "1" if is_admin_user else "0")
        return is_admin_user

    # ================= 缓存主动淘汰方法 =================

    @classmethod
    async def evict_user_cache(cls, user_id: int, redis: aioredis.Redis):
        """场景 1：当给单个用户分配/解绑角色时，清空该用户的缓存"""
        keys_to_delete = [
            cls._get_user_perm_key(user_id),
            f"rbac:user:{user_id}:is_admin",
            f"rbac:user:{user_id}:empty"
        ]
        await redis.delete(*keys_to_delete)

    @classmethod
    async def evict_users_by_role(cls, role_id: int, db: AsyncSession, redis: aioredis.Redis):
        """场景 2：当管理员修改了某个角色的权限时，批量清除该角色下所有用户的缓存"""
        # 查询该角色下的所有用户 ID
        stmt = select(UserRoleLink.user_id).where(UserRoleLink.role_id == role_id)
        result = await db.exec(stmt)
        user_ids = result.all()

        if not user_ids:
            return

        # 批量删除这些用户的 Redis 缓存
        keys = []
        for uid in user_ids:
            keys.extend([
                cls._get_user_perm_key(uid),
                f"rbac:user:{uid}:is_admin",
                f"rbac:user:{uid}:empty"
            ])
        await redis.delete(*keys)
```

## 4. 依赖项无缝接入 (`app/api/deps.py`)

在 `require_perm` 依赖中同时注入 `get_redis`，全程对路由透明：



Python

```
from fastapi import Depends, HTTPException, status
from sqlmodel.ext.asyncio.session import AsyncSession
import redis.asyncio as aioredis

from app.core.database import get_db
from app.core.redis import get_redis
from app.models.table import User
from app.services.rbac_service import RBACService


def require_perm(*required_perms: str):
    async def checker(
        current_user: User = Depends(get_current_user),
        db: AsyncSession = Depends(get_db),
        redis: aioredis.Redis = Depends(get_redis)
    ) -> User:
        # 1. 检查管理员
        if await RBACService.is_admin(current_user.id, db, redis):
            return current_user

        # 2. 查缓存 / DB
        user_perms = await RBACService.get_user_permission_codes(current_user.id, db, redis)

        # 3. 校验交集
        if not (set(required_perms) & user_perms):
            raise HTTPException(
                status_code=status.HTTP_403_FORBIDDEN,
                detail=f"权限不足：需要拥有以下权限之一：{list(required_perms)}"
            )

        return current_user

    return checker
```

## 🚀 性能与稳定性保障技巧

1. **设置合理的 TTL（如 30-60 分钟）**：即使极端情况下缓存清理失败（如 Redis 网络超时），用户权限也会在 TTL 到期后自动同步。
2. **防缓存穿透**：如果用户没有任何权限（新注册用户），写入一个短期空标记，防止空权限用户每次请求都击穿到 MySQL。
3. **先改 DB，再删 Cache**：遵循 Cache-Aside 标准原则，务必在数据库事务 `commit()` 成功之后再执行 `redis.delete()`。
